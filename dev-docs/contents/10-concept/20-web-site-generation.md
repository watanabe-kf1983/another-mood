# Web サイトジェネレータとしての利用

**Proposal** (未着手の検討メモ。実装も tasks への登録もまだない)。Markdown の語彙 (H1-H6 / P / TABLE / UL) では表現しきれない内容を、どう扱うかの、現時点でのスタンス。2026-10-11 の検討の記録。

## 現時点でのスタンス

- **Markdown の出力木が正本で、HTML はその派生。** この軸は崩さない。
- **mood の HTML はプレビュー品質の既定表示**であり、それ以上を目指さない。本気でテーマを当てたい利用者は `output/` を MkDocs や自前の Hugo に食わせればよく、その道は正当なものとして案内する。
- **mood は第三者の資材を選んで抱え込まない。** 同梱テーマ、同梱レンダラ、同梱 CSS はしない。選択の所有は利用者側に置く。MIT でも NOTICE の運用は一度始まると以後ずっと続く。
- **計算は mood の中ではやらない。** ビルド内で他人のコードを走らせたくないので計算プラグインは断念した。計算はブラウザの砂場か、外部プログラムからの書き戻しで行う。
- **tap は副産物であって、バックエンドビルダーではない。** Firebase 等と競う話ではない。導入理由は「ソースを手で書く人が文書を主産物として欲しい」であり、「そのデータをついでにアプリから読みたい」には安く既定で応えるが、売り物にはしない。

## 三つのやり方

いずれも塞がない。安い順に、具体的な要望が出たものから足す。

| | CSS の差し込み口 | N2: HTML 出力形式 | tap + openapi.json |
|---|---|---|---|
| mood の拡張 / 保守コスト | 小。許可リストに一項目と `<link>` の切り替え。レンダラに依存しない | 大。HTML 用ヘルパー一式と組み込みテンプレートを `md` と二系統で保守し続ける | 中。build への tap 同梱と blob は小さいが、J5 (JSON Schema) は M13 を前提とする設計タスクで、以後もスキーマの機能追加に追従し続ける。フロント側の仕組みは増やさない |
| 利用者の利用コスト (フロント実装) | CSS 一枚。ただし Markdown の語彙は超えられない | Jinja2 で HTML を手書き。ヘルパー語彙は `md` と同じで、エージェントは現に難なく書けている。部品の生態系がない分、カードやグリッドは毎回 CSS を手で書く | SPA かビルドなしの HTML 一枚。エージェントが最も流暢に書ける領域で、typegen も効く |
| 運用コスト | ほぼなし。静的 HTML | ほぼなし。静的 HTML | 高。ツールチェーンを持ち、腐り、ブラウザでしか検証できず利用者がレビューしにくい。ビルドなしの HTML 一枚なら緩和 |

### CSS の差し込み口

`definition/site.css` があれば既定の github-markdown-css の `<link>` を出さず、それだけを読む。追加ではなく **置き換え** にする理由:

- `<head>` の stylesheet は描画をブロックする。社内プロキシが黙って落とす環境では、CDN への `<link>` が残っているだけでタイムアウトまで白画面になる。仕様書を社内で開く利用者がいちばん踏む。
- 置き換えなら「既定 CSS を外す」設定項目が要らない。github の見た目を保ちたい人は自分の CSS の先頭で `@import` すればよい。
- オフラインの利用者は自分で CSS を写せるので、mood が同梱する必要がない。

レンダラに依存しない形なので [N1](node:/tasks/N/tasks/N1) の足枷にならない。

### N2: HTML 出力形式

`md` と並ぶ `html` を OutputFormat に足す ([N2](node:/tasks/N/tasks/N2))。表現力は最大だが、ヘルパー一式と組み込みテンプレートを二系統で保守し、その edition では Markdown 出力木がなくなる。テンプレートに生の HTML が積み上がってから考える。

### tap + openapi.json (アプリの道)

mood は `tap` の JSON と契約書 openapi.json までを出し、表示は別物のフロントエンドに任せる。tap はテンプレートが受け取る名前空間そのもので view の評価結果まで入るので、フロントは「この JSON を表示する」だけで済む。node プロジェクトの中に sbdb プロジェクトが居座り、`mood tap` がビルドステップになる絵。フロントは配らない。watch 専用の仕組みは作らない。view を SPA 向けに拡張しない。

この道の本当の動機は計算を安全な場所でやること。様式は二つ。

- **ブラウザで計算**: 見るだけ、対話的、結果は文書に戻らない。
- **外部プログラムで計算して JSON を `contents/` に書き戻す**: 結果が文書と git に入る。実行は利用者の責任で mood の外。

SPA しか作らない利用者には view の層は不要で、mood は前半 (schema + normalize + tap) だけのコンパイラとして使われる。view が効くのは、文書と SPA の両方を同じデータから出すときと、データの持ち主とフロントの書き手が別人のとき。

フロントをエージェントに書かせるコストは、書く側は Jinja2 テンプレートより安く、持つ側 (ツールチェーン、ブラウザでしか検証できない、利用者がレビューできない、腐る) は高い。ビルドなしの HTML 一枚 + `fetch` という中間があり、フロントに疎い利用者の最初の形として妥当。mood 側の作業はフロントの形に依存しないので、いま決めなくてよい。

mood 側に要るもの (着手するときに tasks へ起こす):

1. build に tap を同梱し、blob も `tap/blob/<id>` へ。[J5](node:/tasks/J/tasks/J5) に依存しない。tap は compose 出力の直列化だけなので安い。edition ではなく publish の第三の宛先として扱う
2. watch に `--tap-dir` (`--out-dir` と同じ opt-in の流儀)
3. [M13](node:/tasks/M/tasks/M13) → [J5](node:/tasks/J/tasks/J5)
4. tap 出力に openapi.json を添える。`GET /tap` 相当と `GET /blob/{id}`。ファイル名が URL になるので `data.json` の名前は要検討。prose の `node:` リンク形式は description に書く
