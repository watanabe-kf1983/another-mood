# Tap Specification

Compose 結果を機械可読な形で外部に取り出す経路（`mood tap`）の設計。

## Proposals

### compose 結果の取り出し (J3)

`mood tap <project_dir>` で、compose 段階の結果（エンティティデータ + ビュー）を一塊の JSON ドキュメントとして出力する。MCP からも同じ機能を提供する。（tap = パイプラインの途中に口をあけ、混ざったものを流れを止めずに抜き出す）

想定する利用者は二種類:

- **外部プログラム** — 出力を読んで計算する（動機となった実例: 設計ドキュメントの構造化データから Function Point を算出する）
- **エージェント** — `mood tap . | jq` の形でデータを照会する

#### 背景: なぜソースを直読みさせないのか

利用者が `contents/` の YAML を直接読めば済むように見えるが、ソースは**著者が書きやすい形**であって**照会しやすい形**ではない。tap はその差を埋める:

1. **形が揃う** — ソースは map パターン（`{id: {...}}`）で書けるが、tap の出力は正規化後の配列（`[{id: ..., ...}]`）。`jq 'map(select(...))'` がそのまま効く
2. **マージ済み** — ソースは複数ファイルに分かれ、ビルド時に deep-merge される。直読みでは利用者側がマージを再実装することになる
3. **形式が一本化される** — ソースは YAML と Markdown が混在する（prose は Markdown ファイル）。tap の出力は 1 本の木
4. **ビューが入る** — join・グループ化された結果はソースには存在しない。導出データは tap でしか取れない

1〜3 は外部プログラムに、4 は主にエージェントの照会に効く。

#### 出力の範囲

compose 出力のトップレベル名前空間をそのまま出す。`__definition` や built-in メタビュー（`__entity_defs` 等）を含め、**除外しない**。

除外規則を持たないほうが契約が単純で、「jq で探しに行く」前提とも整合する。何が入っているかは `jq 'keys'` で分かる。

#### 一塊で出す（部分指定を設けない）

トップレベルビューを選ぶ引数は設けない。絞り込みは利用者の道具（jq / yq）に任せる。

検討時に「dev-docs では出力の 7 割以上が prose の Markdown 本文で、Function Point 算出が読みたいのは `categories` の 32K だけ」という理由で部分指定を検討したが、実測すると全体でも 200KB / 0.16 秒で、jq に流す分にはコストとして数えるに値しなかった。セレクタは jq が既にできることを狭い形で再実装するだけになる。

#### 照会の口は持たない

tap が提供するのは**成果物を作ることだけ**で、それを絞り込む手段（jq 式の引数など）は CLI にも MCP にも持たせない。絞り込みは利用者の道具に委ねる。

```
mood tap <project_dir> [--out <path>]     # 既定は stdout
tap(project_dir)                          # MCP: ファイルに書き、パスを返す
```

MCP が **payload を返り値に載せない**のが要点。200KB の木を tool result に乗せるとエージェントのコンテキストを圧迫する。返すのはパスだけで、キー一覧などの要約も付けない（後述の自己記述で足りる）。

##### 背景: なぜ jq 引数を持たせないのか

検討過程では「MCP に `jq` 引数を持たせ、CLI にも同じ `--jq` を置く」案を採っていた。理由は「tap の実行はファイル操作ではなくコマンド実行であり、MCP クライアントがファイルツールを持っていてもシェルを持つとは限らない。シェルを持たないエージェントには、生成はできても照会する手段が残らない」というもの。

この理由付けは、対象読者を場合分けすると成立しないことが分かった:

| クライアント | ファイルシステム共有あり | 共有なし |
|---|---|---|
| シェルあり | パスが効く。ただし `mood tap` を自分で叩けるので MCP 経由である必要が薄い | パスは無意味。jq だけが効く |
| シェルなし | パスは返るが、照会手段は丸読みしかない → jq が要る | 何も効かない |

つまり jq 引数が救うのは**シェルを持たないクライアントだけ**で、その読者は現時点で仮想的である（実需の外部プログラムは CLI 経路、エージェント照会の実体はいずれもシェルを持つ）。そして jq 引数は後から**純粋な引数追加**として足せる（既存の呼び出しも出力も壊れない）。仮想の読者のために、jq エンジンの依存（PyPI `jq` は C 拡張）とエラー面・結果フォーマットの設計を先に払う理由がない。

副次的に、mood 側が jq の口を一切持たないことで「クエリ言語が二つあるのはどちらで書くのか」という混乱も生じない。mood が持つクエリ概念はビュー定義の DSL（[query-dsl-spec](10-query-dsl-spec.md)）ひとつで、jq は利用者が勝手にパイプする外部の道具にすぎない。

#### 探索の定石: 出力は自己記述している

照会を利用者に委ねられるのは、出力の木が自分自身の構造を含んでいるため。トップレベルは「contents 由来のエンティティ + ビュー結果 + `__definition`」で、`__definition.entities` にはその両方の定義（属性まで）が入る。

```bash
mood tap . | jq 'keys'                              # 何が入っているか
mood tap . | jq '.__definition.entities | map(.id)' # 定義されている型
```

MCP がキー一覧を返り値に付けたとしても、これの劣化コピーにしかならない。docs 側にはこの定石を書く。

#### 出力フォーマット: JSON のみ

**照会を利用者の jq に委ねる以上、そのまま jq に食わせられる形でなければならない**（jq は YAML を読まない）。外部プログラムが標準ライブラリだけで読めるのも JSON。第一版は JSON 単独とし、YAML 出力は実需が現れたら足す（これも純増）。

検討の記録として: **シリアライズ速度もトークン量も判断根拠にならない**ことを実測で確認済み（dev-docs 全体で YAML 152ms / JSON 0.7ms、いずれもビルド全体に対して誤差。トークンは YAML が JSON 比 1〜6% 減にとどまり、実測でも 21K 対 20K）。LLM がどちらを読みやすいかも、公開ベンチマークがモデル依存で割れており根拠にできない。

YAML 側に唯一残る実質的な利点は、prose の複数行本文が literal block で展開されて grep や行指定読みが効くこと（JSON では 1 行に潰れる）。ただしこれは「生ファイルを人・エージェントが直接読む」前提の利点で、照会は jq に通す前提と噛み合わない。

#### 残論点

- ファイル出力先。CLI は stdout 既定で `--out <path>`、MCP はファイル書き出し、を想定している
- compose で止める実装形。generate 以降を走らせないため、テンプレートが壊れていてもデータ層を取り出せるという副次的な利点がある

#### 対象外: contents への還流

J3 の元の note は「tap → 外部計算 → contents 還流」のラウンドトリップをガイド化する想定を含んでいたが、本タスクの対象からは外す。還流が必要になるかどうかはまだ分かっておらず、ガイド化は還流の実需の形が見えてからで遅くない。取り出し経路の整備だけで J3 の動機（外部計算への入力を取り出せること）は満たせる。

なお [M11](node:/tasks/M/tasks/M11)（入力形式に JSON を追加）後は JSON 出力もそのまま別プロジェクトの `contents/` に置けるため、mood → mood の連携（複数プロジェクトの tap 出力を横断プロジェクトが集約する等）は入口・出口とも機械可読で閉じる。還流の実需が現れたときの受け口はある。

計算結果を通常の contents YAML として書き戻すことは現状でも可能で（schema / x-ref 検証も効く）、新たな仕組みを要しない。実需が現れた時点で改めて検討する。
