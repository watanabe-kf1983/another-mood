# Export Specification

Compose 結果を機械可読な形で外部に取り出す経路の設計。

## Proposals

### クエリ結果の機械可読エクスポート (J3)

`mood export <project_dir>` で、compose 段階の結果（エンティティデータ + クエリ結果）を一塊のドキュメントとして出力する。MCP からも同じ機能を提供する。

想定する利用者は二種類:

- **外部プログラム** — 出力を読んで計算する（動機となった実例: 設計ドキュメントの構造化データから Function Point を算出する）
- **エージェント** — `export | jq` の形でデータを照会する

#### 背景: なぜソースを直読みさせないのか

利用者が `contents/` の YAML を直接読めば済むように見えるが、ソースは**著者が書きやすい形**であって**照会しやすい形**ではない。export はその差を埋める:

1. **形が揃う** — ソースは map パターン（`{id: {...}}`）で書けるが、export は正規化後の配列（`[{id: ..., ...}]`）。`jq 'map(select(...))'` がそのまま効く
2. **マージ済み** — ソースは複数ファイルに分かれ、ビルド時に deep-merge される。直読みでは利用者側がマージを再実装することになる
3. **形式が一本化される** — ソースは YAML と Markdown が混在する（prose は Markdown ファイル）。export は 1 本の木
4. **クエリ結果が入る** — join・グループ化されたビューはソースには存在しない。導出データは export でしか取れない

1〜3 は外部プログラムに、4 は主にエージェントの照会に効く。

#### 出力の範囲

compose 出力のトップレベル名前空間をそのまま出す。`__definition` や built-in メタビュー（`__entity_defs` 等）を含め、**除外しない**。

除外規則を持たないほうが契約が単純で、「jq で探しに行く」前提とも整合する。何が入っているかは `jq 'keys'` で分かる。

#### 一塊で出す（部分指定を設けない）

トップレベルビューを選ぶ引数は設けない。絞り込みは利用者の道具（jq / yq）に任せる。

検討時に「dev-docs では出力の 7 割以上が prose の Markdown 本文で、Function Point 算出が読みたいのは `categories` の 32K だけ」という理由で部分指定を検討したが、実測すると全体でも 200KB / 0.16 秒で、jq に流す分にはコストとして数えるに値しなかった。セレクタは jq が既にできることを狭い形で再実装するだけになる。

#### MCP の形

```
export(project_dir, jq=None)
```

- `jq` を指定すると jq 式として評価し、結果を返す
- 省略すると出力をファイルに書き、そのパスを返す

パラメータ名は `query` ではなく `jq` とする（`gh` CLI の `--jq` フラグに倣う）。`query` の語はビュー定義の DSL（[query-dsl-spec](10-query-dsl-spec.md)）に予約されており、jq 式を query と呼ぶと語彙が衝突する。名前から「jq 式である」ことが自明になる利点もある。

**payload を返り値に載せない**のが要点。200KB の木を tool result に乗せるとエージェントのコンテキストを圧迫する。

##### 背景: なぜ MCP に jq を持たせるのか

当初は「MCP はファイルを生成するだけにし、jq はエージェントが自分で叩く」案を検討したが、これは成立しない。**`mood export` の実行はファイル操作ではなくコマンド実行**であり、MCP クライアントがファイルツールを持っていてもシェルを持つとは限らず、持っていても `mood` が PATH にいる保証がない（MCP サーバは別環境から起動されうる）。シェルを持たないエージェントには、生成はできても照会する手段が残らない。

`build` を MCP ツールとして提供しているのと同じ理由が export にも当てはまる。CLI 側にも同じ `--jq` を持たせ、[mcp-design.md](../20-app/30-mcp-design.md) の「MCP と CLI の論理的機能は一致すべき」を満たす。

##### 背景: クエリ言語が二つになることの整理

このツールは既にビュー定義の DSL という第一級のクエリ概念を持つため、jq 式の口を開けると「どちらで書くのか」という疑問が生じる。役割で言い分けられる:

- ビュー定義（G11 後は `definition/views/`）— **ビルド時・宣言的・データベース定義の一部**。出力ドキュメントに現れるビューを作る
- export の `jq` — **アドホック・読み取り専用・ビルドの外**。出力には一切影響しない

「出力を作るのがビュー定義、出力を作らずに覗くのが jq」。パラメータ名を `jq` に固定したことで、query の語はビュー定義側に一本化される。

#### 出力フォーマット

YAML / JSON の両対応。**既定は未決**。

決めるにあたって、**シリアライズ速度は根拠にならない**ことを実測で確認済み（dev-docs 全体で YAML 152ms / JSON 0.7ms、いずれもビルド全体に対して誤差）。トークン量も差がない（YAML は JSON 比 1〜6% 減にとどまり、実測でも 21K 対 20K）。

残る判断材料:

- **JSON 寄り** — jq が要求する。外部プログラムが標準ライブラリだけで読める。LLM の構造理解では明示的な区切り文字が有利という説がある（ただし後述のとおり証拠は割れている）
- **YAML 寄り** — prose の複数行本文が literal block で展開されるため、grep や行指定読みが効く（JSON では 1 行に潰れる）。プロジェクトの他ファイルが全て YAML

LLM がどちらを読みやすいかは、公開ベンチマークの結果がモデル依存で割れており、判断の根拠にできる状態にない。なお `query` 経路を設けたことでエージェントは生ファイルを読まなくなるため、この論点自体の重みが下がっている。

#### 残論点

- 出力フォーマットの既定
- MCP が `jq` の結果を返すときの形式（結果は小さいことが多いので YAML が読ませやすい、という見込みはある）
- ファイル出力先。CLI は stdout 既定で `--out <path>`、MCP はファイル書き出し、を想定している
- compose で止める実装形。generate 以降を走らせないため、テンプレートが壊れていてもデータ層を取り出せるという副次的な利点がある

#### 対象外: contents への還流

J3 の元の note は「export → 外部計算 → contents 還流」のラウンドトリップをガイド化する想定を含んでいたが、動機となった実需（Function Point 算出）では**還流は必要ない**ことが確認できたため、本タスクの対象から外す。

計算結果を通常の contents YAML として書き戻すことは現状でも可能で（schema / x-ref 検証も効く）、新たな仕組みを要しない。実需が現れた時点で改めて検討する。
