# プロジェクトマニフェスト (sbdb.yaml)

## External Design

プロジェクトの識別と、フォーマット互換性の契約を担うマニフェスト。

### マニフェスト `sbdb.yaml`

マニフェストは `<projectDir>` の直下に置く。Cargo.toml や package.json と同じ置き方で、`contents/` の外にあるので contents を編集する人の目には入らない。各フィールドの書き方と意味は `docs/reference/manifest.md` が正本で、本節は設計判断だけを書く。

author や license のようなメタ情報は、あとから足しても互換性を壊さないので今は載せない。逆に、`sbdb_version` の欄名と形式、および `tools.<name>` の形は**永久に凍結する**。古いツールが未来の世代のファイルを開いたとき「このファイルには対応できない」と正しく断るには、少なくとも版を宣言するこの二欄だけは、どの世代でも同じ場所に同じ形で書かれていなければならないからである（背景で述べる edition と minimum version の宣言欄がこれにあたる）。

CWD 側に置く設定ファイル（[設定システム仕様](node:/prose/20-design/20-app/20-config-spec) の G2）とは別物である。設定は「どうビルドするか」を決めるもので、環境やツールの設定として CWD 側にある。マニフェストは「このプロジェクトは何か」を宣言するもので、識別と互換性の契約として projectDir 側にある。

### 背景: 問題の型と、定番の三つの道具

ここで扱うのは「人間が書いた成果物（フォーマット）を、それとは独立に進化するツールが読む」ときの互換性問題である。成果物とツールのそれぞれに新旧があるので 2×2 の組み合わせができ、新旧が食い違う二つの組み合わせが危険になる:

- **旧ソースを新ツールが読む**（後方互換）— ツールが旧世代の意味論を変えたのに、旧ソースをそのまま解釈してしまう
- **新ソースを旧ツールが読む**（前方互換）— 旧ツールが知らない構文を黙って読み飛ばしてしまう

どちらも、エラーを出さずに壊れた出力が出る「静かな破損」になりうる。本設計の目的は、これを検出して**はっきり失敗させる**ことにある。古いソースを自動で移行することはスコープ外。

この型の問題に対して、成熟したエコシステムはほぼ同じ道具立てに落ち着いている:

1. **edition**（Rust の edition、Kubernetes の apiVersion、Compose file の version）— 人間がソースの一箇所に世代を宣言する。番号が上がるのは**破壊的変更のときだけ**。ツールは対応する世代の集合を持ち、集合の外なら拒否する。整数の比較だけで前後両方向の互換性を守れる。宣言欄の位置と形式は永久に凍結する（古いツールにも読めなければならないため）
2. **minimum version**（Rust の rust-version、Terraform の required_version、package.json の engines）— 「このソースにはバージョン X 以上のツールが要る」という任意の宣言。追加された機能への依存を表明でき、「ツールをアップグレードしてください」という正確なエラーを出せる。宣言が古くなって実態とずれることは、どのエコシステムでも許容されている
3. **厳格パース** — 知らない構文・キー・演算子を黙って読み飛ばさず、エラーにする。宣言が何もなくても静かな破損だけは起こさない、最後の防衛線

「新ソースを旧ツールが読む」場合をさらに分けると、新しい**構文**（仕様の追加）は厳格パースが構文エラーとして捕まえる。本当に静かに壊れるのは、既存の構文の**意味が変わった**とき（破壊的変更）だけで、それを受け持つのが edition である。だから edition は仕様追加では動かず、改版が頻発することはない。

ビルド時にバージョンを自動で書き込む方式は、lock ファイルや DB ファイルのような機械が書く成果物のための道具である。人間が書くソースへの版の宣言は、どのエコシステムでも人間が書いている。

本設計はこの道具立てをそのまま採用する。以下の各節で、edition と minimum version はマニフェストの二つの欄として、厳格パースは欄ではなくツール側の設計義務として定める。

### `sbdb_version`（edition）

`sbdb_version` はフォーマットの世代を表す整数で、宣言とチェックの単位はこの一つだけである。フォーマットを構成する領域（スキーマ・ビュー・テンプレートなど）ごとに版を分けることはしない。

語るのは、ソースとツールの**フォーマット互換のみ**。ツール自身の利用者向け契約（CLI 等）を壊す変更はソースにもマニフェストにも関係せず、「破壊」としての扱いはリリースフローの管轄になる。sbdb_version はツール中立なスペックの所有物で、mood の CLI 変更で上げるのはスペック/ツール分離の破壊になるため。

#### フォーマットを構成する契約面

| 契約面 | 契約書 |
|---|---|
| schema | `resources/schemas/schema-schema.yaml` |
| view | `resources/schemas/view-schema.yaml` |
| parser/prose | Markdown 解釈規約 + `content-schema.yaml`（組み込み prose/blob）+ 埋め込み構文 |
| template | フィルタ・タグ・グローバルの登録面（コードが契約） |
| layout | プロジェクト配置規約（`definition/` / `contents/`） |
| manifest | `sbdb.yaml` 自体（凍結欄を除く） |

contents は**独立の契約面を持たない**: YAML レコードを縛る契約はユーザの schema.yaml であり、mood の変更が contents の意味を変える事態は必ず schema 面か parser/prose 面の変更として現れる。ゆえに版宣言は definition 側の関心で、contents 編集者は versioning の存在を知らなくてよい。

#### 版が上がる条件

ある変更（PR の差分）が破壊的かどうかは、契約面のいずれかを非互換に編集したかで判定する。どの面がどの世代で非互換に動いたかの履歴は持たない。エラーメッセージ・移行ガイドの粒度は、破壊的 PR 自身が docs に書く移行手順から得る。

フォーマット破壊の定義（対応集合からの世代脱落）と、破壊的 PR が含めるべき追随一式は[リリースフロー](node:/prose/30-dev/50-release)の管轄。

#### 欠落の扱い

`sbdb_version` は必須とする。無ければチェックのしようがなく、宣言を忘れた新世代のソースを旧世代として黙って解釈してしまうのは、本設計が防ぎたい静かな破損そのものだからである。`mood init` と blueprint が自動で書き込むので、新しく使い始める人に手間はかからない（省略時のフォールバックを持たない理由は[背景](../../90-appendix/20-design/20-app/60-sbdb-manifest.md#cargo-との比較)）。

同じ理由で、`sbdb.yaml` というファイルそのものが無い場合もエラーにする（欄が無い場合と区別しない）。つまりマニフェストがあることがプロジェクトの成立条件で、ビルドはマニフェストの無いディレクトリを受け付けない。

エラーメッセージは事実だけを述べ、対処は書かない。このエラーに至る現実的な経路はディレクトリの指し間違いで、そこで対処を示してもノイズにしかならないためである（[背景](../../90-appendix/20-design/20-app/60-sbdb-manifest.md#エラーメッセージの文言)）。

### `tools.another-mood.minimum_version`（minimum version）

フォーマット（source-based DB、識別子 **sbdb**）はツールに依存しないスペックで、Another Mood はそれを処理するツールの一つにすぎない（[style guide](../../30-dev/40-style-guide.md) の Means の定義）。だからスペックの語彙にツール名を混ぜない。minimum version は本質的に「ツールごと」の関心なので、pyproject.toml が `[project]` と `[tool.<name>]` を分けているのに倣い、`tools:` 名前空間の下に置く。将来別のプロセッサが現れたらそれぞれが自分の行を持ち、他のツールの行は互いに無視する。

細かな仕様は minimum version の先例に合わせる（[背景](../../90-appendix/20-design/20-app/60-sbdb-manifest.md#minimum-version-の細目)）:

- **受け付けるのは素のバージョンだけ**で、範囲指定は受けない。将来必要になれば、別の欄を互換性を壊さずに足せる
- **宣言の意味は「この版で動くことを確認した」という検証済みの下限**で、本当の最小版を調べることは求めない。下限にすぎないので、scaffold は生成時に実行中のバージョンを機械的に書き込んでよい

### 厳格パース（ツールの設計義務）

**設計義務として明文化する**: mood が定める語彙（スキーマのキー、クエリの演算子、タグ、フィルタ、マニフェストのキー）に知らない入力があれば、黙って読み飛ばさずエラーにする。将来の機能追加もこの性質を保つこと。これが、版を宣言していない、あるいは宣言を更新していない利用者にとっての最後の防衛線になる。

edition は破壊的変更のときにしか動かず、minimum version は任意の宣言で、古くなることも許している。そのため「追加された機能を使うソースを、古い宣言のまま、旧 mood で読む」組み合わせをはっきり失敗させられるのは、この義務だけである（minimum version を下限と定めて宣言の放置を許した以上、避けられない帰結）。逆に、新しい構文が必ずエラーになるおかげで、edition は意味が変わるときだけ番号を上げれば済む（背景の「新ソースを旧ツールが読む」の分解）。三つの道具は保険の重ね掛けではなく、分業になっている。

この義務を契約面ごとに誰が担うか（契約面の区切りは「フォーマットを構成する契約面」の表と同じ）:

| 契約面 | 知らない入力の扱い |
|---|---|
| schema / view | メタスキーマの `additionalProperties: false` により、知らないキーは検証エラーになる。contents の語彙はユーザの schema.yaml が決めるものなので対象外 |
| parser/prose | 構造的に対象外。本文は自由な Markdown で、「知らない入力」と本文を区別できないため、意味変更からの防衛は edition に全面的に委ねる |
| template | 知らないタグ、知らないフィルタ、未定義のグローバルの呼び出しはどれもエラー。未定義の変数参照が空文字になるのは、ユーザデータに由来する名前に対する書き味であって互換性の穴ではない（mood の機能追加でテンプレート変数が増えることはない） |
| layout | `definition/` 直下には既知のエントリ以外を置けない。プロジェクト直下は `.git` や `README.md` と同居する設計なので、構造的にエラーにできない。`views/` 配下はビュースキーマの検証が受け持ち、`templates/` はユーザが名付ける開いた名前空間なので、検査の深さは直下で止めて完備とする |
| manifest | 読み込み時の厳格検証（知らないキーの拒否。Internal Design のゲート実装）が兼ねる |

## Internal Design

### ゲートの実装（`components/manifest`）— 二段読み

マニフェストは二段で読む。最初は凍結欄（`sbdb_version` / `tools.another-mood.minimum_version`）だけを読んで互換ゲートにかけ、通過後にマニフェスト全体を厳格検証する。ゲートの順序とその理由は `manifest.py` の `read_manifest` に記載してある。

対応集合は定数一行の専用モジュール `supported_sbdb_versions.py` に単独で置く。このファイルの diff が、リリース側の破壊検知の信号になる（[リリースフロー背景](node:/prose/30-dev/55-release-background)）。

### showcase / dev-docs の実物マニフェスト

`minimum_version` は置かない。これらのプロジェクトは実装ワークフロー（機能 PR が
showcase の入出力例を義務で伴う）により構造的に常に未リリースの HEAD 機能へ依存する
ため、正直なフロア = 次版は宣言できず（dev 版 < リリース版のためゲートに落ちる）、
実在版での凍結は「その版で動くことを確認済み」という恒久の偽宣言、リリース追随は
bump コミットの再発明であり「版宣言の正本は git tag ただ一つで、bump コミットという工程はない」というリリースフロー
側の前提を崩し、多ファイル版整合という release-please の解く問題の自作になる
（[リリースフロー](node:/prose/30-dev/50-release)）。真実を宣言できない
任意欄は宣言しないのが正直。フィールドの実例は `docs/reference/manifest.md` と
scaffold の生成物（実行中版を機械スタンプ）が務め、旧 mood × 新ソースの防衛は
厳格パースが受ける。
