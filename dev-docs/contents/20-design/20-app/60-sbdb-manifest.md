# プロジェクトマニフェスト (sbdb.yaml)

## External Design

プロジェクトの識別と、フォーマット互換性の契約を担うマニフェスト。

### マニフェスト `sbdb.yaml`

`<projectDir>` 直下に置く（Cargo.toml / package.json の慣習。`contents/` の外なので
contents 編集者の視界に入らない）。

```yaml
sbdb_version: 1             # 必須 — フォーマット世代
title: My Project           # 任意 — 省略時はディレクトリ名にフォールバック（現行挙動）
tools:                      # 任意 — 各プロセッサの名前空間
  another-mood:
    minimum_version: "0.3.5"   # 任意 — このツールの最低バージョン
```

| フィールド | 必須 | 意味 |
|---|---|---|
| `sbdb_version` | **必須** | フォーマット世代。整数。欠落 = エラー |
| `title` | 任意 | 表示名。トップページ等で使用。省略時はディレクトリ名 |
| `tools.<processor>.minimum_version` | 任意 | プロセッサ固有の最低バージョン要求。素のバージョン（演算子・レンジなし） |

author / license 等のメタ情報は additive に追加できるため今は載せない。逆に
`sbdb_version` の欄名・形式と `tools.<name>` の形は**永久凍結**——旧版のツールが
未来世代のファイルを開いたとき「対応できない」と正しく断るには、少なくとも版宣言の
二欄だけはどの世代でも同じ場所・同じ形で読める必要があるため（下記背景の道具1・
道具2 の宣言欄にあたる）。

なお CWD 側の設定ファイル（[設定システム仕様](node:/prose/20-design/20-app/20-config-spec)
の G2）とは別物: config は「どうビルドするか」（環境・ツール設定、CWD 側）、
マニフェストは「このプロジェクトは何か」（識別・互換契約、projectDir 側）。

### 背景: 問題クラスと一般論の三道具

「人間が書いた成果物（フォーマット）を、独立に進化するツールが読む」系の互換性問題。
成果物とツールの新旧で 2×2 の行列ができ、対角以外の 2 マスが危険:

- **① 旧ソース + 新ツール**（後方互換）— ツールが旧世代の意味論を変えたのに旧ソースをそのまま解釈する
- **② 新ソース + 旧ツール**（前方互換）— 旧ツールが未知の構文を黙って読み飛ばす

どちらも「黙って壊れた出力が出る」silent 破損があり得る。本設計の目的はこれを検出して
loud に失敗させること。マイグレーション（自動移行）はスコープ外。

この問題クラスに対し、成熟したエコシステムはほぼ同じ道具立てに収斂している:

1. **edition 型**（Rust edition / Kubernetes apiVersion / Compose file version）—
   人間がソース内の一箇所に宣言。**破壊的変更のときだけ** +1。ツールは対応する版の
   集合を持ち、範囲外なら拒否。整数比較だけで①②両方向を守る。宣言欄の位置・形式は
   永久凍結（旧ツールも読めなければならないため）
2. **MSRV 型**（Rust rust-version / Terraform required_version / package.json engines）—
   「このソースはツール ≥ X が必要」の任意宣言。追加機能への依存を表明し、正確な
   「アップグレードしてください」エラーを出せる。宣言の陳腐化はエコシステム的に許容
3. **厳格パース**—未知の構文・キー・演算子を黙って読み飛ばさずエラーにする。
   宣言が無くても silent 破損だけは起こさない最終防衛線

②を分解すると: 新**構文**（仕様追加）は道具3 が構文エラーとして捕捉し、
既存構文の**意味変更**（破壊的変更）だけが本当に silent —— それは道具1 の管轄。
ゆえに edition は仕様追加では動かず、めまぐるしい改版サイクルは起きない。

なお、ビルド時の自動スタンプはマシンが書く成果物（lock ファイル・DB ファイル）の
道具であり、人間が書くソースへの版宣言はどのエコシステムでも人間の宣言で行う。

本設計はこの道具立ての直接の採用で、以下の各節で定める: 道具1・道具2 は
マニフェストの二欄として、道具3 は欄ではなくツール側の設計義務として。

### `sbdb_version`（道具1: edition 型）

必須とする理由: 無ければチェック不能であり、「宣言忘れの新世代ソースを旧世代として
黙って解釈する」のは本設計が防ぎたい silent そのもの。Cargo の「省略 = 最古 edition」
フォールバックは既存資産を壊せない事情ゆえの妥協で、pre-1.0 の本ツールには不要。
`mood init` / blueprint が自動で書き込むため新規利用者の摩擦はない。

同じ理由で `sbdb.yaml` ファイル自体の欠落もエラーとする（欄の欠落と区別せず扱う）。
すなわちマニフェストの存在がプロジェクトの成立条件であり、ビルドは manifest なしの
ディレクトリを受け付けない。

エラーメッセージは事実のみを述べ、対処を書かない
（`No sbdb.yaml in <dir>: not an Another Mood project.`）。ここに至る現実的な経路は
ディレクトリの指し間違いで、そこでは対処の提示はノイズにしかならないため
（uv の `No pyproject.toml found` と同じ判断）。「`mood init` してください」に至っては
マニフェストだけ失ったプロジェクトには効かない（init は既存プロジェクトへの scaffold を
拒む）。主語を（存在しない）ファイルではなくディレクトリに置くのは、無いファイルの
パスから始めると読み手がまずそのファイルを探しに行くため。

宣言・チェックの単位は、この単一の `sbdb_version` 番号のみ。フォーマットを構成する
領域（スキーマ・ビュー・テンプレート等）ごとに版を分けることはしない。どの変更が
世代を上げるか（判定基準）と、世代の記録・運用は Internal Design の
「世代の運用」節で定める。

### `tools.another-mood.minimum_version`（道具2: MSRV 型）

フォーマット（source-based DB, 識別子 **sbdb**）はツール中立のスペックであり、
Another Mood はその *a processor*（[style guide](../../30-dev/40-style-guide.md) の
Means 定義）。ゆえにスペックの語彙に
ツール名を混入させない。道具2 は本質的に「ツールごと」の関心なので、pyproject.toml の
`[project]` / `[tool.<name>]` 分離に倣い `tools:` 名前空間に置く。将来別のプロセッサが
現れたら自分の行を持ち、他ツールの行は互いに無視する。

細目は MSRV 型の先例に倣う: 「ビルドツールがソースのマニフェストを読む」系
（Go / Rust `rust-version` / CMake）と同じく素のバージョンのみを受け（レンジ語彙は
依存解決器を持つ系のもの — 上限は書く時点で知り得ず、除外はツールの性質であって
ソースの宣言ではない。将来必要になれば別欄を additive に足せる）、宣言の意味は
「この版で動くことを確認済み」という**検証済みフロア**で、真の最小版の監査は
要求しない（`uv add` が現行版で下限を切る実務と同じ）。フロアゆえに scaffold は
生成時に実行中バージョンを機械的にスタンプしてよい。

### 厳格パース（道具3: ツールの設計義務）

**設計義務として明文化**: mood 由来の語彙（スキーマキー・クエリ演算子・タグ・
フィルタ・マニフェストキー）に対する未知の入力は、黙って読み飛ばさずエラーにする。
将来の機能追加はこの性質を保つこと。これが版宣言を持たない/更新しない利用者への
最終防衛線になる。

道具1 は破壊的変更でしか動かず、道具2 は任意宣言で陳腐化も許容するため、
「追加機能を使うソース × 古い宣言 × 旧 mood」の組はこの義務だけが loud にできる
（道具2 のフロア意味論が宣言の放置を明示的に許した帰結）。逆に、新構文が必ず
エラーになるおかげで道具1 は意味変更のときだけ +1 で済む（背景の②分解）——
三道具は保険の重ね掛けではなく分業になっている。

監査（2026-07）。面の区切りは世代の運用（Internal Design）の契約面と同じ —
契約面が道具1 の判定基準、この監査が道具3 の網羅確認で、どちらも
「mood 由来の語彙」の同じ境界を見る:

- **schema / view** — 完備。メタスキーマが `additionalProperties: false` を徹底しており
  未知キーは検証エラー（contents の語彙はユーザの schema.yaml の管轄であり対象外 —
  世代の運用と同じ整理）
- **parser/prose** — 道具3 の適用対象外（構造的に）。prose 本文は自由な Markdown で
  あらゆる文字列が合法 — 「未知の入力」と本文が区別できず、エラーにする余地がない
  （node: 形式へ正規化するリンク以外は書かれたまま通す）。この面の意味変更の防衛は
  道具1（世代判定）に全面委任する
- **template** — 完備。未知タグ = `TemplateSyntaxError`、未知フィルタ =
  `TemplateAssertionError`、グローバルは callable のみで Undefined の呼び出しは
  `UndefinedError` — mood 由来の名前はすべて loud。変数・フィールド参照の
  `ChainableUndefined`（空文字）はユーザデータ由来の名前に対する書き味の設計であり、
  バージョン互換の穴ではない（mood の機能追加でテンプレート変数が増えることはない —
  そこはユーザ定義領域）
- **layout** — 完備。プロジェクト直下は `.git` / `README.md` 等との同居が
  設計であり loud 化は構造的に不可（scaffold の `cargo init` 型と同根の判断）。
  mood の管轄領域である `definition/` 直下は既知エントリ以外を拒否する。深さを直下で
  止めても完備なのは、その下が `views/` はビュースキーマ検証の管轄、`templates/` は
  ユーザが名付ける開いた名前空間で閉じた既知集合を持たないため
- **manifest** — 完備。マニフェスト読み込みの厳格検証（未知キー拒否 — Internal Design
  のゲート実装）が道具3 を兼ねる

## Internal Design

### ゲートの実装（`components/manifest`）— 二段読み

マニフェストは二段で読む——最初は凍結欄だけ、ゲート通過後に全体。手順は三つ:

1. **緩い抽出** — パイプラインの何よりも先に、凍結欄（`sbdb_version` /
   `tools.another-mood.minimum_version`）だけを読む。未知キーがあってもこの段階では無視
2. **互換ゲート** —
   - `minimum_version` があり実行中バージョンが不足 → 「mood を X 以上に上げてください」
     で即死（最も正確なエラー、パース前の fail-fast）
   - `sbdb_version` がツールの対応集合外 → 拒否。当面の対応集合は現行世代のみ
     （厳密一致 `{1}`）。対応レンジ `[Gmin..Gmax]` は将来、後方互換に拡張できる
3. **厳格検証** — ゲート通過後にマニフェスト全体を道具3 の対象として検証
   （未知キー拒否）

厳格検証をゲートの後に置く理由: 新 mood で書かれたマニフェストに未来のキーがあるとき、
旧 mood が「未知キー」で先に死ぬと `minimum_version` のヒントを出す前に倒れるため。

コード上は `read_manifest` が 存在確認 → パース → `minimum_version` ゲート →
`sbdb_version` ゲート → 厳格検証 → `title` 抽出 の順に進む。ゲートの順序・バージョン比較（`packaging` /
PEP 440）・型はずれ値や bool の扱い・例外の使い分けは、判断理由ごと `manifest.py` の
docstring とコメントに記載してある。ここに残すのは実装形の選択のみ:

- **ゲートは型付き `Manifest` ではなく生の Mapping を見る** — 型付きオブジェクトは
  全段通過後の成果物で、ゲート時点では存在できない（自ツールより新しい世代のファイルを
  型に読める保証がない）。厳格検証を先に置く逆順も不可（未知キーがアップグレードの
  ヒントを握りつぶす）。凍結欄だけの envelope 基底型 + 世代別 Manifest 型への分離が
  型付きゲートの正形だが、sbdb_version が増え、かつマニフェスト仕様自体が世代間で
  変わるまでは YAGNI。`Manifest` が凍結欄の値を持たないのも同じ系（現状消費者がいない）
- **欠落の検出は `read_manifest` が持ち、`SourceLayout` は素の必須パスとして重ねる** —
  マニフェストは `SourceLayout` の一欄でもあるので存在確認が二重になるが、利用者が
  実際に見るのは `read_manifest` の側（ビルドはこちらを先に呼ぶ）。この順序は必須:
  layout もまた世代で変わりうる契約面（次節）の一つであり、未対応世代のプロジェクトには
  「layout がおかしい」ではなく「sbdb_version 非対応」と言わねばならない。
  `SourceLayout` 側は `resolve_layout` を直接呼ぶ経路のバックストップ
- **対応集合は定数一行の専用モジュール（`supported_sbdb_versions.py`）に単独で置く** —
  「このファイルに diff = 対応世代集合が動いた」をファイル境界で読める構造フラグに
  するため。フォーマット破壊の PR 規律（[リリースフロー](node:/prose/30-dev/50-release)
  の管轄）の機械検査は、集合をパースせず diff の有無だけで発火できる。定数しか
  置かないので過剰発火は実質起きない

### 世代の運用

ある変更（PR の差分）が破壊的かどうかは、次の**契約面**のいずれかを
非互換に編集したかで判定する:

| 契約面 | 契約書 |
|---|---|
| schema | `resources/schemas/schema-schema.yaml` |
| view | `resources/schemas/view-schema.yaml` |
| parser/prose | Markdown 解釈規約 + `content-schema.yaml`（組み込み prose/blob）+ 埋め込み構文 |
| template | フィルタ・タグ・グローバルの登録面（コードが契約） |
| layout | プロジェクト配置規約（`definition/` / `contents/`） |
| manifest | `sbdb.yaml` 自体（凍結欄を除く） |

contents は**独立の契約面を持たない**: YAML レコードを縛る契約はユーザの
schema.yaml であり、mood の変更が contents の意味を変える事態は必ず schema 面か
parser/prose 面の変更として現れる。ゆえに版宣言は definition 側の関心で、
contents 編集者は versioning の存在を知らなくてよい。

版の記録は二層に分かれる（**外は単一カウンタ、中は面ごとの履歴**）。宣言・チェックは
単一カウンタ `sbdb_version` のみで行う——面ごとの版を全プロジェクトに宣言させるのは、
ほぼ全プロジェクトが全面を通る以上、精度利得のない死荷重になるため。一方、どの面が
どの世代で非互換に動いたかの履歴は、docs/reference のフォーマット章
（schema / view / template / manifest）に置かれる**非互換注記**——破壊的 PR が壊した
章に「この章の契約が最後に非互換に動いた版」を記す一行。機構と PR 規律は
[リリースフロー](node:/prose/30-dev/50-release)の管轄——が担う。フォーマット章の
注記の値は世代番号で、注記のない章 = 初期契約（sbdb_version 1）から動いていない。
単一カウンタ sbdb_version は、全フォーマット章の注記の max として導出できる。
エラーメッセージ・移行ガイドの粒度は、注記の指す章の差分と docs 内の移行手順から得る。

sbdb_version が語るのは、ソースとツールの**フォーマット互換のみ**。ツール自身の
利用者向け契約（CLI 等）を壊す変更はソースにもマニフェストにも関係せず、役割としての
「破壊」の扱いはリリースフローの管轄になる。それも世代 +1 とみなす規約拡張は
棄却した——sbdb_version はツール中立なスペックの所有物で、mood の CLI 変更で
上げるのはスペック/ツール分離の破壊。しかもゲートは厳密一致なので、ソースが
完全互換な全既存プロジェクトを偽陽性で拒否してしまう。

**リリースフローとの関係**（[Q6](node:/tasks/Q/tasks/Q6)）: mood のフォーマット破壊の
定義は「それまでサポートされていた世代が一つでもツールの対応集合から外れること」
（[リリースフロー](node:/prose/30-dev/50-release)）。現行の単一世代運用では脱落と
世代 +1 が常に同時に起きるため sbdb_version +1 との 1:1 対応に見えるが、定義は
脱落の側にあり、対応集合が複数世代に広がれば世代の追加は破壊ではない。この対応は
mood 側のリリース規律であり、スペックの性質ではない。スペックが所有するのは
sbdb_version のみ。

フォーマット破壊の PR は、世代番号まわりの追随一式——コードの対応集合・scaffold
生成物・showcase / dev-docs のマニフェスト——を自身に含める。更新漏れは、ビルドと
テストが世代番号に張り付いているため既存 CI が落とす。破壊的変更全般の PR 規律
（非互換注記・移行手順・breaking トレーラー）は
[リリースフロー](node:/prose/30-dev/50-release)の「PR 側の規律」を参照。

### showcase / dev-docs の実物マニフェスト

`minimum_version` は置かない。これらのプロジェクトは実装ワークフロー（機能 PR が
showcase の入出力例を義務で伴う）により構造的に常に未リリースの HEAD 機能へ依存する
ため、正直なフロア = 次版は宣言できず（dev 版 < リリース版のためゲートに落ちる）、
実在版での凍結は「その版で動くことを確認済み」という恒久の偽宣言、リリース追随は
bump コミットの再発明であり「版を持つファイルは pyproject のみ」というリリースフロー
側の前提を崩し、多ファイル版整合という release-please の解く問題の自作になる
（[リリースフロー](node:/prose/30-dev/50-release)）。真実を宣言できない
任意欄は宣言しないのが正直。フィールドの実例は External Design 冒頭のスニペットと
scaffold の生成物（実行中版を機械スタンプ）が務め、旧 mood × 新ソースの防衛は
道具3 が受ける。
