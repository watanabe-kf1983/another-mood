# システム開発ドキュメント

ユーザがシステム設計書を authoring する際に、本ツールが first-class でサポートする artifact 群。各タスクは「artifact 用のスキーマ」「サンプルデータ」「表現テンプレート」の三点セットを blueprint として提供する。

[F (メタドキュメンテーション)](../20-app/40-meta-documentation.md) との違い: F は catalog から auto-derive する meta-view (ツールが自分自身を説明する用途)、本カテゴリはユーザが authoring した data 上で動く first-party blueprint (ユーザに設計書 authoring の力を授ける用途)。両者は同じ「構造化データ → 自動描画」のメカニズムを共有するが、データの出所 (catalog vs ユーザデータ) と動機が異なる。

## External Design

### S5: 標準文書セットの調査とモデルファースト方針

単一の showcase プロジェクトから「要求仕様書」「設計書」の二文書を導出する。目的はソフトウェア開発ドキュメントの手本を示すことではなく、Another Mood のソフトウェア開発への応用例を見せること。作られるべき文書とその粒度はプロジェクト固有なので、showcase は標準の成果物構成を示すものではなく、一つのテーラリングであると自ら明言する (「あなたのプロジェクトでは別の形になる」)。何に依拠するかは、無料一次資料の調査を経て下記「モデルファースト」方針に確定した。conformance は主張せず "informed by" に留め、docs での謳い方もそう抑える (29148 の full conformance は要求文の特性 5.2.x と Clause 9 の内容要求の網羅義務を伴い、応用例という目的には過剰)。作業言語は日本語で作り切ってから英訳する (W2 の英語化と同じ流れ)。

#### 方針: 借りるのは目次ではなくモデル

調査の帰結: 「要求仕様書 + 設計書」をそのまま書ける、無料で再配布可能な既製テンプレートは存在しない。各資料が持つのは断片で — 29148 は目次はくれるが節の内容定義は有償、IEEE 1016 はそもそも文書テンプレートを規定しない、IPA は成果物の項目定義は完全だが文書の目次を持たない、arc42 / Volere は完全なテンプレートだがライセンスと守備範囲が合わない — 目次を寄せ集めても「標準のラベルを着た我流」にしかならない。

一方、標準はモデル (スキーマ) の水準では実体のある定義を持つ:

- **ISO/IEC/IEEE 42010** の本体は目次ではなく概念モデル (ステークホルダ–関心事–ビューポイント–ビュー のエンティティ・関係・多重度)。Rozanski & Woods 本の概念モデル図はこの系譜の拡張で、同書が足した Perspectives は 42010:2022 で規格側に逆輸入された
- **IEEE 1016** は viewpoint の仕様を「design concerns + design elements (entity / relationship / attribute / constraint の型)」として定義せよという規格で、最初からスキーマ集として書かれている (文書テンプレートが無いのは欠落ではなく設計)
- **OMG ReqIF** は文字通りのメタモデル。ただし要求がどんな属性を持つべきかは意図的に固定しない (そこは各組織のスキーマ、という割り切り)
- **IPA ガイド** はメタモデルを描かないが、27 工程成果物の項目定義とクロスリファレンス (画面 —識別ID→ 入出力項目 → アクション → 遷移先画面、帳票項目 → 参照先エンティティ・カラム、CRUD = 機能 × エンティティの関係) を裏返すと、暗黙の ER モデルが復元できる構造をしている

そこで、よりどころは目次ではなくモデルに置く:

- **項目の典拠は成果物の系統ごとに一つに絞る**。設計書側の相互参照型の成果物 (画面 ⇔ 入出力項目 ⇔ エンティティ、CRUD) は IPA ガイドの項目定義、要求仕様書側は 29148 (+ Volere) の要求属性。42010 の概念モデルは文書の枠組み (ビューポイント = schema の定義の束、ビュー = 章) を理解する道具として使い、データには持たない (S7 の背景参照)。1016 のビューポイント名を IPA 由来の内容に被せることもしない
- **モデルの記述場所は showcase の schema.yaml そのもの**。抽出したモデルを別文書に起こさず、スキーマ + x-ref として書き、description に参照元を補記する (「IPA 画面一覧に対応」「29148 5.2.8 の属性」程度)。ビルドすれば `__entity_defs` / ER メタビューがモデルの図を出す — 抽出成果物の置き場問題をツール自身で解決する
- **目次はモデルから導出されるビューの一つ**とみなす。章の並びは 29148 (「編成に万能解はなく合意で決めよ」) も IPA (「工程成果物 ⊂ 設計書、束ね方は各社標準に委ねる」) も自由裁量と明記しており、こちらで決めてよい。標準との対応は章の並びではなく「何が記述され、どう関係づけられるか」の水準で取り、それも conformance ではなく description の典拠注記に留める
- **抽出は網羅しない**。サンプルに必要な範囲へのテーラリング + 突合 (自作スキーマに標準対応を注記し、対応が付かない箇所だけ立ち止まる) で済ませる。IPA の暗黙モデルを忠実・網羅的に抽出するほど二次著作物として翻案禁止条項に近づくため、部分的・自分の言葉での再構成は作業量でも法的にも安全側

#### 背景: IPA ガイドのローカル性の判定

IPA ガイドは文書の章立てを提示しない。「工程成果物 ⊂ 設計書」という関係モデルだけを示し、束ね方は各社標準に委ねると明記している (6 領域 × 27 種の工程成果物カタログ + 構成要素の項目定義、という構造)。したがって「IPA から目次を借りる」選択肢はそもそも無く (モデルファースト方針の一因)、項目定義だけを借りる使い方はガイド自身の想定用途に沿う。IPA の日本ローカル性は、発注者/開発者の二者モデルや帳票の詳細慣習 (社印・全角/半角文字種・編集フォーマット) といったプロセス前提・詳細度の水準にあり、項目定義そのもの (画面・データモデル・CRUD) は可搬で、採用記法も国際標準 (IDEF1X / BPMN / ユースケース記述) と整合する。帳票・バッチの二領域を今回の範囲外とした理由はローカル性ではなく (存在自体は普遍)、二文書テーゼの実証に必須でなく題材規模に対して過剰なため。Candidates に残す。

#### 29148 の購入判定

不要。目次骨格・規範内容 9.6.1–9.6.20 の項目名・conformance 条項の枠組みは、無料の正規プレビュー (iTeh preview PDF) と二次文献で確定できた。当初は「各章の内容定義のよりどころに 9.6.x の規範本文 (有償) が要るのではないか」が論点だったが、モデルファースト方針の下では章の内容のよりどころはモデル (schema) 側に移り、規範本文を典拠にする必要自体が消えた。規範本文が要るのは conformance を名乗る場合のみで、"informed by" 方針では不要。

#### showcase の形と進め方

- 文書別に blueprint を分けず、単一の showcase プロジェクトから二文書を導出する。CRUD マトリクスやトレーサビリティ (要求 ↔ 設計) は文書をまたいで同じレコードを参照する成果物で、分割すると「単一ソースから同期した文書群」という製品テーゼの実証が立たない
- 進め方: **S7 (モデル構築) → S8 (モデルと目次の突合・目次確定) → 章別の個別撃破 (S3 / S4 / S6。S2 は独立の showcase)**。章別タスクは「S7 で粗く立てたエンティティを属性レベルまで詰め、データ・ビュー・テンプレートを作って章を埋める」増分で、独立に出荷できる。CRUD やトレーサビリティのようなエンティティ横断の関係は後付けすると手戻るため、粗くても S7 で全体を張るのが増分主義と両立する順序

### S1: テーブル定義 → 2 種類のスキーマ図 (showcase/japanese-table-design)

`showcase/japanese-table-design` がユーザ-land の参照実装。題材は小規模書店の蔵書管理 (5 テーブル / 4 FK)。スキーマ・データ・description・出力ファイルパスのすべての日本語識別子を運用している。

#### 1 つの source data から 2 つの artifact

S1 は 1 つのテーブル定義データから 2 つの図を生成する:

| Artifact | レイヤ | Mermaid 記法 | 型 |
|---|---|---|---|
| **テーブル設計図 (ER 図)** | データストア物理層 (DDL) | `erDiagram` | `VARCHAR(16)` / `INTEGER` / `DATE` |
| **ドメインモデル図 (クラス図)** | アプリケーション論理層 | `classDiagram` | `string` / `integer` / `date` |

両者は同じ `テーブル` entity を別レイヤから見たもの。橋渡しはユーザ-authored の `型対応` entity が担う (ORM の type mapping 相当)。

```yaml
# contents/型対応.yaml (一部)
型対応:
  "VARCHAR(16)":
    ドメイン型: string
    Python型: str
  INTEGER:
    ドメイン型: integer
    Python型: int
  DATE:
    ドメイン型: date
    Python型: datetime.date
```

スキーマ側では `列.型` に `x-ref: { entity: 型対応 }` を付けて build-time 整合性検査を有効化。

#### 背景: なぜ 2 図を分けるか

「ER 図」を 1 つの notation で語ろうとすると notation 選定で矛盾する:

- **classDiagram** は OO/UML の表現力 (composition / association の区別、`name : type` 形式の属性) を持つが、`(` を含む属性行をメソッドと解釈するヒューリスティックがあり SQL 型 (`VARCHAR(N)`) と衝突する
- **erDiagram** は relational schema の母国語 (PK/FK/UK マーカー、crow's-foot カーディナリティ、`型 名前` の attribute 表) を持つが、composition と association を区別しない (両者をリレーションに潰す)

両者は実は **異なる artifact の母国語** で、無理に競合させず両用するのが整理になる。F4 (built-in メタドキュメンテーション) の方は catalog 型 (`string` / `integer` / `object`) が括弧無しの論理型なので classDiagram の attribute 表記とは整合する — F4 が classDiagram 採用、S1 のテーブル設計図が erDiagram 採用、で notation の責任分割が綺麗に立つ。

#### Mermaid Unicode 制約の実機検証結果

PoC で Mermaid v11 (CDN 経由、Chromium ヘッドレス + Noto CJK) に対して実機確認した結果:

| 位置 | 形式 | 結果 |
|---|---|---|
| classDiagram class 名 | `` class `日本語名` `` (backtick 形式) | OK |
| classDiagram edge ラベル | `` `A` --> `B` : 日本語ラベル `` (unquoted) | OK |
| classDiagram attribute 名 | `日本語名 : 型` (colon 形式) | OK |
| classDiagram attribute 型に括弧 | `日本語名 : VARCHAR(16)` | **NG (メソッドと誤判定され class ボックスが上下分割)** |
| erDiagram entity 名 | `"日本語名" { ... }` (double-quoted) | OK |
| erDiagram attribute 名 | `VARCHAR(16) 日本語属性名 PK` | OK (公式 docs に明文化なし、実機で確認) |
| erDiagram 型表記 | `VARCHAR(16)` `VARCHAR(255)` | OK (括弧入り) |
| erDiagram relationship label | `"A" }o--|| "B" : "日本語ラベル"` | OK |
| erDiagram キー指定 (PK/FK/UK) | ASCII のみ | docs に明記: Unicode 非対応 |
| 日本語 entity ID を含む出力ファイルパス | `__entity_defs/テーブル.md` 等 | OK (mood build 通過) |

#### user-accessible primitive のみで 2 図が描けるか

`showcase/japanese-table-design/definition/templates/index.md` を Jinja2 の素の機能と既存組み込みフィルタのみで実装できた。新規 Jinja2 フィルタも新規 DSL 機能も不要。

- **erDiagram**: `{% for t in テーブル %}` でそのまま展開
- **classDiagram**: `列_with_ドメイン型` ビュー (`from: テーブル` / `flatten: { of: 列, as: 列 }` / `join: { to: 型対応, on: { left: 列.型, right: id }, flatten: { as: 型情報 } }`) でテーブル × 列 × 型対応を結合 → template 側で `groupby('テーブルID')` してクラスに復元
- composition edge: 本題材には親子 entity が無いため出現せず (将来 PoC を拡張するなら確認余地あり)
- association edge: `{% for c in t.列 if c.参照 %}` で `参照` フィールドを持つ列だけ拾う

`列_with_ドメイン型` ビューは flatten + join + nested key (`列.型`) の組合せを 1 本のクエリで実証している (music の `tracks_with_artist` 級の複雑さ)。これが user-land で素直に書けたことで、F4 の built-in 側で同等パターンが必要になっても primitive が足りる見込み。

ユーザ ID 空間にはドット (`.`) が含まれない想定なので、F4 の `mermaid_class_id` フィルタのような alias 化は user-land では不要だった。

#### F4 への含意

- F4 (built-in) の **classDiagram 採用は維持**。catalog 由来の型 (`string` / `integer` / `object`) は括弧無しの論理型なので、S1 で発覚した「括弧入り型 → method 誤判定」問題は起きない
- F4 の `__entity_tree` ビューの蓋然性が S1 で間接的に裏付けられた (flatten + join + nested key を持つクエリが user-land でも素直に書ける)
- ヘッダのみの全体図 (`F4a`) は実機ではかなり「ガラ空き」の見た目になる。実装は予定通り進めつつ、`F4b` 近傍図と並べて読み心地を判断する
- 不足プリミティブは見つからなかった (新規 Jinja2 フィルタ追加なし)

### S7: 二文書 showcase のモデル (showcase/system-dev-docs-ja)

単一のデータソースから要求仕様書と設計書を導出する showcase の **モデル (schema.yaml)**。S7 ではエンティティ単位の解像度 (エンティティ / 関係 (x-ref) / 主要属性) でモデルだけを出荷し、題材・サンプルデータ・二文書の目次は S8 以降に委ねる。モデルの図は `mood build showcase/system-dev-docs-ja` の `__db/__entity_defs` (ER メタビュー) で読める。

#### 位置づけと規約

- **プロジェクト名**: `showcase/system-dev-docs-ja`。本カテゴリ名 + 言語接尾辞。S1 の `japanese-` 接頭辞命名は本カテゴリの進展に伴い発展的に廃止する予定
- **題材とサンプルデータは S7 で決めない**。S7 の成果物はスキーマ (モデル) であり、「どんなサンプルを作るか」を混ぜるとタスクの難度が上がる。contents は空で出荷し、題材の選定 (S1 の書店ドメインを拡張するか等) とデータ投入は S8 以降に委ねる
- **showcase は内容ではなく機構の見本**。作られるべき文書とその粒度はプロジェクト固有で標準化もテンプレ化もできない (だからこそ構造を柔軟に定義できるツールが要る)。showcase の schema はそのまま流用されるものではなく「読んで自分の構造に書き換えるための見本」であり、価値は読みやすさと改変しやすさにある。description の典拠と英名は、その改変の手がかりとして機能する
- **解像度**: 各エンティティは ID と関係 (x-ref) に加え、一覧や参照先の表示で一行に出せる見出し属性 (名前。要求のように「一文が実体」のものは 題名) と説明相当の属性を持ち (例外: データアクセス のような関連レコードは両端の参照で識別され、見出しも説明も持たない)、章別タスクが詰める属性は「主要なもの」だけ先に置く。細部 (必須性、enum の値、シナリオの構造化、入出力項目の書式属性、説明系属性を plain text にするか Markdown prose にするか等) は S2-S4 / S6 に委ねる
- **正本は英語、日本語は下書きの作業言語** (docs/ と同じ流れ)。日本の従事者向けに日本語版を製品として残すかは S8 以降に判断する。どちらに転んでも手戻りが出ないよう、識別子・enum 値は日本語のまま進め、**英名を schema.yaml の description 末尾に `英名: xxx` の形で付記する規約**にする (enum は値の並び順どおり `英名: kind (a / b / c)`)。英語版の派生は同一ファイル内の置換で済み、`__entity_defs` の表にも英名が出る。命名は既存 showcase に合わせ、トップレベルのエンティティと配列プロパティは複数形、参照は `xxx_id`
- **英語版では章の割り当てが変わりうる**。日本の基本設計 (外部設計) の内容は、29148 の区分ではかなりの部分が SRS 側 (外部インタフェース要求 / 論理データベース要求) に入る。文化差があるのはモデルではなく束ね方なので、英語版を起こすときは schema の改名だけでなく章の割り当ても見直す余地がある
- **最小テンプレート**: `index.md` 1 枚 (プロジェクトの説明とモデルの読み方)。二文書の目次は S8
- **blueprint 登録 (`showcase/index.yaml`) は E17 (合成ビュー) を待つ**。当初は「二文書が完成してから」としていたが、7b で章が揃った時点の見た目 (web では章や節が index.md の合本から抜けて別頁になり、二文書の骨格が一頁に見えない) は見本として出すには不格好で、二文書を頁ノードとして立てられる E17 の後に登録する。それまでは `mood build showcase/system-dev-docs-ja` で直接ビルドする (`make ci` の showcase ビルドは blueprint 一覧から回るので、未登録の間は CI 対象外)

#### 背景: 42010 の概念モデルをデータに持たない

42010 の概念モデル (ステークホルダ –has→ 関心事 –framed by→ ビューポイント –governs→ ビュー) は **データには持たない**。当初はステークホルダ / 関心事 / ビューポイントをエンティティにしていたが、レビューで水準の混同と判定して削除した: ビューポイント / モデル種別 / ビューは文書の作り方を語るメタ要素で、本ツールではモデル種別 = schema.yaml のエンティティ定義、ビュー = テンプレートが生成する章に対応する (レコードではなく schema の構成そのもの)。ステークホルダはプロジェクト管理 (PMBOK のステークホルダ登録簿) の要素で SRS / SDD には登場せず、関心事は SRS では要求 (と rationale) に化けるので要求と二重になる。ユースケースのアクター (システム境界の外でシステムと相互作用する役割) はステークホルダとは別物で、上流の小さな独立エンティティとして持つ。

#### 参照の向きと層

**参照の向きは下流 (設計書のソース) → 上流 (要求仕様書のソース) のみ**。要求は要求の著者が書き、設計は下流の要員や AI が書いて要求の著者がレビューする、という著者分離を想定すると、上流のデータは下流を知らずに閉じている必要がある (将来プロジェクトを分ける場合も機械的に切れる)。この規律で CRUD (ユースケース × エンティティ) は設計側に置き、用語 ↔ エンティティ の対応もエンティティ側から張る。上流の中にも層があり (ユースケース = StRS 層が上、要求 = SRS 層が下)、要求 → ユースケース の向きはこれに従う。schema.yaml の節構成はこの二段 (上流: 要求 / ユースケース / アクター / 用語、下流: 画面 / エンティティ / データアクセス) で、1016 のビューポイント単位にはしない。

**層の内訳と二文書の境界**。上流 / 下流の二段をもう少し細かく切ると次のとおり。用語 はどの層にも属さない横断要素で、要求仕様書の用語集に置く。

| 層 | 29148 / 1016 での呼び方 | 日本の SI での呼び方 | 本 showcase | 文書 |
|---|---|---|---|---|
| 業務 | BRS (事業要求)、OpsCon の業務モデル | 業務分析、業務フロー | (含めない。S2 の独立 showcase) | — |
| 利用者の視点 | StRS (ステークホルダ要求)、OpsCon の運用シナリオ | 要件定義の業務要件、システム化業務説明 | ユースケース、アクター | 要求仕様書 |
| ソフトウェア要求 | SRS 3.2 Functions ほか (要求文) | 要件定義の機能・非機能要件一覧 | 要求 | 要求仕様書 |

29148 と日本の基本設計が重なるのは外部設計の層で、重なりが強いのはエンティティ (SRS 3.5 の中身はほぼ論理データモデル)、弱いのが画面 (3.1 が求めるのはインタフェースへの要求で、項目・アクション・遷移の定義は 29148 でも設計寄り)。本 showcase は日本の束ね方 (基本設計 = 設計書) を採る。文化差はモデルではなく束ね方にあるので、英語版で 29148 寄りに束ね直す場合は章の割り当てだけを動かす (上記「英語版では章の割り当てが変わりうる」)。

参照の向きの規律の結果、参照だけで並べると アクター / 用語 → ユースケース → 要求, エンティティ → 画面, データアクセス の順になる。要求と画面 / エンティティの間に直接の参照は無く、ユースケース経由で辿る。S6 のトレーサビリティで設計要素から要求へ直接張りたくなった場合は、規律に従い 画面 / エンティティ → 要求 の向きで足す。

見込みリストにあった 遷移 / 入出力項目 / アクション / 属性 は独立エンティティにせず、画面 / エンティティの **子型 (配列要素)** として持つ。理由: これらは親無しに存在しない部分であり、本ツールの composition (親子分解) にそのまま載る。ER メタビューでは `画面.item.アクション.item` 等の子クラスとして描かれる。

逆に **データアクセス (CRUD 図のセル) は子型にしない**。当初は エンティティ.操作[] (ユースケース + C/R/U/D) としてエンティティの部分に置いていたが、レビューで関連レコードと判定した: CRUD 図のセルは ユースケース × エンティティ の交差で、どちらの部分でもない。エンティティ配下に置くと記述順が「エンティティごとに触るユースケースを列挙」になり、実務の「ユースケースごとに触るエンティティを列挙」と逆になる。上流側 (ユースケース) には規律上置けないので、下流の独立エンティティとし、自然な単一キーが無いため配列パターンで持つ (music の `playlist_tracks` と同型)。一つのユースケースが複数のエンティティに触る場合はセルが複数になるだけで、それらを一つのトランザクションとして束ねる概念は内部設計の領分 (対象外)。名前は「CRUD」を避けて データアクセス (data_access) とした。この関係 1 件を名付けている典拠は ArchiMate の access relationship (accessType: read / write / readwrite) だけで、他 (Information Engineering の Process/Entity matrix、TOGAF の Data Entity/Business Function matrix、IPA の CRUD 図) はいずれも表を二軸の名前で呼び、セルには名前を与えていない。CRUD は成果物・分類の名前であって記録される「もの」の名前ではなく、普及しすぎた略語が実装寄りの連想を招くのも避けた。

データモデル側のエンティティは IPA の用語どおり `エンティティ` と呼ぶ。ツール自身の「entity」と語が重なるが、ユーザ ID 空間と組込み (`prose` / `blob`) は衝突せず、利用者が混乱する場面もない (開発側の会話で紛れる場合は「データモデルのエンティティ」と言い分ける)。

#### 背景: 業務モデル (DFD) を含めない

**業務モデル (DFD) は本 showcase に含めない (レビューで決定)**。当初はプロセス / データストア / 外部エンティティ / フローの 4 エンティティを上流の付録として持ち、付録側から本体 (ユースケース / アクター) を参照していた。しかし 29148 の層で業務モデルは BRS の領分でユースケース (StRS) より上流にあり、参照の向きの規律に従えば ユースケース → プロセス、アクター → 外部エンティティ と反転して本体が業務モデルに依存する形になる。付録として取り外し可能にするか、正式な最上流層にするかのどちらかしか整合せず、二文書同期の実証に業務モデルは不要なので外した。DFD は製品動機に近い題材だが、製品動機と showcase の題材は分けて考え、S2 を独立の showcase として扱う

#### スキーマ言語との突合 (実機確認済み)

- **多対多 (画面 → ユースケース[] 等)**: `x-ref` は `type: string` のプロパティにしか付かず、`items: { type: string, x-ref }` は meta-schema に拒否される。`items: { type: object, properties: { ID: { type: string, x-ref } } }` と 1 段包む (S1 の `列[].参照.テーブル` と同型)。書き味は落ちるが、関係に属性を足す余地 (ReqIF の「関係自身が型と属性を持つ」) にもなる。関係が独立して立つほど重い場合 (データアクセス) はトップレベルの配列パターンにする。string 配列への x-ref はツール側の Candidate として別途起票を検討
- **多態参照 / 自己参照**: DFD のフロー (元 / 先) とプロセス (親) で実機確認したが、業務モデルを外したので結果は S2 節に移した
- contents の無いエンティティがあってもビルドは通り、ER メタビューにノードとして現れる (S7 が contents 無しで出荷できる根拠)。ダングリング参照は警告 (`--strict` で失敗)

### S8: 二文書の目次仕様 (showcase/system-dev-docs-ja)

S7 のモデルと S5 の章立てのたたき台を突き合わせ、章 → ソース (この章はどのレコード群のビューか) と エンティティ → 登場章 の対応を張って確定した **二文書の目次仕様**。どの章にも現れないエンティティ、どのエンティティにも支えられない章は無い。S8 はこの目次を器 (章見出し・導入文・prose 章・用語集) として敷設し、章の本文は「担当」列のタスクが埋める。

#### 題材

**小規模書店の在庫管理システム** (書籍マスタ / 入荷 / 販売 / 棚卸)。S1 (japanese-table-design) の書店ドメインの拡張で、S7 の schema の description に置いた例 (入荷登録、書籍、店員、決済サービス) が既にこの題材を指している。S8 で投入するデータは 用語 (書籍 / ISBN / 在庫 / 入荷 / 販売 / 棚卸 / 仕入先 程度) と各文書の prose (はじめに / 付録) のみ。ユースケース / アクター等のレコードは章別タスクが投入する。

#### ユースケースとアクターの粒度

要求仕様書 1 章の生成部を最初の章 PR として入れたときに決めた事項。

- **粒度規則**: 1 ユースケース = 1 アクターが一続きで達成する業務目標 (IPA のシステム化業務 1 件)。書籍 / 仕入先のマスタ登録は独立のユースケースとして持つ (入荷が参照する先で、CRUD で C を担う行が要る)。修正・削除は範囲外扱いで持たない (showcase は機構の見本で、業務の網羅は要らない)
- **本数**: ユースケース 6 (書籍登録 / 仕入先登録 / 入荷登録 / 販売反映 / 棚卸 / 在庫照会)、アクター 3 (店員 / 店主 / 決済サービス)。店主は「利用者」の節が一行にならないよう置いた役割で、在庫照会に関わる (当初は棚卸にも置いたが、3a で外した。下記「ユースケース記述」)
- **ID**: ユースケースは `UC01` 形式のコード。設計書の「記法と規約」が機能を ID で識別すると宣言しているのと、英語版でも識別子が変わらないため。アクターは 用語 と同じく自然語キー (ID を文書に出す場面が無い)
- **並び順**: contents のマップの記述順 = 業務の時系列。主要機能 / CRUD の行順はすべてこの順で、view や template で並べ替えない
- **要求仕様書 1 章の構成**: prose (目的 / 範囲 / 製品の位置づけ) → 生成 (主要機能、利用者と外部システム) → prose (制約)。29148 の順序 (機能・利用者の後に制約) を保つために 制約 を別 prose ファイルに分け、prose と生成部を交互に挟む例を兼ねる
- **利用者の逆引きは view**: サブテンプレートからトップレベルの名前空間が見えないので、アクター → 関わるユースケース の逆引きはテンプレートでは書けず、view (`ユースケース_アクター` で `ユースケース.アクター[]` を flatten し、`アクター_with_ユースケース` がアクターから join) で作る。多対多のオブジェクト配列に対する join の定石
- **anchor**: ユースケースの anchor は要求仕様書 3 章のユースケース記述の節 (render 主題なので自動) にあり、主要機能の表の行や設計書の各章 (関連図 / CRUD / 画面一覧) からそこへリンクする (3a までは主要機能の行に仮置きしていた。3b で主題が entity から view `ユースケース記述` の行に変わり、リンクは `node("ユースケース記述", id)` になった。下記「要求」)。アクターの anchor は利用者の表の行で、view の行から `node("アクター", id) | anchor` で entity ノードの anchor を出す (view 行の anchor では他章からの `node("アクター", …)` が着地しない)

#### ユースケース記述 (要求仕様書 3 章前半)

章別 PR 3a で決めた事項。ユースケース記述は 概要、項目表 (アクター / 事前条件 / 事後条件)、基本シナリオ、例外 からなり、要求仕様書 3 章「機能要求」節にユースケースごとの節として出る (3b がこの下に要求を足す)。

- **ユースケースは主アクター一人の目標**。シナリオは主アクターとシステムの対話で、人から人へ仕事が渡る場面はユースケースの境界 (業務フロー / スイムレーンは複数の役割にまたがるが、それは business use case で、system use case とは別の成果物)。この定義に照らし、棚卸から店主を外した (店員が数えて店主が確定するのは業務フローの記述で、システムのユースケースとしては二つ)。`ユースケース.アクター[]` は主アクターの一覧 (同じ目標を複数の役割が持つ 在庫照会 では 2 件) で、副アクター (システムがサービスを借りる相手。決済代行など) は本 showcase に無く、要る場合は別属性として足す。配列の順序に意味を持たせない
- **シナリオは二列形式 (Wirfs-Brock の conversation)**。基本シナリオ は `{操作, 応答, 例外[]}` の配列で、操作 は主アクターの操作 (主語を書かない)、応答 はシステムの応答。番号はテンプレートが振る。列見出しのアクター名 (「店員の操作」) は ユースケース.アクター[] から導くので、ステップにアクターを持たない (一箇所に持ち、出力に必要な所へ導く)。副アクターとのやり取りは 応答 の文中に畳む (二列形式の定石。副アクターを主語にしたラリーは書かない)。退けた案: 主語付きの文の string 配列 (Cockburn の一列形式。副アクターを自然に書けるが構造が文の中にしか無い)、ステップに アクター の x-ref を持つ形 (主アクターが交代するユースケースは無い)
- **例外はステップの子** (`基本シナリオ[].例外[]` = `{条件, 応答}`)。「基本シナリオの何番目で起きるか」を番号で書かず、出力時にテンプレートが親ステップの番号を振る (nested loop で `{% set step_no = loop.index %}`)。ステップを差し替えても例外は一緒に動き、入れ子要素への x-ref が無くても参照がずれない
- **説明系の属性は plain text**。テンプレートエンジンは `{{ }}` の出力の ASCII 記号をすべてエスケープするので、YAML 文字列内の Markdown は `| safe` を付けない限り効かず、付ければ表セルの `|` 等の保護が外れる。概要 / 事前条件 / 事後条件 / 操作 / 応答 / 条件 に加え、要求 (記述 / 理由 / 適合基準) と 画面 (説明 / アクション.説明) もすべて plain text とし、段落・箇条書き・強調を要する説明は prose レコードに置く。schema.yaml の冒頭コメントに規約として書いた
- **必須性**: 基本シナリオ を required に足した (シナリオの無いユースケース記述は無い)。事前条件 / 事後条件 は string (1〜2 文) のまま任意で、無い項目は項目表から行が消える (仕入先登録 / 在庫照会 に 事前条件 が無い)
- **1 件ずつ render**: 殻 `要求仕様書.md` (root の文脈。名前空間が見える) で `{% for uc in ユースケース %}` し、`ユースケース記述.md` を 1 件ずつ render する。コレクションを主題に 1 テンプレートで loop する形 (主要機能 と同じ) でも書けるが、web edition では `ユースケース.item` (3b からは `ユースケース記述.item`) を `file_per` に挙げて 1 件 1 頁に割り、殻の 機能要求 節にユースケースへのリンクの一覧を置く (book では節の直前の目次になる。dev-docs の index.md と同じ作法)。例外表の有無は `{% set 例外のあるステップ = 基本シナリオ | selectattr("例外") | list %}` で判定する (未定義属性は falsy)

#### 要求 (要求仕様書 3 章後半)

章別 PR 3b で決めた事項。要求仕様書 3 章は 機能要求 / 非機能要求 の二節で、機能要求はユースケース記述 (概要 / 項目表 / 基本シナリオ / 例外) の末尾にそのユースケースの要求の表が続き、非機能要求は種別 (外部インタフェース / 品質 / 設計制約) ごとの節に同じ表を置く。両節とも「導入文 → 節へのリンク一覧 → 節 (web では 1 頁ずつ)」の同じ構造で、29148 が別々の節に置く外部インタフェース / 設計制約を 非機能要求 の下に束ねたのはこの平仄のため。

- **ユースケース記述は view `ユースケース記述` (ユースケース に 要求 を join) を主題に描く**。要求の表をユースケース記述の末尾に置くには、要求がデータツリー上でもユースケースの配下にいる必要がある: リンクの向き先の頁は anchor が書かれた場所ではなくノードのデータ上の位置 (split 対象の最寄りの先祖) で決まるので、トップレベルの 要求 を `node(path="/要求")` で引いて web の (split された) ユースケース頁に描くと、anchor はその頁に出るのに 4 章や設計判断からの `node("要求", id) | link` は index.md を指して着地しない (実機で確認。`--strict` も検出しない)。view で `要求.ユースケース` を join すると、要求のコピーはユースケース行の子になり、anchor path も `/ユースケース記述/UC03/要求/R04` と要求 ID で指せる。**x-ref で結ばれたレコードを参照先の頁に描く定石は join view** で、殻側に表を置く案 (web でユースケース記述と表が別頁に分かれる) はこれで退けた
- **ユースケースの home は view 行 `/ユースケース記述/{id}`**。entity `ユースケース` のノードはどこにも render せず、主要機能の行・利用者の表・設計書の各章 (関連図 / CRUD / 画面一覧) からのリンクは `node("ユースケース記述", id)` で張る。web の `file_per` も `ユースケース記述.item` (頁は `ユースケース記述/UC03.md`)。3a の「ユースケースの anchor は entity」はこれで置き換わる
- **非機能要求の節も view `要求種別` の行を主題に描く**。機能 以外の 要求 を `grouped: {by: 種別, as: 要求}` で種別ごとに束ね、種別の値を `select … as: id` で行の id にする (行 = 節、頁は `要求種別/品質.md`)。節見出し (「品質要求」等) と導入文は種別の値から章テンプレート `要求種別.md` の中で引く (テンプレートが持つ文書の文言で、殻の章見出し・導入文と同じ扱い)。殻のリンク一覧は種別の値 (「品質」) をラベルにする
- **要求の home はすべて view 行の配下のコピー**で、entity `要求` のノードはどこにも render しない。機能要求は `/ユースケース記述/{uc}/要求/{id}`、非機能要求は `/要求種別/{種別}/要求/{id}`。4 章 (検証) と設計判断から要求を指すときは、`要求.ユースケース` の有無で `node("ユースケース記述", 要求.ユースケース, "要求", 要求.id)` と `node("要求種別", 要求.種別, "要求", 要求.id)` を使い分ける。4 章は 3 章にパラレルなので、二つの view を回して各行の 要求 を描けば使い分けは要らない
- **表の列は ID / 要求 (題名を太字、`<br>` の後に記述) / 理由 / 優先度**。検証方法 と 適合基準 は 4 章 (検証) の列に回し、同じレコードを二章で違う列で描く。表は 1 テンプレート (`要求一覧.md`) で、主題は view 行に join / grouped で載った 要求 配列
- **ID は `R01` 形式の連番**。種別の接頭辞 (FR / NFR 等) は 種別 属性の重複になり、種別を直すと ID が変わるので採らない。contents の記述順 = 掲載順 (ユースケース順、次いで種別順)。`link` の自動ラベルは title / name / id しか見ないので、要求は ID で参照し、題名を添えるときは参照側が明示する
- **必須属性**: 題名 (一覧・4 章・設計判断からの参照に要る)、種別、記述、適合基準、優先度、検証方法。29148 は要求文の特性として verifiable を求めるので、適合基準 と 検証方法 を欠く要求を許すと 4 章の「3 章にパラレル」が崩れる。計画表では PR 4 の決め事だったが、レコードを書くのは 3b なのでここで決めた。理由 は任意で、要求文だけでは必要性が読み取れないものに付す
- **機能要求は必ず 1 つのユースケースに属する** (ユースケース 属性は機能要求では実質必須、他の種別では省略)。schema では条件付き必須を表現しないので description に書く
- **レコード**: 20 件 (機能 13、外部インタフェース 2、品質 3、設計制約 2)。contents の記述順が節の順 (grouped は初出順) なので、非機能要求は種別ごとに固めて書く。要求文は「システムは、…しなければならない / してはならない」の一文。種別 は 29148 SRS 3 章の区分を畳んだ 4 区分 (機能 / 外部インタフェース / 品質 / 設計制約) を維持した

#### 検証 (要求仕様書 4 章)

章別 PR 4 で決めた事項。4 章は 3 章にパラレルな二節 (機能要求の検証 / 非機能要求の検証) で、節の下にユースケースごと・種別ごとの小節を置き、各小節は 3 章の同じ要求を ID / 要求 (題名) / 検証方法 / 適合基準 の列で描き直す表だけを持つ (ユースケース記述の本文は繰り返さない)。新規レコードは無い。

- **3 章の二つの view (`ユースケース記述` / `要求種別`) を章テンプレートの `for` で回し、行を `render` し直さない**。view 行を 4 章でもう一度 `render` すると、web edition では同じ出力パス (`ユースケース記述/UC01.md`) に二頁が衝突してビルドが失敗する。行の配下の 要求 配列を `render` すると、その配列の anchor (`/ユースケース記述/UC01/要求`) が 3 章と 4 章に二重に出る。そのため小節の見出しはループ側で書き、表は `{% include "検証一覧.md" %}` で描く (呼び出し側が変数 `要求` を `set` する。`要求一覧.md` が `this` を主題にする render 部品なのと対になる、include 部品)。章本体は `検証.md` に置き、殻の章導入文の下から `{% include %}` する
- **4 章は要求のコピーを持たない**。ID 列は 3 章の行の配下のコピー (要求の home) に `r | link(r.id)` で張る: ループ変数 `r` は view 行に載ったコピーそのものなので、anchor path が 3 章の `<a id>` に一致し、`node(...)` の使い分けは要らない。web では要求のあるユースケース頁 / 種別頁に、book では index.md 内の行に着地する。4 章の側に anchor は置かない (要求の home を一つに保つ)
- **4 章はどの edition でも分割しない**。表の主題が無いので split の単位が無く、3 章とパラレルな参照表としても一頁で見渡せるほうがよい。小節見出しはユースケース / 種別の行へのリンク (`uc | link(uc.名前)` + ID、`k | link`) にして 3 章の節へ飛べるようにする。種別の小節見出しは殻のリンク一覧と同じく種別の値 (「品質」) で、`要求種別.md` の節見出し (「品質要求」) の文言は繰り返さない。退けた案: **3 章の view の別名 view** (`from: ユースケース記述` 等) を立てて行を `render` する。パス衝突は消えて 4 章の節を 3 章と同じ粒度で頁に割れるが、得られるのは節の頁であって章の頁ではなく (章 = 単一行のノードは今の DSL では偽の属性を足さないと作れない)、要求のコピーがもう一組増え、E17 で捨てる暫定物になる。本当に欲しいのは章ごとの頁なので、E17 まではインラインで待つ
- 3 章と 4 章の間で、同じ 要求 レコードが違う列で二度描かれることが、この showcase の「一つのソースから複数の表を導く」最初の同一文書内の例になる

#### 設計方針 (設計書 1.3)

章別 PR 5 で決めた事項。設計書 1 章の設計方針節は、設計判断ごとの小節 (見出し = ID + 題名、本文 = 判断、一段下の小見出し 理由 / 根拠要求。根拠要求は箇条書き) を並べる。退けた案: (a) 要求一覧と同じ 4 列の表 (ID / 設計判断 / 理由 / 根拠要求)。判断と理由の長文が二列を占め、根拠要求の列が狭くなって「ID + 題名」が数文字ごとに折り返した。(b) ユースケース記述と同じ項目表 (項目 / 内容)。列の揃えに意味が無く、ラベルだけの表になる。長文の属性を二つ以上持つレコードは、表ではなく小節と段落で描く。設計書が要求仕様書のレコードを参照する、文書横断参照の二例目 (一例目は文書冒頭の用語集へのリンク)。

- **ID は `D01` 形式の連番**。要求 (`R01`) / ユースケース (`UC01`) と揃え、contents の記述順 = 掲載順 (データの持ち方 → 業務の扱い → 慣行)。小節の見出しの前に anchor を置き、将来の逆引き (要求 → 設計判断) から着地できるようにする
- **根拠要求はテンプレートで引く**。設計判断 は要求の ID しか持たないので、`node("要求", ID)` でレコードを引いて題名を添え (`node()` が返すノードは Mapping なので属性を読める)、`要求.ユースケース` の有無で `node("ユースケース記述", uc, "要求", id)` と `node("要求種別", 種別, "要求", id)` を使い分けて要求の home (3 章のコピー) にリンクする。表記は「R04 入荷時の在庫加算」(ID + 題名)。退けた案: 設計判断 から 要求 を join する view (アクター_with_ユースケース と同じ flatten → join の定石)。データを join しても home の切り替えはテンプレートに残るので、リンクの関心事はテンプレートで閉じ、view を増やさない。x-ref で結ばれたレコードを**参照先の頁に描く**なら join view (「要求」の定石)、**参照元からリンクするだけ**なら `node()`、という使い分け
- **Jinja のマクロはこの用途に使えない**。autoescape が切ってあるのでマクロの戻り値は素の文字列で、呼び出し側の `{{ }}` がもう一度エスケープする (`\[R04\]\(…\)` と出る)。リンクを組み立てる部品は `{% set %}` を行内に書く
- **web では節をまるごと 1 頁に割る** (`設計判断.item[]`。用語集と同じ形で、頁は `設計判断.md`)。節の見出しと導入文は章テンプレートが持ち、殻の章導入文から `{{ 設計判断 | link("設計方針") }}` で導線を張る (book では頁内リンク)。判断ごとの頁 (`設計判断.item`) にはしない: 1 件が数段落で、6 件を一頁で見渡せるほうがよい
- **レコード**: 6 件。D06 (日時は店舗のローカル時刻で持つ) は根拠要求を持たない判断 (技術上の慣行) の例で、根拠要求の箇条書きが出ない。判断の文言は要求の適合基準と矛盾しないように書く (棚卸中の販売通知は R11 に合わせて「拒否」とし、「受領して保留」にはしない)

#### コンテキスト (設計書 2 章)

章別 PR 2 で決めた事項。コンテキストの章は図 1 枚とその読み方の地の文で、新規レコードは無い。図は **UML ユースケース図の形** — システム境界を Mermaid `flowchart` の subgraph にし、その中にユースケースのノードを業務の流れの順で並べ、外側に置いたアクターから線を引く。形はアクターの種別で分け、利用者は角の丸い箱 (`("店員")`)、外部システムは二重の縦線 (`[["決済サービス"]]`)、ユースケースは端の丸い箱 (`(["書籍登録"])`)。

- **人のアクターも描く**。目次仕様のたたき台は IPA 外部システム関連図に倣って「アクター (種別 外部システム) × ユースケース」をソースにしていたが、この題材で外部システムは決済サービス 1 つなので、図はノード 2 個・辺 1 本になり章として持たない。章の目的である「境界」は、外を跨ぐものだけでなく**誰が外にいて何が中にあるか**で示すほうが図として成立する。目次仕様のソース欄と「エンティティ → 登場章」表の アクター / ユースケース の行はこれに合わせて書き換えた (ユースケースは辺ではなく境界の中のノードになった)
- **要求仕様書 1 章の再掲にはならない**。1 章の利用者 / 外部システムの表は同じアクター × ユースケースの関係を持つが、そこに無く 2 章だけが持つのが**境界** — 何が本システムの担当で何が外かの線引きで、これは設計側の判断である。機能構成の章を落としたときの理由 (列まで同じ表の再掲) とは異なり、同じ関係を表と図という別の形で描くことは、この showcase が示したい「構造化データ → 自動描画」そのものになる。退けた案: (a) **外部システムのみ・システムは黒箱** (目次仕様どおり。上記のとおり図が持たない)。(b) **全アクター・システムは黒箱で辺のラベルがユースケース名**。境界は黒箱のままなので 1 章の表との差が辺の向きだけになり、7 本の辺が束になって「在庫照会」が 2 度出る
- **図の中から要求仕様書へはリンクしない**。Mermaid の `click` は書けるが、リンク先の URL がコードフェンスの中にあるため出力 Markdown から HTML への書き換えが効かず、HTML 版で外れる (実機確認。下記「ツール側・将来の検討事項」)。導線は図の下の地の文に置き、ユースケースの内容は 1 章の主要機能へ、境界を跨ぐ連携そのものへの要求は 3 章の外部インタフェース要求の節へ渡す。後者が設計書から要求仕様書への三例目の参照になる
- **章専用の view を主題に立てて、章を 1 ページに割る**。章の見出しと導入文は章テンプレートが持ち、殻は見出しを書かずに `render` する (用語集・設計方針と同じ作法)。web edition では `コンテキスト.item[]` でこの章が 1 ページになり、book edition ではインラインに戻る。**章の内容が単一のコレクションに収まる章は、E17 (合成ビュー) を待たずに頁に割れる**: 4 章 (検証) が割れなかったのは、内容が二つの view にまたがり、行を再 `render` すると出力パスが衝突するためで、章が頁になれないという一般則ではなかった
- **主題には章専用の view (`コンテキスト`) を立てる**。ユースケース entity をそのまま主題にはできない: 要求仕様書 1 章の主要機能が既に `render` していて主題の anchor が重複し、`file_per` の型 ID も共有するので分割が要求仕様書側に及ぶ。view の中身は ユースケース の射影 (id / 名前 / アクター) で join も要らない。E17 が入ったら章の合成ビューに置き換わる
- **主題の外のコレクションは `node()` で引く**。サブテンプレートからトップレベルの名前空間が見えないのは変わらないが (実機で再確認: `{% for uc in ユースケース %}` は空を返す)、`node("アクター")` は**コレクションごと返り、そのまま反復できる**。設計方針節が `node("要求", ID)` で 1 件引いていたのと同じ入口で、図の外側のノード (アクター) はこれで描く
- **web edition では殻に章の見出しが残らない**ので、文書冒頭の一文から `{{ コンテキスト | link("コンテキスト") }}` で導線を張る (用語集と同じ作法。book では頁内リンクになる)。張らないと、分割された章ページが文書からたどれなくなる
- **ユースケースの並び順は contents の記述順 (業務の流れ) のまま**にし、線の交差は許容する。並びは要求仕様書の主要機能・機能要求の節と共通の背骨なので、図の見た目のために 2 章だけ別の順にはしない
- **Mermaid `flowchart` は日本語のノード ID をそのまま受ける** (実機確認)。S1 で確認した classDiagram / erDiagram に flowchart が加わった。エスケープも引用符も要らず、`店員 --- UC01` が通る

#### 論理データモデル (設計書 3 章前半)

章別 PR 6a で決めた事項。設計書 3 章「データ設計」の前半を、エンティティ のコレクションを主題にした一節「論理データモデル」(ER 図 / エンティティ一覧 / エンティティ定義) として置く。テンプレートはコレクション用 (`論理データモデル.md`: ER 図と一覧) と 1 件用 (`エンティティ定義.md`: 属性の表) に割り、前者が後者を `render` する。投入したレコードは 8 件 — リソース系が 書籍 / 仕入先、イベント系が 入荷 / 入荷明細 / 販売 / 販売明細 / 棚卸 / 棚卸明細。

- **レコードの形は設計方針節の判断から導いた**。在庫数を書籍の属性に持つ (D01)、入荷・販売・棚卸を追記のみのイベントに分ける (D02)、書籍の主キーと他からの参照を ISBN にする (D03)、未登録 ISBN の通知を保留として保存する (D04)、棚卸中を 棚卸.状態 に持つ (D05)、日時はローカル時刻 (D06)。D04 は 販売明細 が 通知ISBN (必須の素の文字列) と 書籍 への参照 (任意) を分けて持つ形になり、判断がそのまま属性の並びに現れた。一つ前の章別 PR で入れた設計判断が次の章のデータの形を決めるという、二文書の中での上流 → 下流がここで効いている
- **ヘッダと明細に割る粒度は、既にあるレコードが決めていた**。用語集の「入荷」の定義 (1 回の入荷は 1 つの仕入先からの複数の書籍と数量からなる) と UC04 / UC05 のシナリオ (各書籍の在庫数を減算、全書籍の在庫数を基準として記録) が、入荷・販売・棚卸のいずれも 1 件が複数の書籍にまたがると既に書いている。1 レコード = 1 書籍 に畳む案はこれらと矛盾するので採れない
- **ER 図に出す属性は主キーと外部キーだけ**。全属性は同じ頁のエンティティ定義が表で持つので、図も全属性を持つと 1 頁に同じ情報が二度出る (機能構成の章を落としたときと同じ判断軸)。図が担うのは関係、属性の詳細は表。全列入りの ER 図は S1 (japanese-table-design) が既に見せている
- **カーディナリティはデータにある情報だけから導く**。参照を持つ側は 0 件以上 (`}o`)、参照先は 必須 なら ちょうど 1 件 (`||`)、任意なら 0 か 1 件 (`|o`)。「参照先 1 件につき参照元が最低 1 件あるか」はスキーマにもデータにも無いので、仮定を置かず `}o` に倒す。読み方は図の下の地の文で説明する
- **`属性.参照.属性` の突合はテンプレートで行う**。x-ref はエンティティの ID しか指せず、参照先の属性名は素の文字列なので、綴り違いはビルドで捕まらない (`--strict` でも通る)。参照先を `node()` で引いてその `属性[]` に同じ名前があるかを確かめ、無ければ参照の列に「(参照先に無い属性名)」と出す。ビルドを止められない代わりに文書の表面に出して人の目に留める形で、入れ子要素への x-ref がツール側に入るまでの代替 (実機で名前を壊して印が出ることを確認済み)
- **属性に 説明 を足した**。S7 の 属性[] は 名前 / 型 / 必須 / 主キー / 参照 だけで、エンティティ定義の表を 1 行ずつ読めなかった (IPA のエンティティ定義も項目ごとの説明を持つ)。スキーマ上は任意だが、本 showcase では全属性に書く。論理型は string / integer / datetime の 3 語に収まった
- **エンティティの ID は名前と同じ自然語キー**。文書に出す識別子が名前で足り、他章からは名前でリンクするので、ユースケース / 要求のような連番コードは置かない (アクター・用語と同じ)。一覧にも ID の列を置かない
- **エンティティ定義の表の見出しは「主キー」ではなく `PK`**。○ を置くだけの狭い列で「主キー」は 2 行に折れて読みにくく、ER 図が PK / FK を使っているので表記も揃う (実機で確認)
- **Mermaid `erDiagram` は日本語のエンティティ名・属性名に加え、`PK, FK` の複数キー指定も受ける** (実機確認。S1 で確認済みの範囲に複数キーが加わった)。コードフェンスの中でも `{{ }}` の出力には Markdown エスケープが効くので、`PK, FK` や `||` のようなリテラルにも `| safe` が要る (付けないと `\,` `\|` になる)
- **web edition は節の頁 + エンティティごとの頁**。`file_per` に `エンティティ.item[]` と `エンティティ.item` を併記し、節の頁 (ER 図と一覧) から各エンティティの頁へリンクする。docs の reports.md が list-and-detail の形として書いている併用の、この showcase での初出。3 章は後半に CRUD マトリクス (別主題) を持つので章全体では 1 頁にできず、要求仕様書 3 章 (機能要求 / 非機能要求) と同じく節ごとに割れる。コンテキスト章が要した章専用 view は要らない: エンティティ はまだどこからも render されていないので、entity をそのまま主題に立てられる。当初は節を 1 頁にまとめていた (定義 1 件が表 1 つで薄く、図と表の往復が頁内で済む) が、他章 (CRUD の列、画面の入出力項目の参照先) からのリンク先が 1 エンティティ 1 頁になる方をレビューで選んだ。一覧の行がそのまま各頁への導線になり、エンティティ定義の導入文にも一覧と同じ順で全件のリンクを並べる (web で導入文の下が空にならないように)
- **本の版では見出しが 6 段に達した**。設計書 (`##`) → データ設計 (`###`) → 論理データモデル (`####`) → エンティティ定義 (`#####`) → 各エンティティ (`######`)。Markdown の下限なので、節の中でこれ以上の入れ子を持つ章 (4 章の画面定義: 画面ごとに入出力項目とアクションの表) では、節の中の見出しを減らすか、E17 で章・節を頁ノードにして段を詰める必要がある。web では各エンティティが自分の頁の `#` になるのでこの制約は本の版だけの話

#### CRUD マトリクス (設計書 3 章後半)

章別 PR 6b で決めた事項。設計書 3 章「データ設計」の後半を、章専用の CRUDマトリクス ビュー (ユースケース に データアクセス を join したもの) を主題にした一節「CRUD マトリクス」として置く。投入したレコードは データアクセス 23 件 (6 ユースケース × 触るエンティティ)。これで S3 の束 (3a / 3b / 6a / 6b) が揃った。

- **セルの粒度は C/R/U/D**。Proposals では read / write の 2 値に傾いていた (C / U / D の別は物理設計に依存し、基本設計で書かせると推測になる) が、この showcase では設計方針節が既に決めている: 在庫数は書籍の属性を更新する (D01)、入荷・販売・棚卸は追記のみで更新も削除もしない (D02)。セルはその判断の写しであって推測ではなく、結果として D がどのセルにも現れないことが D02 の証拠として表に出る。IPA 流の検査 (誰も作らない・誰も更新しないエンティティ) も C と U の別があって初めて成り立つ。schema の `操作` は `^[CRUD]+$` のまま、description に「文字は C R U D の順」「C / U / D の別は論理設計の判断に従い物理設計を先取りしない」を書いた。2 値に倒す場合は `pattern` の差し替えだけで済む
- **行列化はテンプレートが担う**。view DSL に pivot は無いので、view は行 (ユースケース) に データアクセス を配列で付けるまでで、列は `node("エンティティ")` (記述順 = リソース → イベントの作成順)、セルは行の配列を列の ID で突合して出す。行の順は ユースケース の記述順 (業務の時系列)。同じ (ユースケース, エンティティ) の組は 1 件の約束 (schema の description) なので、突合の for が出すのは高々 1 件
- **列の集計を文にして表の下に置く**。IPA の CRUD 図の使い方 (どこからも作られない・更新されないエンティティの検出) を、表を目で追わなくても済むように導出した文で出す: 作成されないエンティティ / 更新されないエンティティ / 削除されるエンティティを列ごとに数え、無ければ「無い」と書く。集計は minijinja の `namespace()` で持ち、名前を「、」で繋いだ文字列に畳む (テンプレート内でリストに要素を足す手段が無い)。文字列への `in` (`"C" in a.操作`) は minijinja で効く
- **行見出しはユースケース記述の頁へ、列見出しはエンティティの頁へリンクする**。6a でエンティティを 1 件 1 頁にした理由 (CRUD の列からのリンク先) がここで使われた。行見出しは 主要機能 と同じく ID にリンクを置き名前を添える
- **web edition は節を 1 頁** (`CRUDマトリクス.item[]`)。ユースケース entity をそのまま主題にできない事情はコンテキスト章と同じ (主要機能が render 済み)
- **表の行末の `{% endfor %}` は `+%}` にする**。行の内側で列を for で回す形では、行を閉じる `{% endfor %}` が trim_blocks で改行を食い、全行が 1 行に繋がる (実機で確認)。docs の Whitespace 節にある opt-out がそのまま効いた
- **マトリクスが上流の穴を見せた**。R07 と D04 は「保留の販売を店員の確認で登録済みの書籍に結び付ける」と書いているが、その確認を行うユースケースが無く、列で見ると 販売 と 販売明細 は誰も更新しない (販売.状態 が 保留 のまま、販売明細.ISBN が空のまま)。6b では穴を残し (下記 Candidates「保留販売の確認」)、上流への追加は別 PR にする。この観察を述べる文はテンプレートではなく prose レコードに置く (下記「テンプレートに書く文と contents に書く文の境界」)。CRUD マトリクスがこの種の抜けを機械的に出すこと自体が、この節を導出で持つ価値の実証になっている

#### 画面一覧と画面遷移図 (設計書 4 章前半)

章別 PR 7a で決めた事項。設計書 4 章「画面設計」を、画面 のコレクションを主題にした章として置く。章の主題が一つなので、コンテキスト章と同じく節テンプレート (`画面設計.md`) が章そのものになり、殻 (設計書.md) には章見出しを書かない。投入したレコードは 画面 7 件 (メニュー / 書籍登録 / 仕入先登録 / 入荷登録 / 棚卸 / 在庫一覧 / 書籍履歴)。画面とユースケースは多対多で、書籍履歴画面が在庫照会と書籍登録の両方に付く。7a で持つのは 名前 / 分類 / 説明 / ユースケース / アクション (名前と遷移) までで、入出力項目とアクションの説明は 7b。

- **画面はユースケースから導く**。人のアクターが遂行するユースケースに画面を割り当て、アクターが外部システムだけのユースケース (販売反映) は画面を持たない。基本シナリオが一画面に収まらないユースケース (在庫照会: 検索一覧 → 履歴) は画面を分け、収まるものは一画面にする (棚卸の 開始 / 実数入力 / 確定 は一画面のモードとして扱い、画面を割らない)。メニュー画面はユースケースを持たない入口として置く。この対応を述べる文 (販売反映が画面を持たない、どの遷移がどの例外に対応するか) は題材に依存するので prose レコード (`contents/設計書/画面設計.md`) に置き、名指しするユースケースや要求種別へは `[UC04](node:/ユースケース記述/UC04)` の形の `node:` リンクで張る (設計書配下の他の prose も同じ形で、エンティティや用語集を名指しする箇所にリンクを入れた)
- **分類 は enum 4 値 (メニュー / 登録 / 一覧 / 照会) で必須** (S7 からの持ち越し)。入口の導出 (下記) が分類に依存するので必須にした。enum の定義文は形の説明なのでテンプレートの表の下に置く
- **遷移は アクション の配下に、画面が変わるものだけを書く**。画面内で完結する操作 (検索、明細の追加、同じ画面で続けて行う登録) は 遷移 を持たないアクションとして残り、図には出ない (7b の画面定義で見える)。条件付きの遷移は 条件 を持ち、無条件は省略する。同じアクションから条件で遷移先が分かれる形は 遷移 の要素を分けて書く
- **図は `stateDiagram-v2`、方向は TB**。state = 画面 (`SCxx : 画面名`)、遷移 = アクション.遷移 から導出する。LR ではメニューへ戻る辺がメニューの左右に絡んで読めなかった。TB ではメニューがハブとして上に立ち、業務間の渡り (入荷登録 → 書籍登録 → 書籍履歴) が下へ流れる (実機で両方を描いて比較)
- **複合 state は使わない**。当初は画面をユースケースごとの複合 state (`state "名前" as UCxx { }`) で束ねていたが、レビューで退けた: 画面とユースケースは多対多 (書籍履歴画面は在庫照会の他に、書籍登録の例外「同じ ISBN が登録済み」で登録済みの書籍を示すのにも使う) で、Mermaid は同じ state を二つの箱に宣言できないため、束ねるには「先頭のユースケース」で代表させるしかなく、n : 1 の仮定をテンプレートに埋め込むことになる。画面とユースケースの対応は画面一覧の表 (多対多をそのまま列挙できる) に任せ、図は遷移だけを担う。複合 state 自体は描けることを確認したので、サブシステムや業務分類のような画面に対して 1 : n の軸を別に持つ題材なら束ねる軸に使える
- **条件分岐は choice node を使わず、ガード付きラベル**。`from --> to : アクション名 [条件]` で足りる。`<<choice>>` は一つのアクションから分岐点を経て複数の遷移先に分かれる形だが、遷移 の要素が条件を持つ設計ではラベルに書く方がデータと図の対応が素直で、分岐点という余分な state も要らない
- **入口は 分類 = メニュー の画面に `[*] -->`、出口は描かない**。利用者はどの画面からでも操作を終えられるので、出口の辺を全画面から引くと図が読めなくなる。描かないことで、schema に「終了」を表す遷移先 (x-ref は画面以外を指せない) を足す必要も消えた
- **web edition は章を 1 頁** (`画面.item[]`)。画面 1 件の頁 (`画面.item`) は 7b の画面定義と同時に割る (7a には各画面を描く節が無く、一覧の画面名からのリンク先が無い)。web で章が index.md から抜けるので、設計書冒頭の一文から章へリンクする (コンテキストと同じ)
- **見出しの段数**は本の版で 章 (###) → 節 (####) の 4 段で、データ設計より 1 段浅い。7b で 画面定義 (####) → 画面 (#####) → 入出力項目 / アクション (######) と 6 段に達する見込み

Mermaid 適合性の実機確認結果 (S4 の検証項目): `stateDiagram-v2` で日本語の state 記述 (`SC01 : メニュー画面`)、日本語の複合 state 名 (`state "書籍登録" as UC01`)、ラベル中の角括弧・空白・日本語、`direction TB` / `LR`、箱の外から箱の中の state への遷移、いずれもブラウザで描画された (複合 state は上記の理由で最終形には残していない)。

#### 画面定義 (設計書 4 章後半)

章別 PR 7b で決めた事項。設計書 4 章の後半を、画面 1 件ごとの節「画面定義」として置く。章テンプレート (`画面設計.md`) が 1 件用テンプレート (`画面定義.md`) を render し、web edition では `画面.item` で 1 画面 1 頁に割って画面一覧の画面名からリンクする (論理データモデル → エンティティ定義 と同型)。新規レコードは無く、7 画面に 入出力項目 (計 28 件) と アクション.説明 を足した。これで S4 の束 (2 / 7a / 7b) が揃い、二文書の章別 PR はすべて済んだ。

- **画面定義の形はユースケース記述と同じ**。概要 → 項目表 (分類 / 関連ユースケース) → 小見出し「入出力項目」(表: 項目 / 入出力 / 参照先 / 説明) → 小見出し「アクション」(表: アクション / 説明 / 遷移先)。web では画面の頁が単独で読まれるので、一覧にもある分類と関連ユースケースを項目表として再掲する。本の版の見出しは 6 段 (設計書 → 画面設計 → 画面定義 → 画面 → 入出力項目 / アクション) に達し、Markdown の下限に着いた。これ以上深い構造 (画面の下に部品や状態を持つ等) は章・節を頁ノードにする E17 無しには置けない
- **入出力項目 に 説明 (任意) を足した** (6a で 属性 に 説明 を足したのと同じ理由。IPA の画面入出力項目一覧も項目説明を持つ)。参照先を持たない項目 (画面にしか無い 検索語、三種のイベントを一つの表に畳む 履歴の日時 / 種別 / 数量) は、ここで意味を示す。参照先 の description にも省略してよい場合を書いた
- **参照先.属性 の突合はエンティティ定義と同型**。x-ref はエンティティの ID しか指せないので、`node("エンティティ", …)` で参照先を引き、属性名が 属性[] に無ければ「(参照先に無い属性名)」を表に出す (綴りを崩して検出を確認)。入れ子要素への x-ref が入るまでの代替で、二例目
- **項目 ⇔ アクションのクロスリファレンスは持たない**。IPA のアクション明細は使う項目を ID で指すが、schema に アクション.項目[] を足すと入れ子要素への参照がもう一組増え、突合も手書きになる。文書内同期の実証は 参照先 → エンティティ.属性 で足りているので見送った。必要になれば 項目名の配列 + テンプレートでの突合という同じ形で足せる
- **アクションの 説明 はユースケースの基本シナリオの応答 (と例外の応答) を画面の言葉に写す**。遷移を持たないアクション (検索、明細の追加、同じ画面で続けて行う登録) は遷移図に出ないので、画面定義のアクション表で初めて見える。遷移先の列は画面の頁へリンクし、条件は括弧で添える
- **エンティティ頁の逆引き (参照する画面) は 7b に含めない**。対象がエンティティの頁で 7b の主題と別なので、独立の小さな PR に切り出す (Candidates 参照)

#### テンプレートに書く文と contents に書く文の境界

章別 PR 6b のレビューで決めた規約。**テンプレートに書けるのは、形を説明する文まで** — 図や表の読み方、記号の意味、schema の enum の定義 (「リソースは業務の対象として在り続ける実体」)、章の導入文 (「本章では…を示す」)。これらは同じ schema なら別の題材に差し替えてもそのまま成り立つ。**レコードに依存する文は contents に置く** — 題材の名前、特定のレコードや設計判断を名指しする解釈 (「入荷と販売が更新されないのは D02 の帰結」)、このデータに固有の観察 (「用語を持たないのは明細のエンティティ」)。題材を差し替えると嘘になる文がテンプレートに残っていれば、それが境界の侵犯の印。showcase は「読んで自分の構造に書き換えるための見本」なので、テンプレートを触らずに題材を差し替えられることが規約の目的でもある。

6b までに入っていた侵犯と、その直し方:

- **CRUD マトリクスの解釈文と論理データモデルの観察文 → prose レコード**。節の補足段落として `contents/設計書/CRUDマトリクス.md` / `contents/設計書/論理データモデル.md` に置き、節テンプレートが表・一覧の下に埋め込む。web で節が 1 頁に割れても補足が同じ頁に載るよう、殻ではなく節テンプレートから引く。prose は主題 (view / エンティティ) の部分木の外なので `render` は `_guard_subtree` に拒まれ (home の頁が別)、`node(path="/prose/…").content | relink` で content だけを埋める。設計方針テンプレートが `node("要求", ID)` の属性を読むのと同じ「部分木の外の値を読む」形で、prose の anchor はどこにも出ないが、補足段落へリンクする者はいない。CRUD の導出文 (列を数えた結果を「作成されないのは X」と出す文) は言い回しが題材に依らないのでテンプレートに残す
- **二文書の冒頭の「小規模書店向け在庫管理システム」とコンテキスト図の境界ラベル「在庫管理システム」→ 単一レコード システム (名前 / 説明)**。一つの値が三箇所に散っていたので、prose ではなく single-record pattern のエンティティに寄せた。殻 (root の文脈) からは `{{ システム.説明 }}`、サブテンプレート (コンテキスト) からは `node(path="/システム").名前` で引く (単一レコードは view の `from` に立てられないが、`node(path=)` では届く。実機確認)。どの層にも属さない横断要素として schema の先頭に置く
- **残る題材名**: `index.md` (プロジェクトの説明) の「題材は小規模書店の在庫管理システム」は、二文書ではなく showcase 自身の説明文なので対象外

#### 背景: 機能構成の章を置かない

たたき台と S8 の目次は設計書 3 章に「機能構成 (機能一覧)」を置き、IPA のシステム化業務一覧に対応させていた。最初の章 PR で実装したところ、要求仕様書 1 章の主要機能の表と列まで同じ再掲になり、読み手には「同じ表がもう一度」でしかなかったので落とした。日本の SI で基本設計書が業務機能を再掲するのは、要件定義書と著者・読者が違い設計書が単体で読める必要があるからで、単一ソースの二文書にはその前提が無い (設計書の記法と規約に「要求仕様書を前提に読み、ユースケースは ID とリンクで参照する」と宣言する)。IPA の一覧が設計成果物として持つ情報 (関連画面 / 関連エンティティ) は、この showcase では 2 章 (関連図の辺)、3 章 (CRUD の行)、4 章 (画面一覧の関連ユースケース列) に分散して現れ、各行から要求仕様書へのリンクがトレーサビリティになる。同じレコードを二文書に出す実証は、列まで同じ再掲ではなく「文書ごとに違う列で描く」形 (要求仕様書は誰が何を達成するか、設計書はどの画面とデータで実現するか) で取る。

#### 二文書の器 (暫定: index.md の合本、本命: 合成ビュー E17)

実機確認の結果、**サブテンプレートからはトップレベルの名前空間 (エンティティ / ビュー) が見えない** (`template_engine._bind` は主題のフィールドと `this` だけを束縛する。paging-spec の「束縛は root とサブテンプレートで同一規則」の帰結)。ただし `node()` はサブテンプレートからも届き、`node("アクター")` のようにコレクションごと引いてそのまま反復できる (PR 2 で確認) ので、主題の外のデータを読むこと自体はできる — できないのは名前空間の参照と、下記のとおり他エンティティを**章として描く**ことである。`render` の主題は `this` の子孫に限られる (`_guard_subtree`) ので、「文書」を主題にしたサブテンプレートで他エンティティの章をインライン展開することもできない。`{% include %}` は root の文脈を共有するので `index.md` を文書ごとのファイルに分けることはできるが、ページは作らない。したがって複数エンティティを束ねる「文書」は、現状 root テンプレート (`index.md`) でしか組めない。

edition 別ルートテンプレート (edition の目的外利用)、予約名でデータルートを渡す案 (第二の入口になる上、リンク解決が静的なので文書ページに描いたノードへのリンクが `index.md` を指す)、`from: __root` のクエリ (特例の積み重ね) を検討して退け、**文書をデータ木のノードとして立てる view の第二の文法 = [合成ビュー (E17)](../60-composer/10-query-dsl-spec.md#合成ビュー-e17)** を本命とした。E17 は M13 が前提。

S8 は E17 を待たず、**暫定の器**で進める:

- `index.md` (root) に二文書を並べる。文書ごとのテンプレート (`要求仕様書.md` / `設計書.md`) は `{% include %}` で取り込み、root の文脈で描く
- 章テンプレート (用語集、prose 章) は、その章が描くエンティティ / prose レコードを主題に取る `render` で書く。E17 後もそのまま使える
- 二 edition (web / book)。book は `file_per: []` (全 inline、二文書が一ページの合本)。web は 用語集 (`用語.item[]`)、ユースケース記述 (`ユースケース記述.item`。3a で `ユースケース.item` として追加し、3b で要求を join した view の行に変えた)、非機能要求の種別ごとの節 (`要求種別.item`、3b)、設計方針 (`設計判断.item[]`、5)、コンテキストの章 (`コンテキスト.item[]`、2)、論理データモデルの節と各エンティティ (`エンティティ.item[]` と `エンティティ.item`、6a)、CRUD マトリクスの節 (`CRUDマトリクス.item[]`、6b) を別ページにし、二文書は index.md に残る。**章の内容が単一のコレクションに収まるなら、章専用の view を主題に立てて章を 1 ページに割れる** (2 で確認)。割れないのは、内容が複数の view にまたがる章 (4 章の検証) と、文書そのものである。split されるページは自分の見出しを持つ必要があるので、用語集の見出しと導入文は章テンプレート (`用語集.md`) が持ち、文書の殻は見出しを書かずに `render` する (dev-docs の tasks.md と同じ作法)。web で文書から用語集へ渡る導線は、文書冒頭の導入文に置く `{{ 用語 | link }}` (book では頁内リンクになる)。E17 が入ったら、文書ごとに合成ビューを定義して殻 (`include` → `render`) を差し替え、web の `file_per` で文書 / 章に割る。手戻りは殻の部分のみ

#### 空の章の見え方

各章はテンプレートに見出しと導入文 1 行 (上表の「目的」を文書の文として書いたもの) を持ち、データのある章 (用語集、prose 章) だけ本文が出る。章見出しに番号は付けない: split される章 (用語集) は自分の見出しを持ち、prose の節見出しには番号を埋め込めないので、番号を付けると edition 間・章節間で不揃いになる。上表の章番号は仕様内の参照用。担当タスクは導入文の下にビューと表を足す。「S3 で埋める」のような内部語彙は showcase の出力に出さない。

### S7 / S8 で表面化したツール側・将来の検討事項 (未起票)

showcase の設計対話で見つかったが、showcase タスクの範囲外として起票を保留しているもの。起票先はツール本体のタスクか本ファイルの Candidates。S8 で表面化した合成ビューは E17 として起票済み (前提は M13)。

- **`{% include %}` の文書化**: 動くが `docs/reference/template.md` に記述が無い (template-trust-model の loader の節で触れているのみ)。root テンプレートの分割手段として記述する。小さな docs PR
- **string 配列への x-ref**: `items: { type: string, x-ref }` を許す拡張。現状はオブジェクト配列に包む
- **入れ子要素への x-ref**: x-ref はエンティティの ID しか指せず、エンティティ配下の 属性[] の要素は指せない。画面.入出力項目.参照先.属性 と エンティティ.属性.参照.属性 は素の文字列で、属性名の綴り違いはビルドで検出されない。親 ID + 子要素の名前 (複合キー) を指す x-ref の拡張か、S3 / S4 で view による突合を検討する
- **上流プロジェクトの参照 (依存)**: 要求を発注者側、設計をベンダや AI のリポジトリで持つ運用では、別プロジェクトの entity を読み取り専用で x-ref の対象にし、版を固定する機能が要る。参照の向きの規律はこの分割を可能にする前提
- **suspect link (要確認リンク)**: 要求に版を持たせ、設計側の参照が設計時の版を持てば、要求変更で古くなった設計要素をビューで導出できる (新規要求の孤児検出と対)。S6 (トレーサビリティ) の増分で載せる候補。多対多で強いられた `{ID, 版}` のオブジェクト配列の形がそのまま使える
- **スコープ管理と FP 概算**: 要望一覧 / リリース計画 / FP 概算は別の文書群ではなく、同じレコードのスコープ確定前の姿 (要求・ユースケースに状態と対象リリースを持たせ、二文書は「採用」の部分集合を描くビュー)。FP が数える要素 (論理ファイル = エンティティ、トランザクション = 画面のアクション・外部インタフェース) は本 schema にあるので概算はビューで導出できる。showcase の範囲外 (showcase はスコープ確定後の文書を描く) だが製品動機に近い
- **プロジェクト管理成果物の showcase**: ステークホルダ登録簿や RACI など PMBOK 系の成果物は「表を構造化データから導出する」題材として筋が良い
- **ja / en 変種の構造同一性テスト**: 日本語版を製品として残す場合、名前を除いて schema の形が一致することを検査する仕組み
- **同じ subject を二度 render すると subject の anchor が二重に出る**: 一時期あった設計書の機能一覧が要求仕様書の主要機能と同じ `ユースケース | render(...)` で、一ページ (index.md) に `<a id="/ユースケース">` が 2 つ出た。ビルドは通り (`--strict` でも警告無し) リンクは先勝ちで着地するが、HTML の id 重複ではある。同じコレクションを二章で描く構成では起こりうるので、ツール側で 2 つ目以降を抑止するか警告するかを検討する
- **anchor の所在とリンクの向き先の食い違いを検出できない**: リンクの向き先の頁はデータ上の位置で決まるので、`node()` で引いたノードを別の頁 (split された他レコードの頁) に `| anchor` で描くと、anchor はそこに出るのにリンクは home の頁を指す。ビルドは通り `--strict` も警告しない (3b で実機確認。定石は join view で、External Design「S8」の「要求」)。anchor が home 以外の頁に出たら警告する検査があると、この取り違えを早く引き当てられる
- **マクロの戻り値の再エスケープ**: autoescape を切っているので Jinja マクロの戻り値は素の文字列になり、`{{ macro() }}` で呼ぶと `link` の出力までエスケープされる (PR 5 で実機確認)。症状は docs の Markdown escaping の節から辿れ、`| safe` か `{% set %}` で回避できるが、同節は `| safe` をコードスパン / フェンス / Mermaid の話として書き、`link` 等は「`| safe` 不要」と明記しているので、マクロ経由だと要るという例外が読めない。同節に一行足す (小さな docs PR)
- **コードフェンスの中のリンクが HTML 版で外れる**: Mermaid の `click` に `href` の URL を埋めると、出力 Markdown では正しいのに、コードフェンスの中なので Markdown から HTML への書き換えが効かず、`.md` のまま残って HTML 版で 404 になる (PR 2 で実機確認)。図の中からのリンクは現状どの図法でも張れない。図が大きくなる章 (4 の画面遷移図) でも効いてくるので、フェンス内の URL を edition に合わせて解決する手立て (専用フィルタ等) を検討する余地がある
- **空の contents / views ディレクトリ**: 無いとビルドが失敗するため `.gitkeep` で保持している。無くても通る方が親切

### 順序の見立て

S5 (調査・方針確定)、S7 (モデル構築)、S8 (突合・目次確定、二文書の器) 完了。以降は **章別の個別撃破**。S2 (階層 DFD) は独立の showcase になったので順序の制約は無く、記法リスク (PlantUML 舵切り) を早く引き当てる意味では先行してよい。次いで上記候補。

#### 進め方: PR の単位は章

S3 / S4 / S6 は artifact の種別で束ねたタスクで、一つのタスクが二文書の複数の章にまたがる (S3 は要求仕様書 1・3 章と設計書 3 章)。この大きさでは、章のレンダリング結果を見て S8 の目次仕様の当否を確かめる、という確認の回し方ができない。そこで **PR は章を単位に切る**。ただし章の大きさは揃っていないので、同じレコードから描く小さな章は抱き合わせ、レコードの投入と設計判断を複数抱える大きな章は節に割る。

S3 / S4 / S6 の task ID は切り直さず、各タスクが抱える **決め事の束** (CRUD セルの粒度、シナリオの構造化、説明属性の形式、stateDiagram の適合性等) の名前として残す。決め事は、それを最初に必要とする章の PR で決め、決めた時点で Proposals から External / Internal Design 節へ移す。PR 本文で該当 task ID を参照し、束の章がすべて入った時点で done にする。
