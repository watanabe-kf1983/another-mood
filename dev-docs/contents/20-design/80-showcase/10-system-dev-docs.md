# システム開発ドキュメント

ユーザがシステム設計書を authoring する際に、本ツールが first-class でサポートする artifact 群。各タスクは「artifact 用のスキーマ」「サンプルデータ」「表現テンプレート」の三点セットを blueprint として提供する。

[F (メタドキュメンテーション)](../75-meta-documentation/10-database-information.md) との違い: F はカタログから auto-derive する meta-view (ツールが自分自身を説明する用途)、本カテゴリはユーザが authoring した data 上で動く first-party blueprint (ユーザに設計書 authoring の力を授ける用途)。両者は同じ「構造化データ → 自動描画」のメカニズムを共有するが、データの出所 (カタログ vs ユーザデータ) と動機が異なる。

## External Design

### 典拠: 借りるのは目次ではなくモデル

単一のsbdb プロジェクト (showcase) から「要求仕様書」「設計書」の二文書を導出する。目的はソフトウェア開発ドキュメントの手本を示すことではなく、Another Mood のソフトウェア開発への応用例を見せること。作られるべき文書とその粒度は開発プロジェクト固有なので、showcase は標準の成果物構成を示すものではなく、一つのテーラリングであると自ら明言する (「あなたのプロジェクトでは別の形になる」)。何に依拠するかは、無料一次資料の調査を経て下記「モデルファースト」方針に確定した。conformance は主張せず "informed by" に留め、docs での謳い方もそう抑える (29148 の full conformance は要求文の特性 5.2.x と Clause 9 の内容要求の網羅義務を伴い、応用例という目的には過剰)。作業言語は日本語で作り切ってから英訳する (docs の英語化と同じ流れ)。

#### 調査の帰結: モデルファースト

よりどころは目次ではなくモデルに置く。既製テンプレートが無く、標準はモデルの水準で実体のある定義を持つことを確かめた調査は[背景](../../90-appendix/20-design/80-showcase/10-system-dev-docs.md#調査の帰結-モデルファースト):

- **項目の典拠は成果物の系統ごとに一つに絞る**。設計書側の相互参照型の成果物（画面 ⇔ 入出力項目 ⇔ エンティティ、CRUD）は IPA ガイドの項目定義、要求仕様書側は 29148（+ Volere）の要求属性。42010 の概念モデルは文書の枠組み（ビューポイント = schema の定義の束、ビュー = 章）を理解する道具として使い、データには持たない。ステークホルダは SRS / SDD に登場せず、関心事は要求と rationale に化けるので持たない。ユースケースのアクターはステークホルダとは別物で、上流の独立エンティティとして持つ
- **モデルの記述場所は showcase の schema.yaml そのもの**。抽出したモデルを別文書に起こさず、スキーマ + x-ref として書き、description に参照元を補記する（「IPA 画面一覧に対応」程度）。ビルドすれば `__defs/entities` / ER メタビューがモデルの図を出す
- **目次はモデルから導出されるビューの一つ**。章の並びは 29148 も IPA も自由裁量と明記しており、こちらで決めてよい。標準との対応は「何が記述され、どう関係づけられるか」の水準で取り、それも conformance ではなく description の典拠注記に留める
- **抽出は網羅しない**。サンプルに必要な範囲へのテーラリングと突合で済ませる。IPA の暗黙モデルを網羅的に抽出するほど翻案禁止条項に近づくため、部分的・自分の言葉での再構成が作業量でも法的にも安全側

資料ごとに借りるものと転載上の制約、情報源は[背景](../../90-appendix/20-design/80-showcase/10-system-dev-docs.md#典拠と借用の分担)。

### showcase/system-dev-docs-ja: 要求仕様書と設計書の二文書

単一のデータソースから要求仕様書と設計書を導出する showcase。モデル (schema.yaml) に章 → ソース (この章はどのレコード群のビューか) と エンティティ → 登場章 の対応を張って目次を確定してあり、どの章にも現れないエンティティ、どのエンティティにも支えられない章は無い。モデルの図は `mood build showcase/system-dev-docs-ja` の `__db/__defs/entities` (ER メタビュー) で読める。

#### 位置づけと規約

- **showcase 名**: `showcase/system-dev-docs-ja`。本カテゴリ名 + 言語接尾辞
- **二文書を一つのsbdb プロジェクトから導出する**。文書別に blueprint を分けると、CRUD マトリクスやトレーサビリティのような文書をまたいで同じレコードを参照する成果物が作れず、「単一ソースから同期した文書群」という製品テーゼの実証が立たない
- **showcase は内容ではなく機構の見本**。作られるべき文書とその粒度は開発プロジェクト固有で標準化もテンプレ化もできない (だからこそ構造を柔軟に定義できるツールが要る)。showcase の schema はそのまま流用されるものではなく「読んで自分の構造に書き換えるための見本」であり、価値は読みやすさと改変しやすさにある。description の典拠と英名は、その改変の手がかりとして機能する
- **正本は英語、日本語は下書きの作業言語** (docs/ と同じ流れ)。日本の従事者向けに日本語版を製品として残すかは今後判断する。どちらに転んでも手戻りが出ないよう、識別子・enum 値は日本語のまま進め、**英名を schema.yaml の description 末尾に付記する規約**にする (書式は schema.yaml 冒頭のコメント)。英語版の派生は同一ファイル内の置換で済み、`__defs/entities` の表にも英名が出る。命名は既存 showcase に合わせ、トップレベルのエンティティと配列プロパティは複数形、参照は `xxx_id`
- **英語版では章の割り当てが変わりうる**。日本の基本設計 (外部設計) の内容は、29148 の区分ではかなりの部分が SRS 側 (外部インタフェース要求 / 論理データベース要求) に入る。文化差があるのはモデルではなく束ね方なので、英語版を起こすときは schema の改名だけでなく章の割り当ても見直す余地がある

#### 参照の向きと層

**参照の向きは下流 (設計書のソース) → 上流 (要求仕様書のソース) のみ**で、上流のデータは下流を知らずに閉じる。理由の著者分離は schema.yaml 冒頭のコメントにある (将来sbdb プロジェクトを分ける場合も機械的に切れる)。この規律で CRUD (ユースケース × エンティティ) は設計側に置き、用語 ↔ エンティティ の対応もエンティティ側から張る。上流の中にも層があり (ユースケース = StRS 層が上、要求 = SRS 層が下)、要求 → ユースケース の向きはこれに従う。schema.yaml の節構成は、横断の システム と業務の節に続くこの二段 (上流: 要求 / ユースケース / アクター / 用語、下流: 画面 / エンティティ / データアクセス / 設計判断 / コンポーネント) で、1016 のビューポイント単位にはしない。

**層の内訳と二文書の境界**。上流 / 下流の二段をもう少し細かく切ると次のとおり。用語 はどの層にも属さない横断要素で、要求仕様書の用語集に置く。

| 層 | 29148 / 1016 での呼び方 | 日本の SI での呼び方 | 本 showcase | 文書 |
|---|---|---|---|
| 業務 | BRS (事業要求)、OpsCon の業務モデル | 業務分析、業務フロー | プロセス、データストア、外部エンティティ、フロー (階層 DFD。下記「業務モデル」) | 要求仕様書 |
| 利用者の視点 | StRS (ステークホルダ要求)、OpsCon の運用シナリオ | 要件定義の業務要件、システム化業務説明 | ユースケース、アクター | 要求仕様書 |
| ソフトウェア要求 | SRS 3.2 Functions ほか (要求文) | 要件定義の機能・非機能要件一覧 | 要求 | 要求仕様書 |
| 外部設計 | SRS 3.1 External interfaces / 3.5 Logical database と SDD の両方に跨る | 基本設計 (画面設計、論理データモデル、CRUD) | 画面、エンティティ、データアクセス | 設計書 |
| 方式設計 | SDD の System architecture (ソフトウェアの分解と、添え物としての配置) | 基本設計のサブシステム分割・機能構成、方式設計のシステム構成 | コンポーネント (+ 配置の prose) | 設計書 |
| 内部設計 | SDD (1016 の Logical / Structure 等) | 詳細設計 (テーブル物理定義、クラス設計) | (対象外) | — |

29148 と日本の基本設計が重なるのは外部設計の層で、重なりが強いのはエンティティ (SRS 3.5 の中身はほぼ論理データモデル)、弱いのが画面 (3.1 が求めるのはインタフェースへの要求で、項目・アクション・遷移の定義は 29148 でも設計寄り)。本 showcase は日本の束ね方 (基本設計 = 設計書) を採る。文化差はモデルではなく束ね方にあるので、英語版で 29148 寄りに束ね直す場合は章の割り当てだけを動かす (上記「英語版では章の割り当てが変わりうる」)。

参照の向きの規律の結果、参照だけで並べると 業務層 (プロセス / データストア / 外部エンティティ / フロー) → アクター / 用語 → ユースケース → 要求, エンティティ → 画面, データアクセス, 設計判断 → コンポーネント の順になる。業務層への参照は ユースケース.業務プロセス[] → プロセス (葉) と エンティティ.データストア[] → データストア の 2 本で、業務層は他の層を知らない。要求と画面 / エンティティの間に直接の参照は無く、ユースケース経由で辿る。トレーサビリティ (要求 ↔ 設計) で設計要素から要求へ直接張りたくなった場合は、規律に従い 画面 / エンティティ → 要求 の向きで足す。

#### 業務モデル (階層 DFD)

業務モデル (階層 DFD) は system-dev-docs-ja の業務層として同梱する。ユースケース → プロセス の参照は下流から上流への向きで参照の規律に適合し、「要求仕様書の本体が付録を参照する」のは文書配置 (テンプレート) の問題でデータの層とは別なので、独立の showcase にはしない。同梱で得られるのは、「参照の向きと層」の表の業務行が埋まり四層が一つのデータで通ること、ユースケース → 葉プロセス の参照から **システム化範囲** が導出できること (Volere の work context → business events → product use cases と同じ構造で、DFD を変えると範囲の節が同期して変わる)、エンティティ → データストア の参照が張れること (構造化分析の DFD → データ辞書 → ER の系譜)。

**境界: 業務 DFD であってシステム DFD ではない**。レベル 0 の唯一のプロセスは 書店の業務 で、端点 (外部エンティティ) は 顧客 / 仕入先 のような業務の外の相手。本システムを唯一のプロセスに置くシステム DFD は設計書 2 章のコンテキスト図 (アクター × ユースケース) の重複になるので採らない。帰結として 外部エンティティ ↔ アクター の対応は張らない: 店員 は業務の内側で (DFD には役割を描く場所が無い)、顧客 は本システムのアクターではなく、決済サービス は業務から見れば会計プロセスの道具で本システムから見れば外部システム、と二つの境界はずれる。ずれること自体が、業務 DFD がコンテキスト章の重複ではなく情報を足す根拠になる。本システムの境界は、葉プロセスのうちユースケースに支えられるものの集合として (システム化範囲) 導出される。

**モデル**。schema.yaml では 上流 の節の前に 業務 の節 (プロセス / データストア / 外部エンティティ / フロー) を置き、業務層は他の層を知らない。モデルの規則 (各レベルのフロー、多態参照、番号、他の層からの参照) は schema.yaml の description とテンプレートのコメントが正本。

**項目定義の典拠**: IPA ガイドに DFD は存在しない (データの流れは業務フロー / バッチ処理フロー / 外部システム関連図に分散)。構造化分析の古典 (DeMarco / Yourdon。レベル分割・バランシング規則は文献上厳密に定義されている) と IPA 外部システム関連図の凡例を参考に自作した。

**置き場**。要求仕様書 1 章に 業務コンテキスト (レベル 0 = コンテキスト図) と システム化範囲 (葉プロセス × ユースケース の表) を置き、5 章 (付録) にレベル 1 以下 (プロセス階層 / データストア / 外部エンティティ / 分解図 / バランシング検査) を置く。29148 の 1.2 Scope / 1.3 Product perspective の位置に業務の境界と範囲が来る形で、システム化範囲の導出という同梱の主目的を付録の奥に沈めない。

**バランシング検査**は付録末尾の節で、分解図ごとに上位の図の親プロセスの入出力と図の中のフローの対応を確かめ、不一致を表に出す (無ければ一致の一文)。規則は行を跨ぎ階層を辿る述語で view 言語では書けないため view は立てない。ビルドの警告に載せる経路は[ツール側の検討事項](../../90-appendix/20-design/80-showcase/10-system-dev-docs.md#showcase-で表面化したツール側将来の検討事項-未起票)。

## Proposals

### 英語版 showcase/system-dev-docs-en (S10)

system-dev-docs-ja を複製して英訳し、SRS / SDD として出す。判断の基準は規格の条文との突合ではなく、**英語圏の読者が見出しを見て「よく見る SRS / SDD だ」と思えるか**。conformance は主張せず "informed by" に留める方針 (上記「典拠」) はそのまま。

**別プロジェクトとして複製する**。同一モデルから両言語を出す案 (tasks.yaml の note) は採らない。識別子が日本語なので、同じデータから両言語を出すには識別子を二重に持つ拡張が要り、showcase の読みやすさ (改変の見本) を損なう。ja / en の構造同一性の検査は[ツール側の検討事項](../../90-appendix/20-design/80-showcase/10-system-dev-docs.md#showcase-で表面化したツール側将来の検討事項-未起票)に既にあり、ここでは扱わない。日本語版を製品として残すかの判断 (上記「位置づけと規約」) も S10 では動かさず、ja はそのまま残す。

**章の割り当ては動かさない**。「英語版では章の割り当てが変わりうる」(上記) の余地は、設計書にシステム構成章 (3 章) が入ったことで使わずに済むと判断した。英語圏の SDD の雛形 (Introduction / System overview / Architecture / Data design / Interface design) と設計書の章立てが並びまで一致し、Data design は英語圏でも SDD の標準の章なので、29148 3.5 Logical database に合わせて論理データモデルを SRS 側へ移す必要が無い。移すと設計書から要求仕様書へのリンク (二文書 showcase の主題) が片側に偏り、ja と en の章の対応も崩れる。完了時に「英語版では章の割り当てが変わりうる」と「層の内訳と二文書の境界」末尾の一文を、この決定で書き換える。

**語彙**。識別子と enum 値は schema.yaml の description 末尾の英名 (既存の規約) を当てる。文書名は Software Requirements Specification (SRS) と Software Design Document (SDD)。SDD は 1016 の "Description" ではなく、英語圏の雛形で多い "Document" を仮に採る (1016 は章に被せない方針なので名前も借りない)。章題の対応:

| ja | en |
|---|---|
| 要求仕様書: はじめに / 用語集 / 要求 (機能要求 / 非機能要求) / 検証 / 付録 (業務モデル) | Introduction / Glossary / Requirements (Functional / Non-functional) / Verification / Appendices (Business model) |
| 設計書: はじめに (目的と範囲 / 記法と規約 / 設計方針) / コンテキスト / システム構成 (コンポーネント図 / コンポーネント一覧 / 配置) / データ設計 (論理データモデル / CRUD マトリクス) / 画面設計 (画面一覧 / 画面遷移図 / 画面定義) | Introduction (Purpose and scope / Notation and conventions / Design decisions) / System context / System architecture (Component diagram / Components / Deployment) / Data design (Logical data model / CRUD matrix) / User interface design (Screens / Screen flow / Screen definitions) |

節より細かい語の選択は訳しながら決め、迷ったものは PR 本文に残す。

**英訳に先立つ小さな改編** (構造は変えない。英語圏の読者が最初に引っかかる箇所の手当て):

1. 設計書 3 章の冒頭に、アーキテクチャの概観の一文を置く (1 台のサーバで動く一つの Web アプリケーション、業務単位の 5 コンポーネントが二層をなし、データベースを共有する)。今は D08 の理由と配置の冒頭に散っている。置き場は prose `設計書/コンポーネント図` の先頭
2. D07 と C02 の責務の「加減算」を、棚卸の「置き換え」(C05) を含む語に揃える
3. 要求仕様書に、外部インタフェースとデータの設計 (29148 なら 3.1 / 3.5 に当たる内容) は設計書で扱う旨の一文を置く。置き場は 1 章 (Product perspective に当たる位置)

**進め方**。一ブランチの上で 複製 → (日本語のまま) 改編 → 英訳 の順に段階ごとにコミットし、PR は一本。構造の diff と訳の diff を分けて確認できるようにするため。改編は ja にも当たるので、ja 側の同じ箇所も直す。英訳の対象は schema の識別子と enum 値、contents (yaml / md / 画面レイアウトの SVG・HTML の文言)、テンプレートの見出しと地の文、ファイル名とディレクトリ名、sbdb.yaml (`title`, `file_per`)、showcase/index.yaml の項目。完了時に上記「位置づけと規約」の showcase 名の規約に en を加え、本節を削除する。
