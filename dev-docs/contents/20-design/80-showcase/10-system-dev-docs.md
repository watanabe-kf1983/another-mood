# システム開発ドキュメント

ユーザがシステム設計書を authoring する際に、本ツールが first-class でサポートする artifact 群。各タスクは「artifact 用のスキーマ」「サンプルデータ」「表現テンプレート」の三点セットを blueprint として提供する。

[F (メタドキュメンテーション)](../20-app/40-meta-documentation.md) との違い: F は catalog から auto-derive する meta-view (ツールが自分自身を説明する用途)、本カテゴリはユーザが authoring した data 上で動く first-party blueprint (ユーザに設計書 authoring の力を授ける用途)。両者は同じ「構造化データ → 自動描画」のメカニズムを共有するが、データの出所 (catalog vs ユーザデータ) と動機が異なる。

## External Design

### 典拠: 借りるのは目次ではなくモデル

単一の showcase プロジェクトから「要求仕様書」「設計書」の二文書を導出する。目的はソフトウェア開発ドキュメントの手本を示すことではなく、Another Mood のソフトウェア開発への応用例を見せること。作られるべき文書とその粒度はプロジェクト固有なので、showcase は標準の成果物構成を示すものではなく、一つのテーラリングであると自ら明言する (「あなたのプロジェクトでは別の形になる」)。何に依拠するかは、無料一次資料の調査を経て下記「モデルファースト」方針に確定した。conformance は主張せず "informed by" に留め、docs での謳い方もそう抑える (29148 の full conformance は要求文の特性 5.2.x と Clause 9 の内容要求の網羅義務を伴い、応用例という目的には過剰)。作業言語は日本語で作り切ってから英訳する (docs の英語化と同じ流れ)。

#### 調査の帰結

調査の帰結: 「要求仕様書 + 設計書」をそのまま書ける、無料で再配布可能な既製テンプレートは存在しない。各資料が持つのは断片で — 29148 は目次はくれるが節の内容定義は有償、IEEE 1016 はそもそも文書テンプレートを規定しない、IPA は成果物の項目定義は完全だが文書の目次を持たない、arc42 / Volere は完全なテンプレートだがライセンスと守備範囲が合わない — 目次を寄せ集めても「標準のラベルを着た我流」にしかならない。

一方、標準はモデル (スキーマ) の水準では実体のある定義を持つ:

- **ISO/IEC/IEEE 42010** の本体は目次ではなく概念モデル (ステークホルダ–関心事–ビューポイント–ビュー のエンティティ・関係・多重度)。Rozanski & Woods 本の概念モデル図はこの系譜の拡張で、同書が足した Perspectives は 42010:2022 で規格側に逆輸入された
- **IEEE 1016** は viewpoint の仕様を「design concerns + design elements (entity / relationship / attribute / constraint の型)」として定義せよという規格で、最初からスキーマ集として書かれている (文書テンプレートが無いのは欠落ではなく設計)
- **OMG ReqIF** は文字通りのメタモデル。ただし要求がどんな属性を持つべきかは意図的に固定しない (そこは各組織のスキーマ、という割り切り)
- **IPA ガイド** はメタモデルを描かないが、27 工程成果物の項目定義とクロスリファレンス (画面 —識別ID→ 入出力項目 → アクション → 遷移先画面、帳票項目 → 参照先エンティティ・カラム、CRUD = 機能 × エンティティの関係) を裏返すと、暗黙の ER モデルが復元できる構造をしている

そこで、よりどころは目次ではなくモデルに置く:

- **項目の典拠は成果物の系統ごとに一つに絞る**。設計書側の相互参照型の成果物 (画面 ⇔ 入出力項目 ⇔ エンティティ、CRUD) は IPA ガイドの項目定義、要求仕様書側は 29148 (+ Volere) の要求属性。42010 の概念モデルは文書の枠組み (ビューポイント = schema の定義の束、ビュー = 章) を理解する道具として使い、データには持たない — ビューポイント / モデル種別 / ビューは文書の作り方を語るメタ要素で、本ツールでは schema.yaml のエンティティ定義とテンプレートが生成する章がそれに当たる (レコードではなく schema の構成そのもの)。ステークホルダはプロジェクト管理の要素で SRS / SDD には登場せず、関心事は SRS では要求と rationale に化けるので要求と二重になる。ユースケースのアクター (境界の外でシステムと相互作用する役割) はステークホルダとは別物で、上流の独立エンティティとして持つ。1016 のビューポイント名を IPA 由来の内容に被せることもしない
- **モデルの記述場所は showcase の schema.yaml そのもの**。抽出したモデルを別文書に起こさず、スキーマ + x-ref として書き、description に参照元を補記する (「IPA 画面一覧に対応」「29148 5.2.8 の属性」程度)。ビルドすれば `__entity_defs` / ER メタビューがモデルの図を出す — 抽出成果物の置き場問題をツール自身で解決する
- **目次はモデルから導出されるビューの一つ**とみなす。章の並びは 29148 (「編成に万能解はなく合意で決めよ」) も IPA (「工程成果物 ⊂ 設計書、束ね方は各社標準に委ねる」) も自由裁量と明記しており、こちらで決めてよい。標準との対応は章の並びではなく「何が記述され、どう関係づけられるか」の水準で取り、それも conformance ではなく description の典拠注記に留める
- **抽出は網羅しない**。サンプルに必要な範囲へのテーラリング + 突合 (自作スキーマに標準対応を注記し、対応が付かない箇所だけ立ち止まる) で済ませる。IPA の暗黙モデルを忠実・網羅的に抽出するほど二次著作物として翻案禁止条項に近づくため、部分的・自分の言葉での再構成は作業量でも法的にも安全側

#### 典拠と借用の分担

| 資料 | 借りるもの | 転載上の制約 |
|---|---|---|
| ISO/IEC/IEEE 42010 | (採用せず) 概念モデルは文書の枠組みの理解に使うのみ。構成図・クラス図系の Candidates で再検討 | 概念モデル図は公式に無料公開。概念の利用は自由 |
| ISO/IEC/IEEE 29148:2018 | 章立ての素材 (SRS 例示アウトライン 8.5.2) と要求レコードの属性 (5.2.8) | 章題の翻案 + "informed by" 表記は確立した慣行で低リスク。本文の逐語転載・アウトライン図の複製は不可 |
| IEEE 1016-2009 | (採用せず) viewpoint 一覧は調査時のメニューとして使ったが、本 showcase の章には被せない。構成図・クラス図系の Candidates の領分 | 2020 年 Inactive-Reserved (10 年無改訂への管理措置、技術的否定ではない) |
| IPA 機能要件の合意形成ガイド | 各 artifact の項目定義 (画面 5 成果物 / エンティティ一覧・定義 / CRUD 図 等) | 複製許諾は目的限定付きで翻案禁止条項あり。項目名・構成をアイデアとして借り、定義文は自分の言葉で再設計し、出典を明記する |
| Volere | atomic requirement のレコード属性 (fit criterion / rationale / 優先度 等) | 27 節テンプレートのツール同梱・再配布は要許諾 (redistribution license の明記あり)。属性名 subset + attribution に留める |
| OMG ReqIF v1.2 | スキーマ設計原理 (型と値の分離 / 要求実体と文書階層の分離 / 関係自身が型と属性を持つ) | メタモデル概念の利用は自由。仕様文書の転載のみ不可 |

29148 の規範本文 (有償) は購入しない。目次骨格と要求属性は無料の正規プレビューと二次文献で確定でき、規範本文が典拠に要るのは conformance を名乗る場合だけで、"informed by" 方針では不要。

arc42 (CC BY-SA 4.0) は骨格候補として調査したが不採用: アーキテクチャ文書テンプレートで、網羅的な詳細設計 (全画面定義・CRUD・DB 物理) の受け皿が弱く ("relevance 優先、退屈な部品は書くな" が公式ガイダンス)、翻案物への ShareAlike 継承義務も showcase 配布物には負担。

#### 背景: 採らなかった目次とモデルのメニュー

調査で見たが目次に採らなかった要素の目録。借りたものは上表のとおりで、ここに残すのは将来の章 (下記 Candidates) を起こすときの材料。

- **29148 SRS 例示アウトライン (8.5.2)**: 1 Introduction (Purpose / Scope / Product overview / Definitions) / 2 References / 3 Requirements (Functions / Performance / Usability / Interface / Logical database / Design constraints / Software system attributes / Supporting information) / 4 Verification (3 章各節にパラレル) / 5 Appendices。文書セットは BRS / StRS / SyRS / SRS の四層 + OpsCon (Annex A)。IEEE 830 は 2011 年に廃止されこれに統合
- **1016 viewpoint 全 12 種** (調査時のメニュー。本 showcase の章には採用せず): Context / Composition / Logical / Dependency / Information / Patterns use / Interface / Structure / Interaction / State dynamics / Algorithm / Resource。artifact 対応の見立て: Information → ER 図・テーブル定義、Logical → ドメインモデル図、Interface → 画面・API 定義、State dynamics → 画面遷移図、Interaction → 処理フロー、Context → コンテキスト図
- **IPA 6 領域 × 27 工程成果物**: システム振舞い (システム化業務一覧 / 業務フロー / 業務説明 / 共通ルール)、画面 (一覧 / 遷移 / レイアウト / 入出力項目一覧 / アクション明細 / 共通ルール)、データモデル (ER 図 / エンティティ一覧 / エンティティ定義 / CRUD 図)、外部インタフェース (関連図 / 一覧 / 項目説明 / 処理説明)、バッチ (一覧 / フロー / 定義 / 共通ルール)、帳票 (一覧 / 概要 / レイアウト / 項目説明 / 編集定義)。全成果物が共通の書誌メタ (成果物 ID / 名称 / 概要) を持つ。ER 図の表記は IDEF1X、業務フローの表記例は BPMN ベース、システム化業務説明は実質ユースケース記述 (基本・例外シナリオ / 事前・事後条件)
- **要求属性のメニュー**: 29148 5.2.8 (ID / 優先度 / rationale / 検証方法 等) と Volere snow card (fit criterion / customer satisfaction–dissatisfaction / conflicts / originator / history 等)

### showcase/japanese-table-design: テーブル定義から 2 種類のスキーマ図

`showcase/japanese-table-design` がユーザ-land の参照実装。題材は小規模書店の蔵書管理 (5 テーブル / 4 FK) で、スキーマ・データ・description・出力ファイルパスのすべてに日本語識別子を運用している。1 つのテーブル定義から 2 つの図 (テーブル設計図 = `erDiagram`、ドメインモデル図 = `classDiagram`) を描き分ける: 記法の責任分割は下表のとおり括弧入りの SQL 型が `classDiagram` で壊れることに由来し、論理型だけを扱う[メタドキュメンテーション](../20-app/40-meta-documentation.md)は `classDiagram` を採る。

### showcase/system-dev-docs-ja: 要求仕様書と設計書の二文書

単一のデータソースから要求仕様書と設計書を導出する showcase。モデル (schema.yaml) に章 → ソース (この章はどのレコード群のビューか) と エンティティ → 登場章 の対応を張って目次を確定してあり、どの章にも現れないエンティティ、どのエンティティにも支えられない章は無い。モデルの図は `mood build showcase/system-dev-docs-ja` の `__db/__entity_defs` (ER メタビュー) で読める。

#### 位置づけと規約

- **プロジェクト名**: `showcase/system-dev-docs-ja`。本カテゴリ名 + 言語接尾辞。`japanese-table-design` の接頭辞命名は本カテゴリの進展に伴い発展的に廃止する予定
- **二文書を一つのプロジェクトから導出する**。文書別に blueprint を分けると、CRUD マトリクスやトレーサビリティのような文書をまたいで同じレコードを参照する成果物が作れず、「単一ソースから同期した文書群」という製品テーゼの実証が立たない
- **showcase は内容ではなく機構の見本**。作られるべき文書とその粒度はプロジェクト固有で標準化もテンプレ化もできない (だからこそ構造を柔軟に定義できるツールが要る)。showcase の schema はそのまま流用されるものではなく「読んで自分の構造に書き換えるための見本」であり、価値は読みやすさと改変しやすさにある。description の典拠と英名は、その改変の手がかりとして機能する
- **正本は英語、日本語は下書きの作業言語** (docs/ と同じ流れ)。日本の従事者向けに日本語版を製品として残すかは今後判断する。どちらに転んでも手戻りが出ないよう、識別子・enum 値は日本語のまま進め、**英名を schema.yaml の description 末尾に `英名: xxx` の形で付記する規約**にする (enum は値の並び順どおり `英名: kind (a / b / c)`)。英語版の派生は同一ファイル内の置換で済み、`__entity_defs` の表にも英名が出る。命名は既存 showcase に合わせ、トップレベルのエンティティと配列プロパティは複数形、参照は `xxx_id`
- **英語版では章の割り当てが変わりうる**。日本の基本設計 (外部設計) の内容は、29148 の区分ではかなりの部分が SRS 側 (外部インタフェース要求 / 論理データベース要求) に入る。文化差があるのはモデルではなく束ね方なので、英語版を起こすときは schema の改名だけでなく章の割り当ても見直す余地がある
- **blueprint 登録 (`showcase/index.yaml`) は E17 (合成ビュー) を待つ**。当初は「二文書が完成してから」としていたが、章が揃った時点の見た目 (web では章や節が index.md の合本から抜けて別頁になり、二文書の骨格が一頁に見えない) は見本として出すには不格好で、二文書を頁ノードとして立てられる E17 の後に登録する。それまでは `mood build showcase/system-dev-docs-ja` で直接ビルドする (`make ci` の showcase ビルドは blueprint 一覧から回るので、未登録の間は CI 対象外)

#### 参照の向きと層

**参照の向きは下流 (設計書のソース) → 上流 (要求仕様書のソース) のみ**。要求は要求の著者が書き、設計は下流の要員や AI が書いて要求の著者がレビューする、という著者分離を想定すると、上流のデータは下流を知らずに閉じている必要がある (将来プロジェクトを分ける場合も機械的に切れる)。この規律で CRUD (ユースケース × エンティティ) は設計側に置き、用語 ↔ エンティティ の対応もエンティティ側から張る。上流の中にも層があり (ユースケース = StRS 層が上、要求 = SRS 層が下)、要求 → ユースケース の向きはこれに従う。schema.yaml の節構成はこの二段 (上流: 要求 / ユースケース / アクター / 用語、下流: 画面 / エンティティ / データアクセス) で、1016 のビューポイント単位にはしない。

**層の内訳と二文書の境界**。上流 / 下流の二段をもう少し細かく切ると次のとおり。用語 はどの層にも属さない横断要素で、要求仕様書の用語集に置く。

| 層 | 29148 / 1016 での呼び方 | 日本の SI での呼び方 | 本 showcase | 文書 |
|---|---|---|---|
| 業務 | BRS (事業要求)、OpsCon の業務モデル | 業務分析、業務フロー | プロセス、データストア、外部エンティティ、フロー (階層 DFD。S2 で追加中、下記 Proposals) | 要求仕様書 |
| 利用者の視点 | StRS (ステークホルダ要求)、OpsCon の運用シナリオ | 要件定義の業務要件、システム化業務説明 | ユースケース、アクター | 要求仕様書 |
| ソフトウェア要求 | SRS 3.2 Functions ほか (要求文) | 要件定義の機能・非機能要件一覧 | 要求 | 要求仕様書 |
| 外部設計 | SRS 3.1 External interfaces / 3.5 Logical database と SDD の両方に跨る | 基本設計 (画面設計、論理データモデル、CRUD) | 画面、エンティティ、データアクセス | 設計書 |
| 内部設計 | SDD (1016 の Logical / Structure 等) | 詳細設計 (テーブル物理定義、クラス設計) | (対象外。物理テーブルは japanese-table-design) | — |

29148 と日本の基本設計が重なるのは外部設計の層で、重なりが強いのはエンティティ (SRS 3.5 の中身はほぼ論理データモデル)、弱いのが画面 (3.1 が求めるのはインタフェースへの要求で、項目・アクション・遷移の定義は 29148 でも設計寄り)。本 showcase は日本の束ね方 (基本設計 = 設計書) を採る。文化差はモデルではなく束ね方にあるので、英語版で 29148 寄りに束ね直す場合は章の割り当てだけを動かす (上記「英語版では章の割り当てが変わりうる」)。

参照の向きの規律の結果、参照だけで並べると アクター / 用語 → ユースケース → 要求, エンティティ → 画面, データアクセス の順になる。要求と画面 / エンティティの間に直接の参照は無く、ユースケース経由で辿る。トレーサビリティ (要求 ↔ 設計) で設計要素から要求へ直接張りたくなった場合は、規律に従い 画面 / エンティティ → 要求 の向きで足す。

#### 題材

#### 二文書の器 (暫定: index.md の合本、本命: 合成ビュー E17)

**複数のエンティティを束ねる「文書」は、現状 root テンプレート (`index.md`) でしか組めない**。サブテンプレートからはトップレベルの名前空間 (エンティティ / ビュー) が見えず (`node()` は届くので主題の外のデータは読める)、`render` の主題は `this` の子孫に限られる (`_guard_subtree`) ので、「文書」を主題にしたサブテンプレートで他エンティティの章をインライン展開できない。`{% include %}` は root の文脈を共有するため文書ごとのファイルには分けられるが、頁は作らない。

edition 別ルートテンプレート、予約名でデータルートを渡す案、`from: __root` のクエリを検討して退け、**文書をデータ木のノードとして立てる view の第二の文法 = [合成ビュー (E17)](../60-composer/10-query-dsl-spec.md#合成ビュー-e17)** を本命とした (E17 は M13 が前提)。それまでの暫定は `index.md` に二文書を並べ、文書テンプレートを `{% include %}` で取り込む形で、E17 が入ったら殻だけを差し替える。

章は、その章が描くエンティティ / ビュー / prose レコードを主題に取る `render` で書く。**章の内容が単一のコレクションに収まるなら、章専用の view を主題に立てて章を 1 頁に割れる**。割れないのは、内容が複数の view にまたがる章 (4 章の検証) と、文書そのものである。

## Proposals

### S2: 階層 DFD

業務モデル (階層 DFD) を **system-dev-docs-ja の業務層として同梱する**。当初は S7 のモデルに含め、S7 のレビューで独立の showcase に切り出したが、再検討 (2026-09) で同梱に戻した。既存の章と同じく章別の増分で進める (下記「増分の切り方」)。

#### 背景: 独立 showcase から同梱に戻した理由

S7 で外した理由は「業務モデルは BRS の層でユースケースより上流にあり、規律に従うと本体が業務モデルに依存する形になる」だった。読み直すと、ユースケース → プロセス の参照は下流から上流への向きで規律には適合しており、残る違和感は「要求仕様書の本体が付録を参照する」という文書配置のものに過ぎない。配置はテンプレートの問題でデータの層とは別なので、除外の必然は無かった。

同梱で得られるもの (独立 showcase では得られない):

- 「参照の向きと層」の表の業務行が埋まり、BRS → StRS → SRS → 設計 の四層が一つのデータで通る
- ユースケース → 葉プロセス の参照から **システム化範囲** (業務プロセスのうちユースケースに支えられるものと手作業のままのもの) が導出できる。Volere の work context → business events → product use cases と同じ構造で、DFD を変えると範囲の節が同期して変わる、という製品テーゼの実証になる
- エンティティ → データストア の参照が張れる。構造化分析の DFD → データ辞書 → ER の系譜そのもの
- showcase を統合する方向 (japanese-table-design の発展的廃止) と整合する

費用は entity 数で、9 (システム 含む) → 13 になる。古典 Northwind の SQL Server 版と同数で、教材として読まれてきた規模の上限あたり。schema は 業務 / 上流 / 下流 の層で節が切れ、層をまたぐ参照は数本に限られるので、読み手が一度に持つのは一層分 (4〜5 entity) で済む。データストア と 外部エンティティ を 1 つの entity に 種別 で畳んで 12 にする案は、フロー の多態参照が残るうえ読み手の負担が増えるだけなので退けた。Mermaid から PlantUML への舵切りが起きた場合の混在は、コンテキスト図と遷移図も Mermaid なので独立 showcase でも変わらない。blueprint 登録は system-dev-docs-ja と同じく E17 待ちに乗るが、記法リスクの実機検証は登録に依存しない。

#### 背景: DFD の製品動機

DFD は本プロジェクトの製品動機を最もよく体現する artifact でもある。DFD の本質はレベル分割 (コンテキスト図 = レベル 0 → 下位分解) と、親プロセスの入出力フローと子図の入出力が一致するバランシング制約にあり、手描きの図でこの階層整合を維持するコストが DFD を実務から廃れさせた。構造化データ + レベル別自動描画 + ビルド時整合性検査は、この維持コストへの直接の回答になる。

#### 境界: 業務 DFD であってシステム DFD ではない

レベル 0 (コンテキスト図) の唯一のプロセスは **書店の業務** で、端点 (外部エンティティ) は 顧客 / 仕入先 のような業務の外の相手。本システムを唯一のプロセスに置くシステム DFD にはしない。それは設計書 2 章のコンテキスト図 (アクター × ユースケース) の重複になる。

帰結として、以前の案にあった 外部エンティティ ↔ アクター の対応は張らない。店員 は業務の内側で (DFD には役割を描く場所が無い)、顧客 は本システムのアクターではなく、決済サービス は業務から見れば会計プロセスの道具で本システムから見れば外部システム、と二つの境界はずれる。ずれること自体が、業務 DFD がコンテキスト章の重複ではなく情報を足す根拠になる。本システムの境界は、葉プロセスのうちユースケースに支えられるものの集合として (システム化範囲) 導出される。

#### モデル

S7 で立てて削除した素案を起点にする。schema.yaml では 上流 の節の前に 業務 の節を置き、業務層は他の層を知らない (参照はすべて上流 / 下流から業務層へ向く)。

| エンティティ | 主要属性 | 関係 (x-ref) | 典拠 |
|---|---|---|---|
| プロセス | 名前 / 説明 | 親 → プロセス (自己参照。親なし = 業務全体 = レベル 0 の唯一のプロセス。子なし = 葉) | DeMarco / Yourdon のレベル分割, IPA 業務フロー |
| データストア | 名前 / 説明 | — | DeMarco / Yourdon data store |
| 外部エンティティ | 名前 / 説明 | — | DeMarco / Yourdon terminator, IPA 外部システム関連図 |
| フロー | 名前 (流れるデータ) / 説明 | 元 / 先 → プロセス or データストア or 外部エンティティ、親 → フロー (自己参照。上位レベルで束ねられているフロー) | DeMarco / Yourdon data flow, IPA 外部システム関連図の凡例 |

フローは **各レベルで記録する** (葉レベルだけ記録して上位を集約導出する形にはしない)。上位レベルのフローは「入荷情報」のように束ねた名前を持つのが通例で、集約では名前が作れない。代わりに フロー.親 で下位フローが上位フローを指し、バランシングはこの対応の検査になる: 親プロセス P の境界を跨ぐ下位フローは、P を端に持つ上位フローを親に持たねばならず (両端はそれぞれ親フローの端の子孫か同一)、P を端に持つ上位フローは、P が分解されている限り少なくとも 1 本の下位フローに束ねられていなければならない。

スキーマ言語との突合 (S7 で実機確認済み):

- **多態参照 (フロー.元 / 先)**: x-ref の参照先は 1 エンティティ固定なので、`元: { プロセス: ref, データストア: ref, 外部エンティティ: ref }` の 3 択オブジェクトで書く。「ちょうど 1 つ」の制約はスキーマで表現できない (`oneOf` 非対応) ので、バランシングと同じく view + テンプレートによる可視化側で扱う
- **自己参照 (プロセス.親、フロー.親)**: music の `genres.parent_id` と同型で問題なし

他の層からの参照 (第 3 増分):

- **ユースケース.業務プロセス[] → プロセス** (葉)。1 つのユースケースが複数の葉を支え、1 つの葉を複数のユースケースが支える (販売反映 と 保留販売の確認 はどちらも販売の記録) ので多対多、配列で持つ
- **エンティティ.データストア → データストア**。論理データモデルが業務のどの台帳を実装するか

#### 置き場

- **要求仕様書 1 章 (はじめに)**: 業務コンテキスト (レベル 0 の図) と システム化範囲 (葉プロセス × ユースケース の表。ユースケースの無い葉 = 手作業のまま)。29148 の BRS / StRS を 1 章に畳むという既存判断に従う。1.2 Scope / 1.3 Product perspective の位置

全部を付録に置く案 (当初の「付録として書く」) は、1 章の範囲が prose のまま残り、システム化範囲の導出という同梱の主目的が付録の奥に沈むので採らない。ただし決定は第 3 増分の時点で、第 1 増分は付録の図だけを立てる。

#### 増分の切り方

1. **モデル + データ + 付録のレベル別描画** — 完了 (章別 PR 8a)。schema の業務層 (4 entity)、書店の業務の DFD データ (レベル 0 〜 2、プロセス 13 / フロー 50)、分解図 ビュー (子を持つプロセスごとに 1 行) を主題にした付録の 業務モデル 節と分解図ごとの頁。番号 (1、1.2、…) はデータに持たず、親子関係と記述順から再帰マクロで導く。Mermaid flowchart はこの規模 (1 図に 3〜4 プロセス + 6 ノード、20 本の線) では読める図を出した。ラベルの重なりは軽微で、舵切りの判断は保留
2. **バランシング検査** — 完了 (章別 PR 8b)。付録の 業務モデル 節の末尾に「バランシング検査」節を置き、分解図ごとに (a) 境界を跨ぐフローが上位のフローを持ちその両端が対応する (跨いだ側の端が親プロセス、反対側の端が同一か一段上)、(b) 図の中で閉じるフローが上位のフローを持たない、(c) 親プロセスの入出力がすべて図の中のフローに束ねられている、を確かめ、加えて元 / 先 が 1 つの相手に定まることを確かめる。不一致は 図 / フロー / 不一致 の表、無ければ一致の一文。view は立てない: 規則は行を跨ぎ階層を辿る述語で view 言語の where / join では書けず、主題は既存の 分解図 ビュー (行 = 図) で足りる。データストアは業務の内側にあってコンテキスト図に現れず、下位の図で初めて描かれることもある (構造化分析の規則: 複数のプロセスが共有する最下位のレベルで描く) ので、データストアとのフローが上位のフローを要するのは、そのデータストアが上位の図に描かれているときに限る。「図の中」の判定は描画と同じ規則 (端のプロセスが子) で、レベルをまたぐプロセス間のフローは描画・検査とも想定しない。ビルド時の警告化はツール側の検討事項 (下記) に起票
3. **他の層からの参照と 1 章**。ユースケース → プロセス、エンティティ → データストア の参照を足し、1 章に業務コンテキストとシステム化範囲の節を立てる。「エンティティ → 登場章」と二文書の目次の表はこのときに更新する

#### 検討項目

- Mermaid flowchart の適合性: 第 1 増分の図は読めたが、flowchart は「手描き向き」 (構造化データから自動レイアウトしにくい) と評価しており、PlantUML 等への舵切りトリガとして第一候補のまま。図が大きくなる場合 (分解の深い業務) の評価は未了

### S7 / S8 で表面化したツール側・将来の検討事項 (未起票)

showcase の設計対話で見つかったが、showcase タスクの範囲外として起票を保留しているもの。起票先はツール本体のタスクか本ファイルの Candidates。S8 で表面化した合成ビューは E17 として起票済み (前提は M13)。

- **`{% include %}` / `{% import %}` の文書化**: 動くが `docs/reference/template.md` に記述が無い (template-trust-model の loader の節で触れているのみ)。root テンプレートの分割手段 (include) と、テンプレート間でマクロを共有する手段 (import。S2 の 業務マクロ.md で実機確認、再帰マクロも動く) として記述する。小さな docs PR
- **string 配列への x-ref**: `items: { type: string, x-ref }` を許す拡張。現状はオブジェクト配列に包む
- **入れ子要素への x-ref**: x-ref はエンティティの ID しか指せず、エンティティ配下の 属性[] の要素は指せない。画面.入出力項目.参照先.属性 と エンティティ.属性.参照.属性 は素の文字列で、属性名の綴り違いはビルドで検出されない。親 ID + 子要素の名前 (複合キー) を指す x-ref の拡張か、S3 / S4 で view による突合を検討する
- **上流プロジェクトの参照 (依存)**: 要求を発注者側、設計をベンダや AI のリポジトリで持つ運用では、別プロジェクトの entity を読み取り専用で x-ref の対象にし、版を固定する機能が要る。参照の向きの規律はこの分割を可能にする前提
- **suspect link (要確認リンク)**: 要求に版を持たせ、設計側の参照が設計時の版を持てば、要求変更で古くなった設計要素をビューで導出できる (新規要求の孤児検出と対)。S6 (トレーサビリティ) の増分で載せる候補。多対多で強いられた `{ID, 版}` のオブジェクト配列の形がそのまま使える
- **スコープ管理と FP 概算**: 要望一覧 / リリース計画 / FP 概算は別の文書群ではなく、同じレコードのスコープ確定前の姿 (要求・ユースケースに状態と対象リリースを持たせ、二文書は「採用」の部分集合を描くビュー)。FP が数える要素 (論理ファイル = エンティティ、トランザクション = 画面のアクション・外部インタフェース) は本 schema にあるので概算はビューで導出できる。showcase の範囲外 (showcase はスコープ確定後の文書を描く) だが製品動機に近い
- **プロジェクト管理成果物の showcase**: ステークホルダ登録簿や RACI など PMBOK 系の成果物は「表を構造化データから導出する」題材として筋が良い
- **ja / en 変種の構造同一性テスト**: 日本語版を製品として残す場合、名前を除いて schema の形が一致することを検査する仕組み
- **同じ subject を二度 render すると subject の anchor が二重に出る**: 一時期あった設計書の機能一覧が要求仕様書の主要機能と同じ `ユースケース | render(...)` で、一ページ (index.md) に `<a id="/ユースケース">` が 2 つ出た。ビルドは通り (`--strict` でも警告無し) リンクは先勝ちで着地するが、HTML の id 重複ではある。同じコレクションを二章で描く構成では起こりうるので、ツール側で 2 つ目以降を抑止するか警告するかを検討する
- **anchor の所在とリンクの向き先の食い違いを検出できない**: リンクの向き先の頁はデータ上の位置で決まるので、`node()` で引いたノードを別の頁 (split された他レコードの頁) に `| anchor` で描くと、anchor はそこに出るのにリンクは home の頁を指す。ビルドは通り `--strict` も警告しない (3b で実機確認。定石は join view)。anchor が home 以外の頁に出たら警告する検査があると、この取り違えを早く引き当てられる
- **マクロの戻り値の再エスケープ**: autoescape を切っているので Jinja マクロの戻り値は素の文字列になり、`{{ macro() }}` で呼ぶと `link` の出力までエスケープされる (PR 5 で実機確認)。症状は docs の Markdown escaping の節から辿れ、`| safe` か `{% set %}` で回避できるが、同節は `| safe` をコードスパン / フェンス / Mermaid の話として書き、`link` 等は「`| safe` 不要」と明記しているので、マクロ経由だと要るという例外が読めない。同節に一行足す (小さな docs PR)
- **コードフェンスの中のリンクが HTML 版で外れる**: Mermaid の `click` に `href` の URL を埋めると、出力 Markdown では正しいのに、コードフェンスの中なので Markdown から HTML への書き換えが効かず、`.md` のまま残って HTML 版で 404 になる (PR 2 で実機確認)。図の中からのリンクは現状どの図法でも張れない。図が大きくなる章 (4 の画面遷移図) でも効いてくるので、フェンス内の URL を edition に合わせて解決する手立て (専用フィルタ等) を検討する余地がある
- **テンプレートが見つけた不整合をビルドの警告に載せる経路**: S2 のバランシング検査は付録の表として可視化するだけで、ビルドは通り `--strict` も止まらない。データの整合性規則のうちスキーマ (x-ref、`oneOf` 非対応の「ちょうど 1 つ」) で言えないものを view やテンプレートで検査する形は他の章 (属性名の突合など) にも広がるので、テンプレートから D7 の警告インフラに載せる手立て (例: 警告を発するフィルタ / 関数で、`--strict` なら失敗させる) を検討する
- **空の contents / views ディレクトリ**: 無いとビルドが失敗するため `.gitkeep` で保持している。無くても通る方が親切
