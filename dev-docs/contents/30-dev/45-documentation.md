置き場ごとの読者と、何を書き、何を書かないかの規約。情報の種類ごとの正本の対応表は `DEVELOPMENT.md` の「ドキュメント」節が持つ。

## `docs/`

[Diátaxis](https://diataxis.fr/) に従い、`reference/` は reference、`guides.md` は tutorial / how-to / explanation として書く。素 Markdown。人間の可読性と、読んだ LLM の振る舞いの双方が UX に直結するため、品質に妥協しない。書かれたことは外部仕様の正本（利用者との契約）としても扱われるが、それは帰結であって執筆の目的ではない。

`reference/` に書くのは約束の層だけ。利用者の関心の外にある精密な規則は `dev-docs/appendix/` に置き、reference を利用者が読める量に保つ。

## `dev-docs/design/`

design は作業に入る前に読む導線として書く。読者が、破ってはいけない設計を知り、次に開く正本を決められれば役割を果たす。読む量が増えるほど導線として機能しなくなるので、本文に置くものを絞る。

各ファイルは以下の 3 セクション構造（該当があるもののみ）:

- `## External Design` — 利用者から見える振る舞いの設計。振る舞いの約束そのものは `docs/reference/` に書き、ここには書かない
- `## Internal Design` — 内部実装の設計。書くのは、各部分が責務として隠している決定と、守るべき不変条件まで。その中でどう動くか（局所的な機構）はコードが正本で、書かない
- `## Proposals` — 未実装機能（task に対応）

### 本文に置くもの

設計そのもの（成果物）: 構造、不変条件、契約、複数モジュールに跨る機構と、それぞれの意図を示す一文。

深さの判別は「コードがここから外れたとき、バグか、リファクタか」。バグなら本文に置く。リファクタならそれより深いので、本文には置かない。

意図の一文は設計と同じ場所に書き、別の体系（ADR 等）で索引しない。設計と意図が同じ場所にあれば、設計の変更時に意図も目に入り、更新漏れが起きにくい。

### 本文から外すもの

設計に至った過程（比較調査、却下案、経緯、検討中に出た未起票の候補）と、約束の外側の精密な規則は、`dev-docs/appendix/` の同じ位置に置き、本文からリンクする。成果物であっても、変更前に読む必要のない深さのものは同様に外す。

### Proposals のライフサイクル

検討メモは実装完了時に削除する（部分実装なら残る検討事項のみに絞る）。維持価値のある設計は External / Internal Design 節に移し、過程は appendix か PR 本文で残す。

## `dev-docs/appendix/`

design / dev の付録。ディレクトリ構成は design / dev の鏡写しで、本文の各ファイルに対応する位置に置く。内容は二種類:

- **過程のログ** — 比較調査、却下案、経緯、未起票の候補。本文の設計がなぜこの形になったかを後から辿るためのもの
- **精密な規則** — 約束の外側で実装が満たすべき正確な条件と、その理由。安定させる意図はあるが契約ではなく、変更はリリースノートの義務を生まない

appendix は本文からのリンクで到達する。appendix だけを読んで作業に入ることは想定しない。

## `dev-docs/background/` と `dev-docs/dev/`

> **[W4 dup]** ↔ 系統表 (同一ファイル内、完全)。案: 削除

background は製品ビジョン・ロードマップ・タスクカタログで、開発判断の根拠を置く。dev は開発規約・手順の正本で、簡潔・規範的に書く。`DEVELOPMENT.md` は dev の要約とポインタであり、規約の本文は dev に置く。

## インデックスの更新

ドキュメントを追加・削除・移動した場合、プルリクを上げる前に以下のインデックスからのリンクを確認・更新する:

- dev-docs の `index.md`（ビルド出力 `.another-mood/dev-docs/output/web/index.md`）— dev-docs 全体インデックス
- `docs/index.md` — 利用者向けトップ
- `docs/catalog.yaml` — MCP 公開対象のカタログ
- `DEVELOPMENT.md` — 開発者向けポインタ
