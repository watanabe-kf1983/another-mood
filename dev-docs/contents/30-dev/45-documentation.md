# ドキュメントの書き方

置き場ごとの読者と、何を書き、何を書かないかの規約。情報の種類ごとの正本の対応表は `DEVELOPMENT.md` の「ドキュメント」節が持つ。

## 系統

ドキュメントは四系統で管理する。`dev-docs/` の三系統は Another Mood 自身で管理する:

| 系統 | 内容 | 読者 | 言語 |
|---|---|---|---|
| `docs/` | 利用者向け文書。実装済み機能のみ | 利用者（人間と LLM） | 英語 |
| `dev-docs/concept/` | 製品コンセプト（ビジョン、核となる設計判断）。開発判断の根拠 | 開発者 | 日本語 |
| `dev-docs/design/` | 内部構造の地図と、コード全体が守る約束 | 開発者 | 日本語 |
| `dev-docs/dev/` | 開発規約・手順の正本（セットアップ / 環境 / チェック / スタイル / リリース）。簡潔・規範的に書く。`DEVELOPMENT.md` はその要約とポインタ | 開発者 | 日本語 |

## `docs/`

[Diátaxis](https://diataxis.fr/) に従い、`reference/` は reference、`guides.md` は tutorial / how-to / explanation として書く。素 Markdown。人間の可読性と、読んだ LLM の振る舞いの双方が UX に直結するため、品質に妥協しない。書かれたことは外部仕様の正本（利用者との契約）としても扱われるが、それは帰結であって執筆の目的ではない。

`reference/` に書くのは約束の層だけ。利用者の関心の外にある精密な規則は書かず（コードと fixture テストが持つ）、reference を利用者が読める量に保つ。

## `dev-docs/design/`

design は、作業に入る前に読む地図として書く。読者が、何がどこにあり、どうつながっているか、何を破ってはいけないかを知り、次に開くコードや正本を決められれば役割を果たす。読む量が増えるほど地図として機能しなくなるので、置くものを絞る。

各ファイルは以下の 2 節構造（該当があるもののみ）:

- `## External Design` — 外部の要求から導かれ、コード全体が守る約束。要求そのもの（`dev-docs/concept/` や `docs/reference/`）へのリンクを添える
- `## Internal Design` — 導線（地図）と、地図を保つ約束

どちらの節の約束も、破る変更が一つのファイルに決まらないものに限る（決まるものの行き先は下の「置かないもの」）。

### 導線と、地図を保つ約束

- **導線（地図）** — 何があり、それぞれが何を担い、何が何に渡るか。語彙、ステージ、コンポーネント、どの概念をどこが持つか。中身を言い直さず、コードのパスや正本を指す
- **地図を保つ約束** — 破られると地図が実態とずれる不変条件。地図の、それが保つ箇所に添えて書く（例: 「ステージはファイルを介してつながる」に「コンポーネントは互いを import しない」を添える）

意図の一文は、地図や約束と同じ場所に書き、別の体系（ADR 等）で索引しない。同じ場所にあれば、変更時に意図も目に入り、更新漏れが起きにくい。

### 置かないもの

| 中身 | 行き先 |
|---|---|
| 機構（それをどうやっているか） | コード |
| 要求そのもの | `dev-docs/concept/` か `docs/reference/` |
| 開発の進め方の約束 | `dev-docs/dev/` |
| 一箇所に閉じた判断で、外部の要求に理由があるもの | 利用者から見える入出力で確かめるテスト（fixture テスト等）。テスト名を判断そのものにし、理由をコメントに一文添える |
| 一箇所に閉じた判断で、内部の都合によるもの | 破る変更が起きる箇所のコメント |
| 経緯（比較調査、却下案） | PR 本文（main の squash コミット本文として残る） |

外部の要求に理由がある判断をテストに置くのは、内部の関数を叩くテストでは、内部を作り直したときにテストごと書き直され、判断が黙って失われるため。利用者から見える層のテストは、作り直しの後も同じ形で残る。

### 境界の見分け方

- **導線か機構か** — その記述が古くなるのは、構造を変えたときか、リファクタしたときか。構造の変更でしか古くならないなら導線、リファクタで古くなるなら機構。モジュールの境界をまたぐ事実は導線になりやすいが、またいでいても「どうやるか」は機構（例: ステージ間をファイルで受け渡すのは導線、hardlink で渡し、張れなければ copy に戻るのは機構）
- **約束をどこに置くか** — 破る変更が一つのファイルに決まるなら、design には置かず、上の表のテストかコメントに書く。決まらないもののうち、地図のどの部分を保つかを言えるなら Internal Design、外部の要求に辿れるなら External Design。コードではなく開発の進め方についての約束なら `dev-docs/dev/`

## インデックスの更新

ドキュメントを追加・削除・移動した場合、プルリクを上げる前に以下のインデックスからのリンクを確認・更新する:

- dev-docs の `index.md`（ビルド出力 `.another-mood/dev-docs/output/web/index.md`）— dev-docs 全体インデックス
- `docs/index.md` — 利用者向けトップ
- `docs/catalog.yaml` — `mood docs` が配るドキュメントのカタログ
- `DEVELOPMENT.md` — 開発者向けポインタ
