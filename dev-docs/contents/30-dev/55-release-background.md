# リリースフローの設計背景

[リリースフロー](50-release.md)の規律を確定した検討
（[Q6](node:/tasks/Q/tasks/Q6) / [Q11](node:/tasks/Q/tasks/Q11)）のうち、
維持価値のある設計判断の記録。

## 大枠の判断

- **「main マージ = リリース」にしない**: 互換リリースは任意のタイミングで打てる。
  破壊リリースは「破壊的変更を出す」という決断そのものが契機であり、自動化する
  余地がない
- **Git Flow を採らない**: 選択的取り込み（破壊的変更を除いてリリースを切る）を
  構造では解けず、常設ブランチの維持コストだけが残る。旧系列への修正需要
  （= 破壊的変更を越えて上がれない利用者）はローンチ前にはほぼ定義上存在しない。
  規律が払えないコストになったときの構造的解は Git Flow ではなく、sbdb_version
  対応集合の複数世代並行サポート
  （[sbdb-manifest](node:/prose/20-design/20-app/60-sbdb-manifest) に YAGNI として
  保留済み）
- **二相構造「PR が置き、リリースが消化する」**: リリースに要る判断と記述はすべて、
  文脈が最も新鮮な PR 時点で置く。リリース時はその消化だけで、判断も、コミットも、
  役割による手順の分岐も残らない——破壊/機能/修正の差は「PR が何を置くか」に全部
  畳まれている
- **機能/修正の副分類は桁選択専用**: リリース手順もリリースノートの扱いも分けない。
  判定の一次入力はトレーラーのマーク、バックストップはリリース手順 1 の検算
  （機能追加は docs 同期が義務なので仕様差分を必ず残す）。賭け金は桁一つなので
  検査機構は建てない。写像表を隔離するのは、1.0.0 で桁の対応が滑っても更新が
  表一つで済むようにするため。0.x 期の「0.MINOR を破壊的変更に予約する」は
  Cargo 系エコシステムの事実上の標準

## 破壊的変更のゲート構造

破壊的変更は外部仕様の正本（docs/reference）の編集を必ず通る——文書化されていない
挙動は契約外（仕様が契約。厳格パースが最終防衛線）。ゆえに非互換注記の規律が検問を
張り（破壊的編集は、注記か「注記を書くべき既存仕様の書き換え」を必ず自身の diff に
含む）、残余リスク（作者が破壊に無自覚なままマージする）には既存機構——fixture
スイート（期待値コミット済みの golden テスト）、showcase / dev-docs のビルド、
manifest ゲート、全 PR のレビュー——が命綱になる。常設装置は lint ワークフロー
（T4）一本に留め、「内容が破壊的かどうか」の意味判定には踏み込まない。

lint の世代側トリガを fail にしないのは、CI がマージ画面で編集される最終 squash
本文を検査できず、「マージ時に PR 本文へ足す」という正規の回復経路が CI の可視範囲の
外にあるため——fail の保証は見かけより弱く、摩擦だけ確実に増える。世代宣言ファイルの
diff 検知は「集合からの世代脱落」（破壊の定義）の保守的近似で、単一世代レジームでは
実質等価、誤るとしても過剰発火の側にしか誤らない。

lint に建てなかった装置と、建てる契機:

- **世代チェックの集合比較化**（ファイル diff 検知を、両端点から対応集合を抽出して
  脱落を検知する方式に格上げ）— 複数世代並行サポート解禁のとき
- **世代側注意喚起の fail 格上げ** — 外部コントリビュータを受け入れたとき
- **「docs/reference に diff ∧ トレーラー無し」の fail 格上げ**（トレーラー宣言の
  義務化。kind 自体は作者選択のまま）— 1.0.0 で feature / fix の桁が分かれ、
  賭け金が生まれたとき
- **差分ハーネス**（merge-base 時点の showcase + dev-docs ソースに旧新両版の mood を
  かけ、出力 diff を Warn として PR に提示）— 外部コントリビュータを受け入れて
  全 diff を精読しなくなったとき、または最初の silent 破損事故が起きたとき

Q11 検討時の候補の顛末: 検査 job は突き合わせ範囲で採用、PR テンプレの自己申告は
外部コントリビュータ向けの面として [Q7](node:/tasks/Q/tasks/Q7) へ送付（全 PR に
発火して precision が低く、`gh pr create --body` はテンプレを適用しないため内部
運用には効かない）、AI レビューは不採用。

## versioning 方式の選定（B: hatch-vcs）

四択の比較:

| | 方式 | フラグの所在 | リリース時の版作業 |
|---|---|---|---|
| A | 静的 + リリース時 bump | ラベル or 世代番号 diff | bump コミット |
| **B（採用）** | hatch-vcs（git tag から動的導出） | 世代番号・非互換注記の diff | なし（tag のみ） |
| C | 静的 + 常時 `.devN` 仮宣言 | pyproject そのもの | `.dev0` 剥がし |
| D | release-please（レールに乗る） | conventional commits | なし（Release PR をマージ） |

各方式の差は「破壊的か否かをいつ判断するか」ではなく「判断の保存場所」にある。
判断を文脈が最も新鮮な PR 時点で行うのはどの流派も共通の実践で、本プロジェクトでは
in-tree の構造側フラグ（世代番号・非互換注記）が既にその保存場所を務めている。
すると版番号は（前回 tag, in-tree フラグの diff, いま出すという裁量）から機械的に
導出できる値になる。導出可能な値は正本から導出し、手書きの複製を持たない——
本プロジェクトの製品テーゼを版管理自身に適用したのが B。

落選理由:

- **C**: `.devN` 仮宣言の携行は「main の版宣言は常に正しい」という義務であり、
  義務は検査を要求する——tag⇔pyproject 一致検証、仮宣言・上書き規律の検査、
  仮宣言遅延（この間 main の版が嘘をつく）を塞ぐ自動化、と装置が運用側に生え続ける。
  しかも携行される宣言は in-tree フラグから導出可能なビューの手書き複製で、要求される
  整合検査は複製の同期検査にほかならない。設営コストゼロと引き換えに自前の規律 + 門を
  恒久に払う分割払いであり、既製で枯れた設営を一回払う B に総負担で劣る
- **D**: 解く問題——bump 判断の分散（多人数）、リリース統治（マージ = 承認フロー
  通過）、艦隊規模（多リポジトリの無人リリース）、多ファイル版整合——がどれも
  本プロジェクトに存在しない。対価（conventional commits の恒久規律 = 全コミットに
  義務のメタデータ埋め込み）だけが残り、`feat!` ⇔ 世代 +1 の整合もレール外
- **A**: 常時仮宣言がないぶん main の版番号が嘘をつき、bump コミットも残る。
  B は両方を消す上位互換

導入設営の実機検証で確認済みの点: 変則 tag（`v0-ts-baseline` 等）が既存のままでも
`v0.1.0` が正しく拾われ `0.1.1.dev1+g...` と導出される。sdist は解決済み版番号を
PKG-INFO に埋めるため .git のない環境でもビルド可。uv.lock は動的版を版固定から省く
（uv 0.5.19+）ためコミットごとの churn は起きない。

運用上の含意:

- tag の打ち間違いは、トレーラー（意図側の第二宣言）との突き合わせで受ける。
  リリース手順 1 で番号を「考案せず導出する」こと自体が照合で、機械化
  （tag sanity check）は打ち間違いが実際に起きるまで保留
- 開発ビルドの版番号 `0.1.2.dev3+g1a2b3c4` の「次版」部分は最下位桁 +1 固定の推測で、
  破壊的 PR マージ後も実際に予定される次版（破壊リリースの桁）を反映しない。
  表示のみの問題で実害はない

## リリースノートの三層整理

リリースノート欄には性格の異なる三層が同居する。要求水準は層ごとに違うが、
運搬機構は二つしかない: 台帳は自動生成、オマケとラベルは Release-Highlight
トレーラー（旗）と PR 本文の `## Release highlight` セクションが PR マージから
Release まで運ぶ。

- **台帳**（自動生成の What's Changed）: 人間向けの伝達価値は薄いが、機械経路——
  Releases ページの本文検索（PR 番号 → 収録版の逆引き）、Renovate / Dependabot が
  bump PR へ行う本文転載、API / LLM エージェントの参照——のためのデータとして
  維持する。正本は git の DAG で、これはその導出ビュー。生成部は手で編集しない。
  ラベル別の節分け（`.github/release.yml`）も置かない——設定自体は数行だが、
  節分けの入力は PR ラベルであり、宣言チャネルとして棄却したものを毎 PR に付ける
  義務が復活する。整合を誰も検査しないトレーラーとの二重宣言になるうえ、読み手が
  人間でない層に可読性を投資することにもなる。外部向けの体裁格上げ判断は
  [Q7](node:/tasks/Q/tasks/Q7)
- **オマケ**（告知ハイライト）: 約束しない。書くかどうかは恣意であり、基準は
  立てない——基準を立てれば義務になり、義務は検査を要求する（C の落選と同じ論法）
- **ラベル**（義務）: 破壊的リリースの Release 冒頭には移行手順が載る。ただし正本は
  リポジトリ内の docs で、書くのは破壊的 PR 自身。義務の錨は PR 側にあり、リリース時の
  動作はオマケと同一——トレーラーの収集結果を貼るだけ

版番号は伝達行為であって機械的真実ではない（破壊なしに major を上げるのも違反では
ない）。ゆえに kind は検知結果ではなく「次の桁をこう動かしたい」という意図宣言で、
トレーラーはその行使時点を文脈が最も新鮮な PR 時へ移す搬送機構。kind の集合は
tag（正本）に対する意図側の第二宣言として、打ち間違いの照合先を兼ねる。次版番号
そのものを書かないのは、kind から三値の max で導出できる値の手書き複製になるため。
feature / fix を義務化しないのは、書き忘れの実害が「機能リリースを修正番号で出す」
（0.x 期は無差、1.0 以降も桁一つ）に留まり、検査装置を建てるほどの賭け金がないため。

## トレーラー搬送路の選定

squash マージ設定は `PR_BODY` + `PR_TITLE`、マージ方式は squash のみ。
PR 本文が squash コミット本文へそのまま
流れ、トレーラーは main の履歴に in-tree で残り、行頭 grep で収集できる。トレーラーは
PR 粒度の宣言であり、住所は squash コミット（= PR 粒度の器）。PR 本文は、記入面・
レビュー面・搬送路がその住所に一致する唯一の媒体。merge commit / rebase を無効化した
のは、他方式でマージすると PR 本文が履歴のどこにも載らず、トレーラーが収集から無言で
漏れるため。

収集に git の trailer 解析（`%(trailers:key=...)`）を使わないのは、それがメッセージ
最終ブロックしか読まないため——squash 本文は連結で構成され、GitHub が末尾に区切りと
`Co-authored-by` を自動付加するので、トレーラーが最終ブロックに残る保証がない
（実機確認済み）。行頭 grep は位置に依存しない。git log の範囲指定が「前回 tag 以降」
だけを返すので、鮮度管理・消し込み・共有ファイルのコンフリクトという問題群は機構ごと
存在しない。

もう一つ実機確認で得た事実として、GitHub はマージ時に squash 本文を約 72 桁で
折り返す。トレーラーを kind 単独の短行に固定した理由の一つがこれで（本文付きの
長行は折り返しで分断され、行頭 grep が尻尾を失う）、ハイライト本文のコピペ元として
PR ページ（折り返しのない原文）を案内するのも同じ理由。

棄却した代替:

- **GitHub の PR ラベル**（`breaking`）— git 履歴に残らず、収集が API 依存になる
- **ブランチコミットメッセージ末尾**（当初採用）— COMMIT_MESSAGES 設定で squash
  本文へ流れはするが、連結の中で位置的に埋まり trailer 解析から漏れる。かつレビューは
  コミットメッセージを読まない（レビュー面は PR の diff と本文）ため、義務層の宣言が
  レビューの視界に入らない。搬送の都合で記入面がコミット側へ逆流した案であり、
  宣言の粒度とも一致していなかった
- **in-tree の走り書きファイル**（`RELEASE_NOTES.next.md` を携行しリリースで
  消し込む、towncrier 断片系の変種）— 消し込みが所有者と契機のない掃除として
  残り続け、並行 PR のコンフリクト磁石になる。トレーラーは git log の範囲指定が
  鮮度管理を定義上済ませる。代償は文言の後編集不可（リリース時の整形で吸収）と
  繰り越しの手動化（オマケは無約束層なので許容）
- **PR タイトルへの CC 風前置**（`fix: ...` 等）— 収集はタイトル行の grep 一本に
  潰れて操作面では優るが、表面が conventional commits と同一になり、履歴が
  「大半のタイトルに前置のない、守られていない CC」に見える。「沈黙 = 告知なしの
  正当な表明」という中核の意味論が見た目から読めず、全数義務へ揃えたくなる圧を
  恒久に受ける。タイトルの本務（変更の説明）に機械向けメタデータが相乗りする点も
  CC と同じ
- **トレーラーの一行本文**（`Release-Note: feature: mood tap outputs JSON`、
  当初案）— 短い告知は PR タイトルの複製になり（導出可能な値の手書き複製）、
  長い告知は一行に収まらない。挟み撃ちで存在理由が消え、72 桁折り返しによる
  分断リスクだけが残った。見出しは PR タイトル、長い説明は `## Release highlight`
  セクション、と分担して解消
- **conventional commits** — D 案の対価と同じ（レール入力としての強制規約。
  全コミットが従い、機械がパースし、違反がリリースを壊す）。トレーラーは裁量の
  告知チャネルで機械は読まず、設計判断の背景を main の squash コミット本文に残す
  本リポジトリの文化の延長にある。最大の差は「沈黙が正当な状態」であること——
  CC では無印が違反だが、トレーラーの不在は「告知することなし」の正しい表明。
  breaking の正本も in-tree フラグのままで、`feat!` との二重宣言整合という
  所有者のいない検査を作らない

## 背景: リリース手順に建てなかった装置と、建てる契機

手順（読む・打つ・貼る）は 5 分で回る軽さを目標とし、自動化は必要が現れてから足す。

- **tag sanity check**（ワークフロー冒頭で tag を kind の最高位と突き合わせ）—
  tag の打ち間違いが実際に起きたとき。導出自体が照合として働くことは versioning 節に既述
- **Release 本文へのトレーラー自動転記**（手順 3 の貼り付けの機械化）— 手作業が
  煩わしくなったとき。ハイライトは無約束層なので、貼り忘れは違反にならない
- **自動 tag**（トレーラーを読んで機械が tag を打つ）— リリース頻度が裁量判断を
  上回ったとき。「リリースの契機は裁量」が前提から外れることと同義

なお squash 本文の正本が PR 本文になることに伴い、設計判断の背景の記録先も
ブランチコミットのメッセージから PR 本文へ移した。
「設計の背景が main のコミットメッセージに残る」という不変条件は保たれ、記入面が
変わるだけ——連結された WIP コミットの箇条書きより、PR 時点で統合された一本の
文章のほうが履歴としても読みやすい。
