# リリースフロー

[Q6](node:/tasks/Q/tasks/Q6)（手順の明文化）/ [Q10](node:/tasks/Q/tasks/Q10)（ワークフロー実装）の検討メモ。
実装完了時にチェックリスト本体へ置き換える。

## 決定事項（大枠）

- **main は trunk のまま、リリースは別イベント**。「main マージ = リリース」にはしない。
  リリースは version 確定 + git tag push であり、tag push を契機に GH Actions が
  build → PyPI publish（trusted publishing）→ GH Release 作成を行う
- **バージョニング**: リリースは役割で分類する——一段目は破壊/互換の二値、互換の内側に
  機能/修正の副分類。破壊 ⇔ フォーマット世代 +1 の 1:1 対応（[sbdb-manifest](node:/prose/20-design/20-app/60-sbdb-manifest)
  の世代台帳が判定の照合先）。役割から版番号の桁への写像は次表に隔離し、本ファイルの
  他の記述はすべて役割語で書く（1.0.0 で桁の対応が滑っても、更新はこの表だけで済む）:

  | 役割 | 0.x 期（現行） | 1.0.0 以降 |
  |---|---|---|
  | 破壊 | 0.MINOR+1 | MAJOR+1 |
  | 互換・機能 | 0.x.PATCH+1 | MINOR+1 |
  | 互換・修正 | 0.x.PATCH+1 | PATCH+1 |

  0.x 期の対応は「0.MINOR を破壊的変更に予約する」慣習（Cargo 系エコシステムの
  事実上の標準）。機能/修正の副分類は桁選択専用で、チェックリストの経路も
  リリースノートの扱いも分けない。判定の既定値は「前回 tag 以降に docs/reference の
  仕様差分があれば機能、なければ修正」（機能追加は docs 同期が義務なので仕様差分を
  必ず残す。文言のみの編集は裁量で修正扱いにしてよい）。賭け金は桁一つなので
  検査機構は建てない。0.x 期は番号に現れないため判定自体が不要。
  1.0.0 はローンチ（[Q3](node:/tasks/Q/tasks/Q3)）で刻む
- **版宣言の正本は git tag ただ一つ**（方式 B: hatch-vcs、選定理由は下記
  「versioning 方式」）。pyproject の version は dynamic 化して tag から導出する。
  bump コミットと tag⇔pyproject 一致検証というエラークラスを最初から持たない
- **リリースの契機は裁量**（少なくともローンチまで）。契機は役割で二層に割れる:
  互換リリースは世代作業・移行手順が不要で原理的に安く、任意のタイミングで打てる。
  破壊リリースは「破壊的変更を出す」という決断そのものが契機であり、自動化する余地がない
- **ブランチモデルは trunk-based 維持、Git Flow は採らない**。Git Flow は選択的取り込み
  （破壊的変更を除いてリリースを切る）を構造では解けず、常設ブランチの維持コストだけが残る。
  旧系列への修正需要（= 破壊的変更を越えて上がれない利用者）が実際に発生したら、
  過去 tag から遡及ブランチを切って cherry-pick する（`git switch -c release-0.X v0.X.Y`）。
  需要はローンチ前にはほぼ定義上存在しない
- **破壊的 PR のマージタイミング**: 破壊的 PR をマージすると、以後の main からは
  互換リリースが打てなくなる（破壊リリースを仕上げて出すか、遡及ブランチに頼る）。
  「次のリリースを破壊リリースにする覚悟ができたときにマージする」を習慣とする。
  規律が払えないコストになったときの構造的解は Git Flow ではなく、
  sbdb_version 対応集合の複数世代並行サポート（sbdb-manifest に YAGNI として保留済み）

## チェックリスト骨格（ドラフト）

前段の判定ブロック → 版種別の経路、という構造。

```
■ 前段（毎回共通）
1. git log <前回タグ>..HEAD で変更を棚卸し
2. 破壊的変更の有無を判定 → 無ければ互換経路 / 有れば破壊経路

■ 互換経路（5 分で回る軽さを目標）
3. version 確定（役割 → 桁は写像表） → showcase / dev-docs の minimum_version 更新
4. tag push → ワークフロー完走・PyPI 反映の確認

■ 破壊経路（互換経路 + 以下）
3'. sbdb_version +1: コードの対応集合更新 + 世代台帳への追記
    （破壊的 PR 自身が済ませているはず — 下記フラグ管理）
4'. 移行手順をリリースノート冒頭に手書き
5'. scaffold 生成物の sbdb_version 追随
```

注意: showcase / dev-docs の minimum_version を未リリース版へ上げてよいのは
リリース時（手順 3）のみ。開発環境の自己申告版は `0.1.2.devN+g...` 形式で、
PEP 440 では dev 版 < リリース版のため、feature PR が先に minimum_version を
上げると手元の manifest ゲートが落ちる。

## 破壊的変更フラグの管理

「前回リリース以降に破壊的変更がマージされたか」をリリース時にどう知るか。
判定を PR マージ時点（文脈が最も新鮮）に前倒しし、リリース時は機械的照会に潰すのが方針。

- **世代番号 in-tree**: 破壊的 PR は定義上フォーマット世代を上げる PR であり、
  対応集合・世代台帳の書き換えを自身に含む。よって「コード内の世代番号が前回 tag から
  変わったか」の diff 一発で判定できる。フラグを立てる行為と破壊的変更が同一物なので
  貼り忘れが構造的に不可能
- **隙間**: フォーマットを変えないが利用者を壊す変更（CLI フラグ廃止等）は世代が動かず
  ツリーに現れない。PR ラベル（`breaking`）を保険で併用するか、「それも世代 +1 とみなす」
  と規約を広げるかは未決（下記残論点）
- B 採用（次節）により、フラグは世代番号 diff の一本。非フォーマット破壊を
  「世代 +1 とみなす」規約拡張で台帳に載せるなら、フラグ機構もそのまま一本化される

## versioning 方式（B: hatch-vcs に決定）

四択から B を採用。版の宣言を git tag ただ一つに置き、pyproject の version は
`dynamic` にして hatch-vcs（setuptools-scm 機構）で導出する。

| | 方式 | フラグの所在 | リリース時の版作業 |
|---|---|---|---|
| A | 静的 + リリース時 bump | ラベル or 世代番号 diff | bump コミット |
| **B（採用）** | hatch-vcs（git tag から動的導出） | 世代番号 diff | なし（tag のみ） |
| C | 静的 + 常時 `.devN` 仮宣言 | pyproject そのもの | `.dev0` 剥がし |
| D | release-please（レールに乗る） | conventional commits | なし（Release PR をマージ） |

### 背景: 選定の枠組み

各方式の差は「破壊的か否かをいつ判断するか」ではなく「判断の保存場所」にある。
判断を文脈が最も新鮮な PR 時点で行うのはどの流派も共通の実践で（B 系の pytest は
towncrier 断片カテゴリに、D は conventional commits に保存する）、本プロジェクトでは
世代台帳が既にその保存場所を務めている（前節）。すると版番号は
（前回 tag, 世代台帳 diff, いま出すという裁量）から機械的に導出できる値になる。
導出可能な値は正本から導出し、手書きの複製を持たない——本プロジェクトの製品テーゼを
版管理自身に適用したのが B。破壊リリース（1.0.0 ローンチ含む）も台帳照会で番号を
決めて tag を直接打つだけで、bump という工程は存在しない。

### 落選理由

- **C**: 検討時は「完成形」と目され、選定過程でも一度は採用に傾いてから覆した経緯が
  あるので詳記する。`.devN` 仮宣言の携行は「main の版宣言は常に正しい」という義務であり、
  義務は検査を要求する——tag⇔pyproject 一致検証（Q10）、仮宣言・上書き規律の検査（Q11）、
  仮宣言遅延（この間 main の版が嘘をつく）を塞ぐ自動化、と装置が運用側に生え続ける。
  しかも携行される宣言は世代台帳から導出可能なビューの手書き複製で、Q11 の整合検査は
  複製の同期検査にほかならない。当初 C の優位とされた「pyproject がフラグを兼ねる」は
  台帳（+ 規約拡張）で等価になり、「版番号が in-tree で読める」は実行時
  `importlib.metadata` で取れる以上の小差。設営コストゼロと引き換えに自前の規律 + 門を
  恒久に払う分割払いであり、既製で枯れた設営を一回払う B に総負担で劣る
- **D**: 解く問題——bump 判断の分散（多人数）、リリース統治（マージ = 承認フロー通過）、
  艦隊規模（多リポジトリの無人リリース。出自は googleapis のコード生成リポジトリ群）、
  多ファイル版整合——がどれも本プロジェクトに存在しない。bump 判断は世代台帳が
  構造化済み、リリースは単独裁量、単一リポジトリ、版を持つファイルは pyproject のみ。
  対価（conventional commits の恒久規律 = コミットメッセージへのメタデータ埋め込み）
  だけが残り、`feat!` ⇔ 世代 +1 の整合もレール外（Q11 に残る）
- **A**: 常時仮宣言がないぶん main の版番号が嘘をつき、bump コミットも残る。
  B は両方を消す上位互換（当初の「C の下位互換」判定を B 基準で言い直したもの）

### 導入設営（一回払い、実機検証済み）

- hatchling に hatch-vcs を追加し `dynamic = ["version"]` 化
- 変則 tag（`v0-ts-baseline` 等が既存）対策の tag パターン設定を保険で入れる
  （現状のままでも `v0.1.0` が正しく拾われ `0.1.1.dev1+g...` と導出されることは確認済み）
- `tool.uv.cache-keys` に git キーを追加（editable 環境の `importlib.metadata` が
  古い版のまま残るのを防ぐ）
- ci.yml と Q10 ワークフローの checkout を `fetch-depth: 0` に（shallow clone では
  版導出できず `uv sync` のビルドが落ちる）
- 問題にならないことを確認済みの点: sdist は解決済み版番号を PKG-INFO に埋めるため
  .git のない環境でもビルド可。uv.lock は動的版を版固定から省く（uv 0.5.19+）ため
  コミットごとの churn は起きない

### 運用上の含意

- tag の打ち間違いには対向検証が原理的に存在しない（tag が唯一の宣言のため）。
  チェックリストで受け、必要になったら「前回 tag より大きい・世代台帳 diff と整合」の
  sanity check を Q10 ワークフロー冒頭に足す
- 開発ビルドの版番号 `0.1.2.dev3+g1a2b3c4` の「次版」部分は最下位桁 +1 固定の推測で、
  破壊的 PR マージ後も実際に予定される次版（破壊リリースの桁）を反映しない。
  表示のみの問題で実害はない

## リリースノートの三層整理（検討メモ — Q10 / Q11 の具体化で確定）

リリースノート欄には性格の異なる三層が同居する。要求水準を層ごとに分けて設計する:

- **台帳**（自動生成の What's Changed）: 人間向けの伝達価値は薄いが、機械経路——
  Releases ページの本文検索（PR 番号 → 収録版の逆引き）、Renovate / Dependabot が
  bump PR へ行う本文転載、API / LLM エージェントの参照——のためのデータとして維持する。
  正本は git の DAG で、これはその導出ビュー。生成部は手で編集しない
- **オマケ**（告知ハイライト）: 約束しない。書くかどうかは恣意であり、基準は立てない
  ——基準を立てれば義務になり、義務は検査を要求する（versioning 方式 C の落選と同じ
  論法。義務にするのはラベル層の一点だけ）。忘却防止には in-tree の走り書きを携行する
  案が有力——告知したいことのある PR（新機能でもセキュリティ修正でも）がマージ時の
  裁量で一行メモを足し、リリース時は残高があれば整形して消し込む、空なら何もしない。
  走り書きは「何を書くべきか」の判定装置ではなく、恣意の行使時点を文脈が最も新鮮な
  PR 時へ移す搬送機構で、これによりリリース時の手順は開放的な判断ではなく残高参照の
  一行に潰れる。緊急リリースで飛ばしても走り書きは残るので、書きそびれは自然に次回へ
  繰り越される。採否は Q10 で確定
- **ラベル**（義務）: 「破壊的リリースの冒頭に移行手順を手書きする」の一点のみを
  義務としてチェックリストに載せ、義務にした一点だけを機構（Q11）で支える

PyPI にはリリースノートの表示面がない（README とメタデータのみ）ため、
`[project.urls]` に Changelog リンク（GH Releases へ）を足して誘導する。

## 自動化の実装（Q10 / Q11）

自動化は契機の異なる二面に分かれる。tag push 側は publish の実行、
PR マージ側は規律のゲート化であり、性格が違う。

### tag push 側 — publish 実行（[Q10](node:/tasks/Q/tasks/Q10)）

- tag push（`v*`）契機: build → PyPI publish → GH Release 作成
- 認証は trusted publishing（PyPI 側にリポジトリ + ワークフローファイル名を登録。
  プロジェクトは 0.1.0 手動 publish（[Q1](node:/tasks/Q/tasks/Q1)）で実在するため通常登録。
  以後 API token は不要になる）
- tag と pyproject の version 一致検証は B 採用により不要（版宣言が tag のみになり、
  このエラークラス自体が消滅）。代わりに checkout は `fetch-depth: 0` が必須
  （hatch-vcs の版導出に tag 履歴が要る）
- リリースノートは GH 自動生成（PR タイトルの束ね）。`.github/release.yml` のラベル別節で
  breaking を分離し、破壊的リリースのみ冒頭に移行手順を手書きする。
  外部向けの体裁格上げ判断は [Q7](node:/tasks/Q/tasks/Q7)

### PR マージ側 — 破壊的変更ゲート（[Q11](node:/tasks/Q/tasks/Q11)）

破壊的変更が「しれっと」マージされるのを PR 時点で捕まえる追加プロセス。
何かを置くことはほぼ確定、実装形が未確定。候補（併用可）:

- **ci.yml への検査 job**（機械化できる規律）: フラグ整合（世代番号を触る PR ⇔
  breaking ラベル。C 落選により `.devN` 規律検査は候補から消えた）
- **AI レビュー**: merge 前に「破壊的変更が紛れていないか」を観点指定でチェックさせる
- **`.github/pull_request_template.md`**: 破壊的変更の有無を自己申告するチェック項目
- **DEVELOPMENT.md の規律明文化**: 人間の習慣として残す部分の文書化

minimum_version 整合（showcase / dev-docs）は GH Actions ではなく通常の
テストスイートに書ける可能性がある。どの手段をどの深さで採るかの捌きは
[Q6](node:/tasks/Q/tasks/Q6) で決める。実装先は新規ワークフローではなく
既存 ci.yml への追加を想定。

## 残論点

- 非フォーマット破壊的変更の扱い（ラベル保険 or 世代 +1 への規約拡張。
  B 採用後はフラグ機構が世代番号 diff 一本のため、台帳に載る後者が有力）
- PR マージ側ゲートの実装形の捌き（上記候補のどれをどの深さで — Q6 で決定）
- リリースノート三層の確定（走り書き携行の採否、`.github/release.yml` の
  節・除外ラベル設計）
- minimum_version 更新（showcase / dev-docs）の自動化余地
- チェックリスト本体の置き場所（DEVELOPMENT.md 直書きか、本ファイルに置いて
  DEVELOPMENT.md からポイントするか）
