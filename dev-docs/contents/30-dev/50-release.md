## 決定事項（大枠）

- **main は trunk のまま、リリースは別イベント**。「main マージ = リリース」にはしない。
  リリースは version 確定 + git tag push であり、tag push を契機に GH Actions が
  build → PyPI publish（trusted publishing）→ GH Release 作成を行う
- **バージョニング**: リリースは役割で分類する——一段目は破壊/互換の二値、互換の内側に
  機能/修正の副分類。破壊は二種の総称——**フォーマット破壊**（それまでサポートされて
  いた世代が一つでもツールの対応集合から外れること。トリガは
  old_supported − new_supported ≠ ∅ であり、世代の**追加**自体は破壊ではない。
  現行の単一世代レジームでは脱落と世代 +1 が常に同時に起きるため「世代 +1 = 破壊」と
  読めてしまうが、定義は脱落の側にある——複数世代並行サポート解禁後は一致しない。
  ソース互換の契約と世代運用は
  [sbdb-manifest](node:/prose/20-design/20-app/60-sbdb-manifest) の管轄）と
  **ツール破壊**（ツールの利用者向け契約——CLI 等——を壊す。ソースにも
  マニフェストにも関係しない）。どちらの PR 規律も下記「PR 側の規律」。
  役割から版番号の桁への写像は次表に隔離し、本ファイルの
  他の記述はすべて役割語で書く（1.0.0 で桁の対応が滑っても、更新はこの表だけで済む）:

  | 役割 | 0.x 期（現行） | 1.0.0 以降 |
  |---|---|---|
  | 破壊 | 0.MINOR+1 | MAJOR+1 |
  | 互換・機能 | 0.x.PATCH+1 | MINOR+1 |
  | 互換・修正 | 0.x.PATCH+1 | PATCH+1 |

  0.x 期の対応は「0.MINOR を破壊的変更に予約する」慣習（Cargo 系エコシステムの
  事実上の標準）。機能/修正の副分類は桁選択専用で、リリース手順もリリースノートの
  扱いも分けない。判定の一次入力はトレーラーのマーク（下記リリースノート節）、
  バックストップはリリース手順 1 の検算（docs/reference 差分の一読——機能追加は
  docs 同期が義務なので仕様差分を必ず残す）。賭け金は桁一つなので検査機構は建てない。
  0.x 期は番号に現れないため判定自体が不要。
  1.0.0 はローンチ（[Q3](node:/tasks/Q/tasks/Q3)）で刻む
- **版宣言の正本は git tag ただ一つ**（方式 B: hatch-vcs、選定理由は下記
  「versioning 方式」）。pyproject の version は dynamic 化して tag から導出する。
  bump コミットと tag⇔pyproject 一致検証というエラークラスを最初から持たない
- **リリースの契機は裁量**（少なくともローンチまで）。契機は役割で二層に割れる:
  互換リリースは任意のタイミングで打てる（リリース手順は役割によらず同一で軽い——
  下記二相構造）。破壊リリースは「破壊的変更を出す」という決断そのものが契機であり、
  自動化する余地がない
- **ブランチモデルは trunk-based 維持、Git Flow は採らない**。Git Flow は選択的取り込み
  （破壊的変更を除いてリリースを切る）を構造では解けず、常設ブランチの維持コストだけが残る。
  旧系列への修正需要（= 破壊的変更を越えて上がれない利用者）が実際に発生したら、
  過去 tag から遡及ブランチを切って cherry-pick する（`git switch -c release-0.X v0.X.Y`）。
  需要はローンチ前にはほぼ定義上存在しない
- **破壊的 PR のマージタイミング**: 破壊的 PR をマージすると、以後の main からは
  互換リリースが打てなくなる（破壊リリースを仕上げて出すか、遡及ブランチに頼る）。
  「次のリリースを破壊リリースにする覚悟ができたときにマージする」を習慣とする。
  規律が払えないコストになったときの構造的解は Git Flow ではなく、
  sbdb_version 対応集合の複数世代並行サポート（sbdb-manifest に YAGNI として保留済み）

## 二相構造: PR が置き、リリースが消化する

リリースに要る判断と記述はすべて、文脈が最も新鮮な PR 時点で置く。リリース時は
その消化（読む・打つ・貼る）だけで、判断も、コミットも、役割による手順の分岐も残らない
——破壊/機能/修正の差は「PR が何を置くか」に全部畳まれている。

### PR 側の規律 — マージ前に済ませる判断と記録

規律の実務チェックリストの正本は DEVELOPMENT.md（[W1](node:/tasks/W/tasks/W1) で
書き出す）。ゲートの実体は「作業中・レビュー時に規律が見えていること」であり、
DEVELOPMENT.md はタスク開始時から必ず作業文脈に載る唯一の場所。本節が持つのは
その設計判断の背景。

破壊的 PR（フォーマット破壊・ツール破壊とも）は、以下を自身に含める。breaking
トレーラーだけが PR 本文（= squash コミット本文）に書かれ、他はすべてレビュー対象の
リポジトリ内容:

- **非互換注記**: 非互換に書き換えた docs/reference の章に、「この章の契約が最後に
  非互換に動いた版」を記す一行を書く（または更新する）。値は、フォーマット章
  （schema / view / template / manifest）は世代番号、ツール章（cli 等）は日付か
  PR 番号（リリース版番号は tag を打つ瞬間まで存在しないため、PR 時点では書けない）。
  貼付は lazy——全章に貼って回らず、最初の破壊的編集が最初の注記を書く。注記の不在 =
  一度も壊れていない、の表明として正しい
- **フォーマット破壊のみ、追加で二つ**: 利用者向けの移行手順を docs に書く
  （正本はリリースノートではなく docs。置き場所は該当章の注記の近傍を第一候補に、
  最初の破壊的変更時に確定。ツール破壊では書き換え後の該当章自体が新契約の案内を
  担うので独立の移行文書は要らない）。および世代番号まわりの追随一式
  （[sbdb-manifest](node:/prose/20-design/20-app/60-sbdb-manifest) の管轄）
- **breaking トレーラー**（PR 本文末尾——下記リリースノート節）: リリースは
  ログしか読まないため義務。「世代宣言が動いたのにトレーラーが無い」という
  不整合は lint ワークフロー（[T4](node:/tasks/T/tasks/T4)——下記 PR マージ側）が
  PR 上のコメントで指摘し、レビューが最終確認する

破壊的変更は外部仕様の正本（docs/reference）の編集を必ず通る——文書化されていない
挙動は契約外（仕様が契約。厳格パースが最終防衛線）。ゆえに非互換注記の規律が検問を
張り（破壊的編集は、注記か「注記を書くべき既存仕様の書き換え」を必ず自身の diff に
含む）、残余リスク（作者が破壊に無自覚なままマージする）には既存機構——fixture
スイート（期待値コミット済みの golden テスト）、showcase / dev-docs のビルド、
manifest ゲート、全 PR のレビュー——が命綱になる。これを超える常設装置は
lint ワークフロー（T4——既存シグナル同士の決定的な突き合わせと注意喚起のみ。
内容が破壊的かどうかの意味判定はしない）一本に留め、意味判定側は建てる契機だけを
記録する: **差分ハーネス**（merge-base 時点の showcase + dev-docs
ソースに旧新両版の mood をかけ、出力 diff を Warn として PR に提示）は、外部
コントリビュータを受け入れて全 diff を精読しなくなったとき、または最初の silent
破損事故が起きたとき。

破壊以外の PR: トレーラー（告知と次版の桁の意図）は裁量。機能 PR の docs/reference
同期（開発ワークフローの既存義務）は、機能/修正判定のバックストップも務める。

### リリース手順 — 役割によらず単一

経路分岐も、main へのコミットも無い。B の「リリース時の版作業: なし（tag のみ）」が
手順全体に及ぶ。5 分で回る軽さを目標とする。

```
1. 次版番号を導出: 前回 tag 以降のトレーラーを収集
   （git log <前回タグ>..HEAD --format=%B | grep -E '^Release-Note: '）
   し、マークの最高位を取って写像表に通す
   検算: git log <前回タグ>..HEAD の一読で宣言の抜けを検める（破壊の記録漏れは
   PR 側の規律が塞ぐ。ここで拾うのは feature マークの書き忘れ程度）
2. tag push → ワークフロー完走（build → PyPI publish → GH Release 自動作成）の確認
3. 生成された GH Release の冒頭に、手順 1 の収集結果を整形して足す——オマケも
   移行手順のポインタも同じ動作（収集が空なら何も無し）
```

収集は一行 grep で、常設の装置は要らない。git の trailer 解析
（`%(trailers:key=...)`）を使わないのは、それがメッセージ最終ブロックしか読まない
ため——squash 本文は連結で構成され、GitHub が末尾に区切りと `Co-authored-by` を
自動付加するので、トレーラーが最終ブロックに残る保証がない（実機確認済み）。
行頭 grep は位置に依存しない。書式の正しさは T4 の lint が PR 時点で担保する分担。
git log の範囲指定が「前回 tag 以降」だけを返すので、鮮度管理・消し込み・共有ファイルの
コンフリクトという問題群は機構ごと存在しない。

## versioning 方式（B: hatch-vcs に決定）

四択から B を採用。版の宣言を git tag ただ一つに置き、pyproject の version は
`dynamic` にして hatch-vcs（setuptools-scm 機構）で導出する。

| | 方式 | フラグの所在 | リリース時の版作業 |
|---|---|---|---|
| A | 静的 + リリース時 bump | ラベル or 世代番号 diff | bump コミット |
| **B（採用）** | hatch-vcs（git tag から動的導出） | 世代番号・非互換注記の diff | なし（tag のみ） |
| C | 静的 + 常時 `.devN` 仮宣言 | pyproject そのもの | `.dev0` 剥がし |
| D | release-please（レールに乗る） | conventional commits | なし（Release PR をマージ） |

### 背景: 選定の枠組み

各方式の差は「破壊的か否かをいつ判断するか」ではなく「判断の保存場所」にある。
判断を文脈が最も新鮮な PR 時点で行うのはどの流派も共通の実践で（B 系の pytest は
towncrier 断片カテゴリに、D は conventional commits に保存する）、本プロジェクトでは
in-tree の構造側フラグ（世代番号。のちに docs/reference の非互換注記へ拡張——
PR 側の規律）が既にその保存場所を務めている。すると版番号は
（前回 tag, in-tree フラグの diff, いま出すという裁量）から機械的に導出できる値になる。
導出可能な値は正本から導出し、手書きの複製を持たない——本プロジェクトの製品テーゼを
版管理自身に適用したのが B。破壊リリース（1.0.0 ローンチ含む）もフラグ照会で番号を
決めて tag を直接打つだけで、bump という工程は存在しない。

### 落選理由

- **C**: 検討時は「完成形」と目され、選定過程でも一度は採用に傾いてから覆した経緯が
  あるので詳記する。`.devN` 仮宣言の携行は「main の版宣言は常に正しい」という義務であり、
  義務は検査を要求する——tag⇔pyproject 一致検証、仮宣言・上書き規律の検査、
  仮宣言遅延（この間 main の版が嘘をつく）を塞ぐ自動化、と装置が運用側に生え続ける。
  しかも携行される宣言は in-tree フラグから導出可能なビューの手書き複製で、要求される
  整合検査は複製の同期検査にほかならない。当初 C の優位とされた「pyproject がフラグを
  兼ねる」は in-tree フラグ（世代番号・非互換注記）で等価になり、
  「版番号が in-tree で読める」は実行時
  `importlib.metadata` で取れる以上の小差。設営コストゼロと引き換えに自前の規律 + 門を
  恒久に払う分割払いであり、既製で枯れた設営を一回払う B に総負担で劣る
- **D**: 解く問題——bump 判断の分散（多人数）、リリース統治（マージ = 承認フロー通過）、
  艦隊規模（多リポジトリの無人リリース。出自は googleapis のコード生成リポジトリ群）、
  多ファイル版整合——がどれも本プロジェクトに存在しない。bump 判断は in-tree フラグが
  構造化済み、リリースは単独裁量、単一リポジトリ、版を持つファイルは pyproject のみ。
  対価（conventional commits の恒久規律 = 全コミットに義務のメタデータ埋め込み。
  裁量のトレーラーとの区別はリリースノート節）だけが残り、`feat!` ⇔ 世代 +1 の整合も
  レール外
- **A**: 常時仮宣言がないぶん main の版番号が嘘をつき、bump コミットも残る。
  B は両方を消す上位互換（当初の「C の下位互換」判定を B 基準で言い直したもの）

### 導入設営（一回払い、実機検証済み）

- hatchling に hatch-vcs を追加し `dynamic = ["version"]` 化
- 変則 tag（`v0-ts-baseline` 等が既存）対策の tag パターン設定を保険で入れる
  （現状のままでも `v0.1.0` が正しく拾われ `0.1.1.dev1+g...` と導出されることは確認済み）
- `tool.uv.cache-keys` に git キーを追加（editable 環境の `importlib.metadata` が
  古い版のまま残るのを防ぐ）
- ci.yml と publish ワークフロー（T3）の checkout を `fetch-depth: 0` に（shallow clone では
  版導出できず `uv sync` のビルドが落ちる）
- showcase / dev-docs のマニフェストから `tools:`（minimum_version）ブロックを削除
  （[sbdb-manifest](node:/prose/20-design/20-app/60-sbdb-manifest) 側で決定済みの
  「置かない」の実施）
- 問題にならないことを確認済みの点: sdist は解決済み版番号を PKG-INFO に埋めるため
  .git のない環境でもビルド可。uv.lock は動的版を版固定から省く（uv 0.5.19+）ため
  コミットごとの churn は起きない

### 運用上の含意

- tag の打ち間違いは、トレーラー（意図側の第二宣言）との突き合わせで受ける。
  リリース手順 1 で番号を「考案せず導出する」こと自体が照合で、機械化は打ち間違いが
  実際に起きるまで保留（tag push 側の保留装置 tag sanity check）
- 開発ビルドの版番号 `0.1.2.dev3+g1a2b3c4` の「次版」部分は最下位桁 +1 固定の推測で、
  破壊的 PR マージ後も実際に予定される次版（破壊リリースの桁）を反映しない。
  表示のみの問題で実害はない

## リリースノートの三層整理

リリースノート欄には性格の異なる三層が同居する。要求水準は層ごとに違うが、
運搬機構は二つしかない: 台帳は自動生成、オマケとラベルは同じトレーラーが
PR マージから Release まで運ぶ。

- **台帳**（自動生成の What's Changed）: 人間向けの伝達価値は薄いが、機械経路——
  Releases ページの本文検索（PR 番号 → 収録版の逆引き）、Renovate / Dependabot が
  bump PR へ行う本文転載、API / LLM エージェントの参照——のためのデータとして維持する。
  正本は git の DAG で、これはその導出ビュー。生成部は手で編集しない。
  手書き CHANGELOG を義務として払い台帳層を持たない流派（minijinja 等）もあるが、
  本設計はオマケを義務化しない代わりに、無料で生成できる台帳を「空にならない床」
  として敷く
- **オマケ**（告知ハイライト）: 約束しない。書くかどうかは恣意であり、基準は立てない
  ——基準を立てれば義務になり、義務は検査を要求する（versioning 方式 C の落選と同じ
  論法。義務にするのはラベル層の一点だけ）。材料はトレーラー（次項）
- **ラベル**（義務）: 破壊的リリースの Release 冒頭には移行手順が載る。ただし移行手順の
  正本はリポジトリ内の docs で、書くのは破壊的 PR 自身（PR 側の規律）。義務の
  錨は PR 側にあり、リリース時の動作はオマケと同一——トレーラーの収集結果を貼るだけ

### リリースノート・トレーラー（採用）

告知したいことのある PR（新機能でもセキュリティ修正でも）が、PR 本文の末尾に
トレーラーを一行書く。key は `Release-Note`、マークは breaking / feature / fix の
三値、本文は英語一行（確定。conventional commits の `feat` と字面を変えるのは
「CC 規約ではない」の表明を兼ねる）:

    Release-Note: feature: mood tap outputs JSON

squash マージ設定を `PR_BODY` へ切り替える（[W1](node:/tasks/W/tasks/W1)。現行は
`COMMIT_MESSAGES`）ことで PR 本文が squash コミット本文へそのまま流れ、トレーラーは
main の履歴に in-tree で残り、リリース手順 1 の一行 grep で収集できる。

トレーラーは PR 粒度の宣言であり、住所は squash コミット（= PR 粒度の器）。
PR 本文は、記入面・レビュー面・搬送路がその住所に一致する唯一の媒体でもある。
先行案二つは棄却:

- **GitHub の PR ラベル**（`breaking`）——git 履歴に残らず、収集が API 依存になる
- **ブランチコミットメッセージ末尾**（当初採用）——COMMIT_MESSAGES 設定で squash
  本文へ流れはするが、実機確認で二つの穴が出た。(1) 連結された squash 本文の中で
  トレーラーは位置的に埋まり、GitHub の末尾自動付加（区切り + `Co-authored-by`）も
  あって git の trailer 解析（最終ブロックのみ）から漏れる。(2) レビューはコミット
  メッセージを読まない（PR の diff と本文がレビュー面）ため、義務層の宣言が
  レビューの視界に入らない。搬送の都合で記入面がコミット側へ逆流した案であり、
  宣言の粒度とも一致していなかった

なお squash 本文の正本が PR 本文になることに伴い、設計判断の背景の記録先も
ブランチコミットのメッセージから PR 本文へ移す（W1 で DEVELOPMENT.md を改訂）。
「設計の背景が main のコミットメッセージに残る」という不変条件は保たれ、記入面が
変わるだけ——連結された WIP コミットの箇条書きより、PR 時点で統合された一本の
文章のほうが履歴としても読みやすい。一行が二役:

- **本文** = オマケの材料。breaking 行は docs 内の移行手順へのポインタを兼ねる
  （ラベル層）
- **マーク**（breaking / feature / fix） = 桁選択の入力。リリース手順 1 が最高位を
  取る。次版番号そのものは書かない——マークから三値の max で導出できる値の手書き
  複製になるため（C の常時仮宣言を退けた判断の縮小版）。マークの集合が tag（正本）に
  対する意図側の第二宣言として、打ち間違いの照合先を兼ねる

版番号は伝達行為であって機械的真実ではない（破壊なしに major を上げるのも違反では
ない）。ゆえにマークは検知結果ではなく「次の桁をこう動かしたい」という意図宣言で、
トレーラーはその行使時点を文脈が最も新鮮な PR 時へ移す搬送機構——リリース時の手順は
開放的な判断（「今回何か書くべきか」）ではなく収集に潰れる。breaking のみ義務
（リリースがログしか読まないため。書き忘れは lint の突き合わせコメントとレビューが
捕まえる——PR 側の規律と T4）、feature / fix は best-effort のまま
義務化しない。機能マークの書き忘れは「機能リリースを修正番号で出す」
（0.x 期は無差、1.0 以降も桁一つ）に留まり、検査装置を建てるほどの賭け金がない。

feature / fix の選択規準は「docs/reference の**約束の集合が増減したか**」。
増減したら feature——既存挙動の新規文書化も、契約外（文書化されていない挙動は
契約外）を契約内に入れる拡張なので feature。同じ約束の言い直し・明確化・構成整理は
fix 以下。この境界の判定は意味判断であり、機械検査せず作者に委ねる。

### 背景: 棄却した代替

- **in-tree の走り書きファイル**（`RELEASE_NOTES.next.md` を携行しリリースで消し込む、
  towncrier 断片系の変種）——消し込みが所有者と契機のない掃除として残り続け、
  並行 PR のコンフリクト磁石になる。トレーラーは git log の範囲指定が鮮度管理を
  定義上済ませる。代償は文言の後編集不可（リリース時の整形で吸収）と繰り越しの
  手動化（オマケは無約束層なので許容）
- **conventional commits（D 案）との混同**——D の対価はレール入力としての強制規約
  （全コミットが従い、機械がパースし、違反がリリースを壊す）。トレーラーは裁量の
  告知チャネルで機械は読まず、設計判断の背景を main の squash コミット本文
  （記入面は PR 本文）に残す本リポジトリの文化の延長にある

PyPI にはリリースノートの表示面がない（README とメタデータのみ）ため、
`[project.urls]` に Changelog リンク（GH Releases へ）を足して誘導する。

## 自動化の実装（T3 / T4）

自動化は契機の異なる二面に分かれる。tag push 側は publish の実行、
PR マージ側は規律の検査と注意喚起であり、性格が違う。

### tag push 側 — publish 実行（[T3](node:/tasks/T/tasks/T3)、旧 Q10）

- tag push（`v*`）契機: build → PyPI publish → GH Release 作成
- 認証は trusted publishing（PyPI 側にリポジトリ + ワークフローファイル名を登録。
  プロジェクトは 0.1.0 手動 publish（[Q1](node:/tasks/Q/tasks/Q1)）で実在するため通常登録。
  以後 API token は不要になる）
- tag と pyproject の version 一致検証は B 採用により不要（版宣言が tag のみになり、
  このエラークラス自体が消滅）。代わりに checkout は `fetch-depth: 0` が必須
  （hatch-vcs の版導出に tag 履歴が要る）
- リリースノートは GH 自動生成（PR タイトルの束ね）が台帳層を担う。ラベル別の節分けは
  しない（ラベル不採用）——`.github/release.yml` は必要になっても除外設定程度。
  オマケ・移行手順はトレーラーの収集結果から手で整形して冒頭に足す。
  外部向けの体裁格上げ判断は [Q7](node:/tasks/Q/tasks/Q7)

保留装置（建てる契機だけ記録して封印）:

- **tag sanity check**（ワークフロー冒頭で tag をトレーラーの最高位と突き合わせ）—
  tag の打ち間違いが実際に起きたとき
- **Release 本文へのトレーラー自動転記**（ワークフローが収集・整形して冒頭に足す）—
  手作業の貼り付けが煩わしくなったとき
- **自動 tag**（トレーラーを読んで機械が tag を打つ）— release-please の自作ミニ版に
  向かう道なので、リリース頻度が裁量判断を上回ったときまで封印

### PR マージ側 — lint ワークフロー（[T4](node:/tasks/T/tasks/T4)、旧 [Q11](node:/tasks/Q/tasks/Q11)）

Q6 時点の予測（新設 CI ゼロ）は Q11 の検討で覆した。lint は「既存シグナル同士の
決定的な突き合わせ」だけを行い、「内容が破壊的かどうか」の意味判定には踏み込まない
（そちらは既存機構と、封印中の差分ハーネスの管轄——PR 側の規律の節）。出口は二種:

- **fail はトレーラー書式検査のみ**: PR 本文に Release-Note 風の行があれば
  key の綴り・マーク語彙・書式を検証し、ニアミス（`Release-Notes:` 等）も狭い
  パターンで検知して落とす。壊れたトレーラーは正当なケースが存在せず、放置すると
  リリース収集から無言で漏れて発覚が最も遅い場所（リリース時の検算）まで遅延する
  ——silent 破損の性質を持つここだけを赤で止める。PR 本文の編集でも再検査する
  （opened / edited / synchronize）
- **注意喚起は非ブロックの sticky コメント**（一件に集約、コピペ可能な suggest と
  DEVELOPMENT.md へのポインタ付き）。トリガ二つ、文面の強度で差別化:
    - 世代宣言ファイル（[V8](node:/tasks/V/tasks/V8) で切り出す専用モジュール）に
      diff ∧ breaking トレーラー無し →「フォーマット破壊に見える。breaking は義務」
    - docs/reference に diff ∧ トレーラーゼロ →「約束の集合が増減したなら
      feature / fix をどうぞ。言い直しだけなら無視してよい」——無視が正当な応答
      （= 言い直しの表明）である点が義務化との違い

世代宣言ファイルの diff 検知は「集合からの世代脱落」（破壊の定義）の保守的近似。
ファイルには定数一行しか無いので現行レジームでは実質等価で、誤るとしても過剰発火の
側にしか誤らない。世代側トリガを fail にしないのは、CI がマージ画面で編集される
最終 squash 本文を検査できず、「マージ時に PR 本文へ足す」という正規の回復経路が
CI の可視範囲の外にあるため——fail の保証は見かけより弱く、摩擦だけ確実に増える。

検討時の候補の顛末: 検査 job は上記の突き合わせ範囲で採用、PR テンプレの自己申告は
外部コントリビュータ向けの面として [Q7](node:/tasks/Q/tasks/Q7) へ送付
（全 PR に発火して precision が低く、`gh pr create --body` はテンプレを適用しない
ため内部運用には効かない）、AI レビューは不採用。

保留装置（建てる契機だけ記録して封印）:

- **世代チェックの集合比較化**（ファイル diff 検知を、両端点から対応集合を抽出して
  脱落を検知する方式に格上げ）— 複数世代並行サポート解禁のとき（追加的な世代追加が
  非破壊になり、ファイル diff 近似が偽陽性を出し始める）
- **世代側注意喚起の fail 格上げ** — 外部コントリビュータを受け入れたとき
- **docs 側注意喚起の fail 格上げ**（docs/reference diff にトレーラー宣言を義務化。
  マーク自体は作者選択のまま「宣言が意識的に行われたこと」だけを検査する弱形）—
  1.0.0 で feature / fix の桁が分かれ、賭け金が生まれたとき

## 実装タスクの分割

  記録先転居 + PR 側規律の書き出し）・収集一行コマンドの確定記載。

  DoD = 実リリース 1 回でチェックリスト本体を確定

どのタスクも docs/reference に触れないため、トレーラーは載らない（沈黙 =
「申告することなし」の正しい表明。検証目的の偽トレーラーは収集にノイズを混ぜるので
積まない）。本物の初検体は、最初に docs/reference を動かす機能 PR が務める。
