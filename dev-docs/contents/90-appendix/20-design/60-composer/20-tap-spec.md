# Tap Specification (appendix)

[Tap Specification](../../../20-design/60-composer/20-tap-spec.md) の背景。

## ソースを直読みさせない理由

利用者が `contents/` の YAML を直接読めば済むように見えるが、ソースは**著者が書きやすい形**であって**照会しやすい形**ではない。tap はその差を埋める:

1. **形が揃う** — ソースは map パターン（`{id: {...}}`）で書けるが、tap の出力は正規化後の配列（`[{id: ..., ...}]`）。`jq 'map(select(...))'` がそのまま効く
2. **マージ済み** — ソースは複数ファイルに分かれ、ビルド時に deep-merge される。直読みでは利用者側がマージを再実装することになる
3. **形式が一本化される** — ソースは YAML と Markdown が混在する（prose は Markdown ファイル）。tap の出力は 1 本の木
4. **ビューが入る** — join・グループ化された結果はソースには存在しない。導出データは tap でしか取れない

1〜3 は外部プログラムに、4 は主にエージェントの照会に効く。

## jq 引数を持たせない理由

検討過程では「MCP に `jq` 引数を持たせ、CLI にも同じ `--jq` を置く」案を採っていた。理由は「MCP クライアントがファイルツールを持っていてもシェルを持つとは限らず、シェルを持たないエージェントには生成はできても照会する手段が残らない」というもの。この理由付けは、対象読者を場合分けすると成立しない:

| クライアント | ファイルシステム共有あり | 共有なし |
|---|---|---|
| シェルあり | パスが効く。ただし `mood tap` を自分で叩けるので MCP 経由である必要が薄い | パスは無意味。jq だけが効く |
| シェルなし | パスは返るが、照会手段は丸読みしかない → jq が要る | 何も効かない |

つまり jq 引数が救うのは**シェルを持たないクライアントだけ**で、その読者は現時点で仮想的である（実需の外部プログラムは CLI 経路、エージェント照会の実体はいずれもシェルを持つ）。そして jq 引数は後から**純粋な引数追加**として足せる。仮想の読者のために、jq エンジンの依存（PyPI `jq` は C 拡張）とエラー面・結果フォーマットの設計を先に払う理由がない。

副次的に、mood 側が jq の口を一切持たないことで、mood が持つクエリ概念はビュー定義の DSL（[query-dsl-spec](../../../20-design/60-composer/10-query-dsl-spec.md)）ひとつに保たれる。

部分指定（トップレベルビューを選ぶ引数）も同根で外した。実測では dev-docs 全体でも 600KB 程度で、jq に流す分にはコストとして数えるに値しない — セレクタは jq が既にできることの再実装にしかならない。

## JSON のみにした理由

照会を利用者の jq に委ねる以上、そのまま jq に食わせられる形でなければならない（jq は YAML を読まない）。外部プログラムが標準ライブラリだけで読めるのも JSON。YAML 出力は実需が現れたら純増で足せる。

検討の記録として: **シリアライズ速度もトークン量も判断根拠にならない**。YAML 側に唯一残る実質的な利点は prose の複数行本文が literal block で展開されて grep が効くことだが、これは「生ファイルを直接読む」前提の利点で、jq に通す前提と噛み合わない。
