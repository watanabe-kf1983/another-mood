# プロジェクトマニフェスト (appendix)

[プロジェクトマニフェスト](../../../20-design/20-app/60-sbdb-manifest.md) の背景。

## Cargo との比較

Cargo は `edition` の省略を最古の edition とみなす。それは既存の資産を壊せない事情から来る妥協で、1.0 前の本ツールには要らない。`sbdb_version` を必須とし、省略時のフォールバックを持たない。

## エラーメッセージの文言

マニフェストが無いときのエラーメッセージは事実だけを述べ、対処は書かない（`No sbdb.yaml in <dir>: not an Another Mood project.`）。このエラーに至る現実的な経路はディレクトリの指し間違いで、そこで対処を示してもノイズにしかならない（uv の `No pyproject.toml found` と同じ判断）。「`mood init` してください」に至っては、マニフェストだけを失ったプロジェクトには効かない（init は既存プロジェクトへの scaffold を拒む）。主語を（存在しない）ファイルではなくディレクトリにするのは、無いファイルのパスから文を始めると、読み手がまずそのファイルを探しに行ってしまうためである。

## minimum version の細目

細かな仕様は minimum version の先例に合わせる:

- **受け付けるのは素のバージョンだけ**で、範囲指定は受けない。Go、Rust の rust-version、CMake のように「ビルドツールがソースのマニフェストを読む」系はどれもそうしている。範囲の語彙は依存解決器を持つ系のもので、上限は書く時点では知りようがなく、特定の版を除外するのはツールの性質の話であってソースの宣言ではない。将来必要になれば、別の欄を互換性を壊さずに足せる
- **宣言の意味は「この版で動くことを確認した」という検証済みの下限**で、本当の最小版を調べることは求めない（`uv add` が現行版で下限を切る実務と同じ）。下限にすぎないので、scaffold は生成時に実行中のバージョンを機械的に書き込んでよい
