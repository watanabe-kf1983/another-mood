# CLI Design (appendix)

[CLI Design](../../../20-design/25-entrypoints/20-cli-design.md) の背景。

## MCP サーバを提供しない理由

かつては `mood-mcp` エントリポイントで MCP サーバを提供していた（`mood` サブコマンドに対応する 7 ツール、`docs/` を公開する Resources、接続時に注入する Server Instructions）。J7 でこれを削除し、エージェント向けの専用経路を持たない形へ寄せた。

### MCP が運んでいたものの分解

MCP の 7 ツールはすべて `mood` サブコマンドの薄い皮であり、当時の設計原則「MCP と CLI の論理的機能は一致すべき」のとおり、MCP でしかできない操作は一つもなかった。実際、MCP を登録できない環境（企業ポリシーで禁止）でも CLI だけで問題なく運用できている実例があり、自リポジトリも削除時点で CLI だけで運用していた。

MCP が CLI に対して余分に運んでいたのは Server Instructions だけで、これは本ツールのエージェント向け文章のうち **唯一 `docs/` を正本としないもの** だった。他のドキュメントは「`docs/` を正本とし複数チャネルで配る」と一元化されていたのに、Instructions だけは MCP というチャネルに正本ごと埋まっていた。「MCP に登録せよ」と利用者に求めていたのは、この埋まり方の帰結にすぎない。

「AI 向け説明文」と一括りにされがちなものは三つに分かれる:

- **内容**（ツールが何をするか、どう使うか）: 人間と AI で同一であるべきで、別版は不要。`docs/` で済んでいる
- **導線**（このディレクトリを管理しているのが何者で、docs がどこにあるか）: sbdb プロジェクト直下に生成する `README.md`（J6）が担う
- **リポジトリ固有の運用**（dev-docs は `dev-docs/` にあり `mood build dev-docs` で組む、等）: ツールの文書ではなくリポジトリの文脈。書く主体はリポジトリの持ち主

結論として、ツールが出荷すべき AI 専用の文章は無い。

多くのライブラリが AI 向け文書（`llms.txt`、skill、AGENTS.md テンプレート）を別途出しているのは、人間向け docs が Web レンダリング前提で機械が取りにくい、量が多すぎて索引が要る、といった「docs が機械に読めない」症状への対処であり、方向は分離ではなく収束（人間向け docs を機械にも読める形に寄せる）である。本ツールは `docs/` が素の Markdown でパッケージに同梱され `mood docs read` で引けるので、収束後の形を最初から持っている。

### Server Instructions は枠ごと落とす

Server Instructions はツール作者の文章がエージェントのシステムプロンプトへ直接注入される経路で、指示は人間の開発者に向けて書きエージェントはそれを読む、という方針に反する。縮めて残すのではなく MCP ごと落とした。

Instructions の内容で `docs/` に無いものは無かった。`mood --help` の冒頭は「schema / views / templates を書く前に `mood docs list` → `mood docs read <uri>` で仕様を読め」と指しており、`docs list` は各ページの要約つきで URI を返す。作業ループ（編集 → build → `__db/` 診断出力で確認）は `docs/guides.md` の Workflow 章に、ソースの四種類は `docs/reference/cli.md` にある。Instructions は「振る舞いを前もって注入する枠」であり CLI に対応物は無い。

### 失ったもの

シェルを持たないクライアント（Claude Desktop のチャット等）から本ツールを操作する経路。この読者は tap の jq 引数を検討した際にも現時点で仮想的と判断している（[jq 引数を持たせない理由](../60-composer/20-tap-spec.md#jq-引数を持たせない理由)）。

ただし失った幅は見かけより狭い:

- **旧 MCP だけでは仕事が完結しなかった**: 旧 MCP は「ツールは読むだけ」の方針どおり書き込みの道具を持たず、できたのは build・docs・tap の参照系に限られた。シェルを持たないクライアントが contents/ を編集するには、ファイル操作の MCP を別途登録する必要がもともとあった
- **利用者の側で取り戻せる**: 汎用のファイル操作 MCP（公式リファレンス実装の filesystem サーバ等）とコマンド実行 MCP を登録すれば、そのクライアントは許可リスト付きのシェルを持つのと同じになり、`mood` CLI をそのまま使える。ツール固有の MCP を一つずつ用意するより、汎用の二つで足りる

削除に伴い、MCP 固有の設計（Resources と Tools への docs の並行公開、クライアント差への対処、MCP Python SDK の採用と依存の受容、パス引数を絶対パスに限る理由）も一緒に落ちた。経緯は git 履歴の `dev-docs/contents/20-design/25-entrypoints/20-mcp-design.md` にある。
