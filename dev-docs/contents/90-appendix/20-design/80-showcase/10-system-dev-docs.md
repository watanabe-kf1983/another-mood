[システム開発ドキュメント](../../../20-design/80-showcase/10-system-dev-docs.md) の背景。

## 調査の帰結: モデルファースト

「要求仕様書 + 設計書」をそのまま書ける、無料で再配布可能な既製テンプレートは存在しない。各資料が持つのは断片で（29148 は目次はくれるが節の内容定義は有償、IEEE 1016 は文書テンプレートを規定しない、IPA は成果物の項目定義は完全だが文書の目次を持たない、arc42 / Volere は完全なテンプレートだがライセンスと守備範囲が合わない）、目次を寄せ集めても「標準のラベルを着た我流」にしかならない。一方、標準はモデル（スキーマ）の水準では実体のある定義を持つ（42010 の概念モデル、1016 の viewpoint 仕様、ReqIF のメタモデル、IPA の項目定義とクロスリファレンスから復元できる暗黙の ER モデル）。そこで、よりどころは目次ではなくモデルに置く (方針は本文)。

## 典拠と借用の分担

| 資料 | 借りるもの | 転載上の制約 |
|---|---|---|
| ISO/IEC/IEEE 42010 | (採用せず) 概念モデルは文書の枠組みの理解に使うのみ。構成図・クラス図系の Candidates で再検討 | 概念モデル図は公式に無料公開。概念の利用は自由 |
| ISO/IEC/IEEE 29148:2018 | 章立ての素材 (SRS 例示アウトライン 8.5.2) と要求レコードの属性 (5.2.8) | 章題の翻案 + "informed by" 表記は確立した慣行で低リスク。本文の逐語転載・アウトライン図の複製は不可 |
| IEEE 1016-2009 | (採用せず) viewpoint 一覧は調査時のメニューとして使ったが、本 showcase の章には被せない。構成図・クラス図系の Candidates の領分 | 2020 年 Inactive-Reserved (10 年無改訂への管理措置、技術的否定ではない) |
| IPA 機能要件の合意形成ガイド | 各 artifact の項目定義 (画面 5 成果物 / エンティティ一覧・定義 / CRUD 図 等) | 複製許諾は目的限定付きで翻案禁止条項あり。項目名・構成をアイデアとして借り、定義文は自分の言葉で再設計し、出典を明記する |
| Volere | atomic requirement のレコード属性 (fit criterion / rationale / 優先度 等) | 27 節テンプレートのツール同梱・再配布は要許諾 (redistribution license の明記あり)。属性名 subset + attribution に留める |
| OMG ReqIF v1.2 | スキーマ設計原理 (型と値の分離 / 要求実体と文書階層の分離 / 関係自身が型と属性を持つ) | メタモデル概念の利用は自由。仕様文書の転載のみ不可 |

29148 の規範本文（有償）は購入しない。目次骨格と要求属性は無料の正規プレビューと二次文献で確定でき、規範本文が要るのは conformance を名乗る場合だけ。arc42（CC BY-SA 4.0）は骨格候補として調査したが不採用。アーキテクチャ文書テンプレートで網羅的な詳細設計（全画面定義・CRUD・DB 物理）の受け皿が弱く、翻案物への ShareAlike 継承義務も showcase 配布物には負担。

## Candidates (未タスク化)

今回の二文書の目次には入れず、将来の章として埋める:

- **HTML プロトタイプは範囲外 (詳細設計の領分)** — 線は HTML という形式ではなく忠実度に引かれている (ワイヤーフレーム水準の HTML は contents に入っている)。contents に .html を置くと blob (`text/html`) として両版の出力と Hugo の site にそのまま複製されることは実機で確認した (iframe で埋めることも、リンクで開くこともできる) が、部品の見た目や操作感まで固めた HTML モックは基本設計ではなく詳細設計の成果物なので、この showcase (外部設計まで) には載せない。同様に、画面定義に要素 ID (`data-testid` 等、E2E テストのロケータ) の列を置く慣行は、E2E テスト仕様 (何を確かめるか) が基本設計から導かれるのに対し、要素 ID はテストスクリプト (どう触るか) と実装の契約で詳細設計の決定という整理。同じレコード (画面.入出力項目) を基本設計が 名前 / 入出力 / 参照先 まで埋め、詳細設計が 要素ID を書き足す「一つのレコードを複数の工程が育てる」型で、要素 ID は規約 (`画面ID-項目名`) を上流で決めれば導出できる列になる。詳細設計の showcase を作るときの手掛かりとしてここに残す
- **システム構成図 (C4 系)** — Mermaid `C4Context` / `architecture-beta` で描く。後者は v11 でも beta 扱いで機能成熟度未確認。コンポーネント / コンテナ / 関係を構造化データで持つこと自体は可能。アーキテクチャ記述の標準は ISO/IEC/IEEE 42010
- **シーケンス図** — ユースケースのシナリオの図示。Mermaid sequenceDiagram。設計書の将来の章の候補 (ユースケース図は設計書 2 章のコンテキスト図として `flowchart` で実現した)
- **API / インタフェース仕様** — エンドポイント / リクエスト / レスポンス / エラーの構造化記述。OpenAPI 風だが本ツール独自スキーマで authoring する形。IEEE 1016 の interface viewpoint に対応
- **帳票定義** — IPA 帳票編 (帳票一覧 / 帳票概要 / 帳票項目説明) を項目典拠に。帳票項目 → 参照先エンティティ・カラムのクロスリファレンスを持ち、文書間同期の題材として筋が良い。帳票の存在自体は日本特有ではないが、二文書テーゼの実証に必須でないため今回は範囲外
- **バッチ処理定義** — IPA バッチ編 (バッチ処理一覧 / バッチ処理フロー / バッチ処理定義) を項目典拠に。処理サイクル / 起動方式 / 再処理方式などの項目定義を持つ

### showcase で表面化したツール側・将来の検討事項 (未起票)

showcase の設計対話で見つかったが、showcase タスクの範囲外として起票を保留しているもの。起票先はツール本体のタスクか本ファイルの Candidates。目次確定の過程で表面化した合成ビューは E17 として起票済み (前提は M13)。

- **`{% include %}` / `{% import %}` の文書化**: 動くが `docs/reference/template.md` に記述が無い (template-trust-model の loader の節で触れているのみ)。root テンプレートの分割手段 (include) と、テンプレート間でマクロを共有する手段 (import。業務モデルの 業務マクロ.md で実機確認、再帰マクロも動く) として記述する。小さな docs PR
- **string 配列への x-ref**: `items: { type: string, x-ref }` を許す拡張。現状はオブジェクト配列に包む
- **入れ子要素への x-ref**: x-ref はエンティティの ID しか指せず、エンティティ配下の 属性[] の要素は指せない。画面.入出力項目.参照先.属性 と エンティティ.属性.参照.属性 は素の文字列で、属性名の綴り違いはビルドで検出されない。親 ID + 子要素の名前 (複合キー) を指す x-ref の拡張か、view による突合 (CRUD マトリクス・画面定義の章) を検討する
- **上流のsbdb プロジェクトの参照 (依存)**: 要求を発注者側、設計をベンダや AI のリポジトリで持つ運用では、別のsbdb プロジェクトの entity を読み取り専用で x-ref の対象にし、版を固定する機能が要る。参照の向きの規律はこの分割を可能にする前提
- **suspect link (要確認リンク)**: 要求に版を持たせ、設計側の参照が設計時の版を持てば、要求変更で古くなった設計要素をビューで導出できる (新規要求の孤児検出と対)。トレーサビリティ表の増分で載せる候補。多対多で強いられた `{ID, 版}` のオブジェクト配列の形がそのまま使える
- **スコープ管理と FP 概算**: 要望一覧 / リリース計画 / FP 概算は別の文書群ではなく、同じレコードのスコープ確定前の姿 (要求・ユースケースに状態と対象リリースを持たせ、二文書は「採用」の部分集合を描くビュー)。FP が数える要素 (論理ファイル = エンティティ、トランザクション = 画面のアクション・外部インタフェース) は本 schema にあるので概算はビューで導出できる。showcase の範囲外 (showcase はスコープ確定後の文書を描く) だが製品動機に近い
- **プロジェクト管理成果物の showcase**: ステークホルダ登録簿や RACI など PMBOK 系の成果物は「表を構造化データから導出する」題材として筋が良い
- **ja / en 変種の構造同一性テスト**: 日本語版を製品として残す場合、名前を除いて schema の形が一致することを検査する仕組み
- **同じ subject を二度 render すると subject の anchor が二重に出る**: 一時期あった設計書の機能一覧が要求仕様書の主要機能と同じ `ユースケース | render(...)` で、一ページ (index.md) に `<a id="/ユースケース">` が 2 つ出た。ビルドは通り (`--strict` でも警告無し) リンクは先勝ちで着地するが、HTML の id 重複ではある。同じコレクションを二章で描く構成では起こりうるので、ツール側で 2 つ目以降を抑止するか警告するかを検討する (重複アンカーパスの検出 B15 に隣接)
- **anchor の所在とリンクの向き先の食い違いを検出できない**: リンクの向き先の頁はデータ上の位置で決まるので、`node()` で引いたノードを別の頁 (split された他レコードの頁) に `| anchor` で描くと、anchor はそこに出るのにリンクは home の頁を指す。ビルドは通り `--strict` も警告しない (実機確認済み。定石は join view)。anchor が home 以外の頁に出たら警告する検査があると、この取り違えを早く引き当てられる
- **マクロの戻り値の再エスケープ**: autoescape を切っているので Jinja マクロの戻り値は素の文字列になり、`{{ macro() }}` で呼ぶと `link` の出力までエスケープされる (実機確認済み)。症状は docs の Markdown escaping の節から辿れ、`| safe` か `{% set %}` で回避できるが、同節は `| safe` をコードスパン / フェンス / Mermaid の話として書き、`link` 等は「`| safe` 不要」と明記しているので、マクロ経由だと要るという例外が読めない。同節に一行足す (小さな docs PR)
- **コードフェンスの中のリンクが HTML 版で外れる**: Mermaid の `click` に `href` の URL を埋めると、出力 Markdown では正しいのに、コードフェンスの中なので Markdown から HTML への書き換えが効かず、`.md` のまま残って HTML 版で 404 になる (実機確認済み)。図の中からのリンクは現状どの図法でも張れない。図が大きくなる章 (4 の画面遷移図) でも効いてくるので、フェンス内の URL を edition に合わせて解決する手立て (専用フィルタ等) を検討する余地がある
- **テンプレートが見つけた不整合をビルドの警告に載せる経路**: 業務モデルのバランシング検査は付録の表として可視化するだけで、ビルドは通り `--strict` も止まらない。データの整合性規則のうちスキーマ (x-ref、`oneOf` 非対応の「ちょうど 1 つ」) で言えないものを view やテンプレートで検査する形は他の章 (属性名の突合など) にも広がるので、テンプレートからビルドの警告インフラに載せる手立て (例: 警告を発するフィルタ / 関数で、`--strict` なら失敗させる) を検討する
- **Mermaid flowchart の適合性 (PlantUML 等への舵切り)**: 業務モデルの DFD は読めたが、flowchart は構造化データからの自動レイアウトに向かないと評価しており、図が大きくなる場合 (分解の深い業務、4 章の画面遷移図) の評価は未了。舵切りの判断材料が要る
- **空の contents / views ディレクトリ**: 無いとビルドが失敗するため `.gitkeep` で保持している。無くても通る方が親切
