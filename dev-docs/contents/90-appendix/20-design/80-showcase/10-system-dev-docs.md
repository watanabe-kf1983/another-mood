# システム開発ドキュメント (appendix)

[システム開発ドキュメント](../../../20-design/80-showcase/10-system-dev-docs.md) の背景。

## 調査の帰結: モデルファースト

「要求仕様書 + 設計書」をそのまま書ける、無料で再配布可能な既製テンプレートは存在しない。各資料が持つのは断片で（29148 は目次はくれるが節の内容定義は有償、IEEE 1016 は文書テンプレートを規定しない、IPA は成果物の項目定義は完全だが文書の目次を持たない、arc42 / Volere は完全なテンプレートだがライセンスと守備範囲が合わない）、目次を寄せ集めても「標準のラベルを着た我流」にしかならない。一方、標準はモデル（スキーマ）の水準では実体のある定義を持つ（42010 の概念モデル、1016 の viewpoint 仕様、ReqIF のメタモデル、IPA の項目定義とクロスリファレンスから復元できる暗黙の ER モデル）。そこで、よりどころは目次ではなくモデルに置く。帰結:

- **項目の典拠は成果物の系統ごとに一つに絞る**。設計書側の相互参照型の成果物 (画面 ⇔ 入出力項目 ⇔ エンティティ、CRUD) は IPA ガイドの項目定義、要求仕様書側は 29148 (+ Volere) の要求属性。42010 の概念モデルは文書の枠組み (ビューポイント = schema の定義の束、ビュー = 章) を理解する道具として使い、データには持たない。ステークホルダは SRS / SDD に登場せず、関心事は要求と rationale に化けるので持たない。ユースケースのアクターはステークホルダとは別物で、上流の独立エンティティとして持つ
- **モデルの記述場所は showcase の schema.yaml そのもの**。抽出したモデルを別文書に起こさず、スキーマ + x-ref として書き、description に参照元を補記する (「IPA 画面一覧に対応」程度)。ビルドすれば `__defs/entities` / ER メタビューがモデルの図を出す
- **目次はモデルから導出されるビューの一つ**。章の並びは 29148 も IPA も自由裁量と明記しており、こちらで決めてよい。標準との対応は「何が記述され、どう関係づけられるか」の水準で取り、それも conformance ではなく description の典拠注記に留める
- **抽出は網羅しない**。サンプルに必要な範囲へのテーラリングと突合で済ませる。IPA の暗黙モデルを網羅的に抽出するほど翻案禁止条項に近づくため、部分的・自分の言葉での再構成が作業量でも法的にも安全側

29148 の規範本文（有償）は購入しない。目次骨格と要求属性は無料の正規プレビューと二次文献で確定でき、規範本文が要るのは conformance を名乗る場合だけ。arc42（CC BY-SA 4.0）は骨格候補として調査したが不採用。アーキテクチャ文書テンプレートで網羅的な詳細設計（全画面定義・CRUD・DB 物理）の受け皿が弱く、翻案物への ShareAlike 継承義務も showcase 配布物には負担。

## 層の対応と二文書の境界

上流 / 下流の二段 (schema.yaml の節構成) をもう少し細かく切ると次のとおり。用語 はどの層にも属さない横断要素で、要求仕様書の用語集に置く。

| 層 | 29148 / 1016 での呼び方 | 日本の SI での呼び方 | 本 showcase | 文書 |
|---|---|---|---|---|
| 業務 | BRS (事業要求)、OpsCon の業務モデル | 業務分析、業務フロー | プロセス、データストア、外部エンティティ、フロー (階層 DFD) | 要求仕様書 |
| 利用者の視点 | StRS (ステークホルダ要求)、OpsCon の運用シナリオ | 要件定義の業務要件、システム化業務説明 | ユースケース、アクター | 要求仕様書 |
| ソフトウェア要求 | SRS 3.2 Functions ほか (要求文) | 要件定義の機能・非機能要件一覧 | 要求 | 要求仕様書 |
| 外部設計 | SRS 3.1 External interfaces / 3.5 Logical database と SDD の両方に跨る | 基本設計 (画面設計、論理データモデル、CRUD) | 画面、エンティティ、データアクセス | 設計書 |
| 方式設計 | SDD の System architecture (ソフトウェアの分解と、添え物としての配置) | 基本設計のサブシステム分割・機能構成、方式設計のシステム構成 | コンポーネント (+ 配置の prose) | 設計書 |
| 内部設計 | SDD (1016 の Logical / Structure 等) | 詳細設計 (テーブル物理定義、クラス設計) | (対象外) | — |

29148 と日本の基本設計が重なるのは外部設計の層で、重なりが強いのはエンティティ (SRS 3.5 の中身はほぼ論理データモデル)、弱いのが画面 (3.1 が求めるのはインタフェースへの要求で、項目・アクション・遷移の定義は 29148 でも設計寄り)。本 showcase は日本の束ね方 (基本設計 = 設計書) を ja / en の両方で採る。文化差はモデルではなく束ね方にあるので、29148 寄りに束ね直す派生を作るなら動かすのは章の割り当てだけで済む。

要求と画面 / エンティティの間に直接の参照は無く、ユースケース経由で辿る。トレーサビリティ (要求 ↔ 設計) で設計要素から要求へ直接張りたくなった場合は、規律に従い 画面 / エンティティ → 要求 の向きで足す。

## 章立ての判断

目次はモデルから導出されるビューの一つで (29148 も IPA も章の並びは自由裁量と明記)、章 → ソース の対応は schema.yaml の description と views が持つ。ここには章立てを決めた際の典拠と判断だけを残す。

- **要求仕様書**は 29148 SRS 例示アウトライン (8.5.2) に informed by。BRS / StRS の層は 1 章に畳む (29148 自身が NOTE で「StRS と BRS は多くの業界で同一視され、結合してよい」と明記)。1 章に業務コンテキスト (レベル 0 = コンテキスト図) とシステム化範囲 (葉プロセス × ユースケース) を置くのは、29148 の 1.2 Scope / 1.3 Product perspective の位置に業務の境界と範囲が来る形にし、システム化範囲の導出という業務モデル同梱の主目的を付録の奥に沈めないため。4 章 (検証) は 3 章とパラレル (29148 SRS 4 の指定) で、同じ view を 検証方法 / 適合基準 の列で描き直す。要求属性は 29148 5.2.8 + Volere atomic requirement
- **設計書**は IPA の工程成果物 (画面編 / データモデル編) を日本の基本設計の慣行で束ねる。設計方針 (1.3) は 42010 の architecture decision / rationale に対応。3 章 (システム構成) は英語版の SDD に骨格を与えるために足した章で、分解の粒度は業務の単位 (サブシステム分割)、利用者から見えない横断の部品 (在庫) を独立させることで機能一覧の再掲ではなくソフトウェアの分解だと読める形にした。英語圏の SDD は分解が中心で配置は添え物なので、配置は章末の prose。ユースケースの一覧 (IPA システム化業務一覧) は設計書に再掲せず、要求仕様書へのリンクで参照する。API 仕様・シーケンス図・帳票・バッチは [Candidates](#candidates-未タスク化) として将来の章に空けてある
- **業務モデル (階層 DFD) の同梱**。独立の showcase にせず要求仕様書の付録に同梱したのは、ユースケース → プロセス の参照が下流から上流への向きで規律に適合し、「本体が付録を参照する」のは文書配置 (テンプレート) の問題でデータの層とは別だから。同梱で得られるのは、層の表の業務行が埋まり四層が一つのデータで通ること、ユースケース → 葉プロセス からシステム化範囲が導出できること (Volere の work context → business events → product use cases と同じ構造)、エンティティ → データストア の参照が張れること (構造化分析の DFD → データ辞書 → ER の系譜)。項目定義の典拠: IPA ガイドに DFD は存在しない (データの流れは業務フロー / バッチ処理フロー / 外部システム関連図に分散) ので、構造化分析の古典 (DeMarco / Yourdon。レベル分割・バランシング規則は文献上厳密に定義されている) と IPA 外部システム関連図の凡例を参考に自作した。バランシング検査の規則は行を跨ぎ階層を辿る述語で view 言語では書けないため、view ではなくテンプレートのマクロで検査し、付録末尾の節に不一致を表で出す。ビルドの警告に載せる経路は[ツール側の検討事項](#showcase-で表面化したツール側将来の検討事項-未起票)

## 英語版 (S10) の判断

- **別プロジェクトとして複製する**。同一モデルから両言語を出す案は採らなかった。識別子が日本語なので、同じデータから両言語を出すには識別子を二重に持つ拡張が要り、showcase の読みやすさ (改変の見本) を損なう。ja / en の構造同一性の検査は[ツール側の検討事項](#showcase-で表面化したツール側将来の検討事項-未起票)
- **章の割り当ては動かさない**。日本の基本設計の内容は 29148 の区分ではかなりの部分が SRS 側 (3.1 / 3.5) に入るので章の割り当てを変える余地を残していたが、設計書にシステム構成章が入ったことで、英語圏の SDD の雛形 (Introduction / System overview / Architecture / Data design / Interface design) と章立てが並びまで一致した。Data design は英語圏でも SDD の標準の章なので、29148 3.5 Logical database に合わせて論理データモデルを SRS 側へ移す必要は無い。移すと設計書から要求仕様書へのリンク (二文書 showcase の主題) が片側に偏り、ja と en の章の対応も崩れる。判断の基準は規格の条文との突合ではなく、英語圏の読者が見出しを見て「よく見る SRS / SDD だ」と思えるか
- **SDD は "Software Design Document"**。1016 の "Description" ではなく英語圏の雛形で多い語を採った (1016 は章に被せない方針なので名前も借りない)
- **ja も製品として残す**。日本語は英訳の作業言語に留めず、日本の従事者向けの見本として ja / en の両方を保つ。ja の識別子・enum 値は日本語のまま、英名の付記規約を ja / en の対応を保つ手段として維持する

## Candidates (未タスク化)

今回の二文書の目次には入れず、将来の章として埋める:

- **HTML プロトタイプは範囲外 (詳細設計の領分)** — 線は HTML という形式ではなく忠実度に引かれている (ワイヤーフレーム水準の HTML は contents に入っている)。contents に .html を置くと blob (`text/html`) として両版の出力と Hugo の site にそのまま複製されることは実機で確認した (iframe で埋めることも、リンクで開くこともできる) が、部品の見た目や操作感まで固めた HTML モックは基本設計ではなく詳細設計の成果物なので、この showcase (外部設計まで) には載せない。同様に、画面定義に要素 ID (`data-testid` 等、E2E テストのロケータ) の列を置く慣行は、E2E テスト仕様 (何を確かめるか) が基本設計から導かれるのに対し、要素 ID はテストスクリプト (どう触るか) と実装の契約で詳細設計の決定という整理。同じレコード (画面.入出力項目) を基本設計が 名前 / 入出力 / 参照先 まで埋め、詳細設計が 要素ID を書き足す「一つのレコードを複数の工程が育てる」型で、要素 ID は規約 (`画面ID-項目名`) を上流で決めれば導出できる列になる。詳細設計の showcase を作るときの手掛かりとしてここに残す
- **構成図の図法 (C4 系)** — 設計書 3 章のコンポーネント図は コンポーネント.依存 から `flowchart` で描き、配置図は prose の手書き。Mermaid `C4Context` / `C4Container` や `architecture-beta` で描き直す案は図法の置き換えで、配置 (端末 / サーバ / 外部サービス) まで構造化して一つの図法に載せるかの判断を伴う。後者は v11 でも beta 扱いで機能成熟度未確認。アーキテクチャ記述の標準は ISO/IEC/IEEE 42010
- **シーケンス図** — ユースケースのシナリオの図示。Mermaid sequenceDiagram。設計書の将来の章の候補 (ユースケース図は設計書 2 章のコンテキスト図として `flowchart` で実現した)
- **API / インタフェース仕様** — エンドポイント / リクエスト / レスポンス / エラーの構造化記述。OpenAPI 風だが本ツール独自スキーマで authoring する形。IEEE 1016 の interface viewpoint に対応
- **帳票定義** — IPA 帳票編 (帳票一覧 / 帳票概要 / 帳票項目説明) を項目典拠に。帳票項目 → 参照先エンティティ・カラムのクロスリファレンスを持ち、文書間同期の題材として筋が良い。帳票の存在自体は日本特有ではないが、二文書テーゼの実証に必須でないため今回は範囲外
- **バッチ処理定義** — IPA バッチ編 (バッチ処理一覧 / バッチ処理フロー / バッチ処理定義) を項目典拠に。処理サイクル / 起動方式 / 再処理方式などの項目定義を持つ

### showcase で表面化したツール側・将来の検討事項 (未起票)

showcase の設計対話で見つかったが、showcase タスクの範囲外として起票を保留しているもの。起票先はツール本体のタスクか本ファイルの Candidates。目次確定の過程で表面化した文書ノードは E17 として起票済み (前提は M13)。

- **`{% include %}` / `{% import %}` の文書化**: 動くが `docs/reference/template.md` に記述が無い (template-trust-model の loader の節で触れているのみ)。root テンプレートの分割手段 (include) と、テンプレート間でマクロを共有する手段 (import。業務モデルの 業務マクロ.md で実機確認、再帰マクロも動く) として記述する。小さな docs PR
- **string 配列への x-ref**: `items: { type: string, x-ref }` を許す拡張。現状はオブジェクト配列に包む
- **入れ子要素への x-ref**: x-ref はエンティティの ID しか指せず、エンティティ配下の 属性[] の要素は指せない。画面.入出力項目.参照先.属性 と エンティティ.属性.参照.属性 は素の文字列で、属性名の綴り違いはビルドで検出されない。親 ID + 子要素の名前 (複合キー) を指す x-ref の拡張か、view による突合 (CRUD マトリクス・画面定義の章) を検討する
- **上流のsbdb プロジェクトの参照 (依存)**: 要求を発注者側、設計をベンダや AI のリポジトリで持つ運用では、別のsbdb プロジェクトの entity を読み取り専用で x-ref の対象にし、版を固定する機能が要る。参照の向きの規律はこの分割を可能にする前提
- **suspect link (要確認リンク)**: 要求に版を持たせ、設計側の参照が設計時の版を持てば、要求変更で古くなった設計要素をビューで導出できる (新規要求の孤児検出と対)。トレーサビリティ表の増分で載せる候補。多対多で強いられた `{ID, 版}` のオブジェクト配列の形がそのまま使える
- **スコープ管理と FP 概算**: 要望一覧 / リリース計画 / FP 概算は別の文書群ではなく、同じレコードのスコープ確定前の姿 (要求・ユースケースに状態と対象リリースを持たせ、二文書は「採用」の部分集合を描くビュー)。FP が数える要素 (論理ファイル = エンティティ、トランザクション = 画面のアクション・外部インタフェース) は本 schema にあるので概算はビューで導出できる。showcase の範囲外 (showcase はスコープ確定後の文書を描く) だが製品動機に近い
- **プロジェクト管理成果物の showcase**: ステークホルダ登録簿や RACI など PMBOK 系の成果物は「表を構造化データから導出する」題材として筋が良い
- **ja / en 変種の構造同一性テスト**: 両版を製品として保つので、名前を除いて schema の形が一致することを検査する仕組みが要る
- **同じ subject を二度 render すると subject の anchor が二重に出る**: 一時期あった設計書の機能一覧が要求仕様書の主要機能と同じ `ユースケース | render(...)` で、一ページ (index.md) に `<a id="/ユースケース">` が 2 つ出た。ビルドは通り (`--strict` でも警告無し) リンクは先勝ちで着地するが、HTML の id 重複ではある。同じコレクションを二章で描く構成では起こりうるので、ツール側で 2 つ目以降を抑止するか警告するかを検討する (重複アンカーパスの検出 B15 に隣接)
- **anchor の所在とリンクの向き先の食い違いを検出できない**: リンクの向き先の頁はデータ上の位置で決まるので、`node()` で引いたノードを別の頁 (split された他レコードの頁) に `| anchor` で描くと、anchor はそこに出るのにリンクは home の頁を指す。ビルドは通り `--strict` も警告しない (実機確認済み。定石は join view)。anchor が home 以外の頁に出たら警告する検査があると、この取り違えを早く引き当てられる
- **マクロの戻り値の再エスケープ**: autoescape を切っているので Jinja マクロの戻り値は素の文字列になり、`{{ macro() }}` で呼ぶと `link` の出力までエスケープされる (実機確認済み)。症状は docs の Markdown escaping の節から辿れ、`| safe` か `{% set %}` で回避できるが、同節は `| safe` をコードスパン / フェンス / Mermaid の話として書き、`link` 等は「`| safe` 不要」と明記しているので、マクロ経由だと要るという例外が読めない。同節に一行足す (小さな docs PR)
- **コードフェンスの中のリンクが HTML 版で外れる**: Mermaid の `click` に `href` の URL を埋めると、出力 Markdown では正しいのに、コードフェンスの中なので Markdown から HTML への書き換えが効かず、`.md` のまま残って HTML 版で 404 になる (実機確認済み)。図の中からのリンクは現状どの図法でも張れない。図が大きくなる章 (5 の画面遷移図) でも効いてくるので、フェンス内の URL を edition に合わせて解決する手立て (専用フィルタ等) を検討する余地がある
- **テンプレートが見つけた不整合をビルドの警告に載せる経路**: 業務モデルのバランシング検査は付録の表として可視化するだけで、ビルドは通り `--strict` も止まらない。データの整合性規則のうちスキーマ (x-ref、`oneOf` 非対応の「ちょうど 1 つ」) で言えないものを view やテンプレートで検査する形は他の章 (属性名の突合など) にも広がるので、テンプレートからビルドの警告インフラに載せる手立て (例: 警告を発するフィルタ / 関数で、`--strict` なら失敗させる) を検討する
- **Mermaid flowchart の適合性 (PlantUML 等への舵切り)**: 業務モデルの DFD は読めたが、flowchart は構造化データからの自動レイアウトに向かないと評価しており、図が大きくなる場合 (分解の深い業務、5 章の画面遷移図) の評価は未了。舵切りの判断材料が要る
- **空の contents / views ディレクトリ**: 無いとビルドが失敗するため `.gitkeep` で保持している。無くても通る方が親切
