# システム開発ドキュメント (appendix)

[システム開発ドキュメント](../../../20-design/80-showcase/10-system-dev-docs.md) の背景。

## 調査の帰結: モデルファースト

「要求仕様書 + 設計書」をそのまま書ける、無料で再配布可能な既製テンプレートは存在しない。各資料が持つのは断片で（29148 は目次はくれるが節の内容定義は有償、IEEE 1016 は文書テンプレートを規定しない、IPA は成果物の項目定義は完全だが文書の目次を持たない、arc42 / Volere は完全なテンプレートだがライセンスと守備範囲が合わない）、目次を寄せ集めても「標準のラベルを着た我流」にしかならない。一方、標準はモデル（スキーマ）の水準では実体のある定義を持つ（42010 の概念モデル、1016 の viewpoint 仕様、ReqIF のメタモデル、IPA の項目定義とクロスリファレンスから復元できる暗黙の ER モデル）。そこで、よりどころは目次ではなくモデルに置く。帰結:

- **項目の典拠は成果物の系統ごとに一つに絞る**。設計書側の相互参照型の成果物 (画面 ⇔ 入出力項目 ⇔ エンティティ、CRUD) は IPA ガイドの項目定義、要求仕様書側は 29148 (+ Volere) の要求属性。42010 の概念モデルは文書の枠組み (ビューポイント = schema の定義の束、ビュー = 章) を理解する道具として使い、データには持たない。ステークホルダは SRS / SDD に登場せず、関心事は要求と rationale に化けるので持たない。ユースケースのアクターはステークホルダとは別物で、上流の独立エンティティとして持つ
- **モデルの記述場所は showcase の schema.yaml そのもの**。抽出したモデルを別文書に起こさず、スキーマ + x-ref として書き、description に参照元を補記する (「IPA 画面一覧に対応」程度)。ビルドすれば `__defs/entities` / ER メタビューがモデルの図を出す
- **目次はモデルから導出されるビューの一つ**。章の並びは 29148 も IPA も自由裁量と明記しており、こちらで決めてよい。標準との対応は「何が記述され、どう関係づけられるか」の水準で取り、それも conformance ではなく description の典拠注記に留める
- **抽出は網羅しない**。サンプルに必要な範囲へのテーラリングと突合で済ませる。IPA の暗黙モデルを網羅的に抽出するほど翻案禁止条項に近づくため、部分的・自分の言葉での再構成が作業量でも法的にも安全側

## 典拠と借用の分担

| 資料 | 借りるもの | 転載上の制約 |
|---|---|---|
| ISO/IEC/IEEE 42010 | (採用せず) 概念モデルは文書の枠組みの理解に使うのみ | 概念モデル図は公式に無料公開。概念の利用は自由 |
| ISO/IEC/IEEE 29148:2018 | 章立ての素材 (SRS 例示アウトライン 8.5.2) と要求レコードの属性 (5.2.8) | 章題の翻案 + "informed by" 表記は確立した慣行で低リスク。本文の逐語転載・アウトライン図の複製は不可 |
| IEEE 1016-2009 | (採用せず) viewpoint 一覧は調査時のメニューとして使ったが、本 showcase の章には被せない | 2020 年 Inactive-Reserved (10 年無改訂への管理措置、技術的否定ではない) |
| IPA 機能要件の合意形成ガイド | 各 artifact の項目定義 (画面 5 成果物 / エンティティ一覧・定義 / CRUD 図 等) | 複製許諾は目的限定付きで翻案禁止条項あり。項目名・構成をアイデアとして借り、定義文は自分の言葉で再設計し、出典を明記する |
| Volere | atomic requirement のレコード属性 (fit criterion / rationale / 優先度 等) | 27 節テンプレートのツール同梱・再配布は要許諾 (redistribution license の明記あり)。属性名 subset + attribution に留める |
| OMG ReqIF v1.2 | スキーマ設計原理 (型と値の分離 / 要求実体と文書階層の分離 / 関係自身が型と属性を持つ) | メタモデル概念の利用は自由。仕様文書の転載のみ不可 |

29148 の規範本文（有償）は購入しない。目次骨格と要求属性は無料の正規プレビューと二次文献で確定でき、規範本文が要るのは conformance を名乗る場合だけ。arc42（CC BY-SA 4.0）は骨格候補として調査したが不採用。アーキテクチャ文書テンプレートで網羅的な詳細設計（全画面定義・CRUD・DB 物理）の受け皿が弱く、翻案物への ShareAlike 継承義務も showcase 配布物には負担。

## 層の対応と二文書の境界

上流 / 下流の二段 (schema.yaml の節構成) をもう少し細かく切ると次のとおり。用語 はどの層にも属さない横断要素で、要求仕様書の用語集に置く。

| 層 | 29148 / 1016 での呼び方 | 日本の SI での呼び方 | 本 showcase | 文書 |
|---|---|---|---|---|
| 業務 | BRS (事業要求)、OpsCon の業務モデル | 業務分析、業務フロー | プロセス、データストア、外部エンティティ、フロー (階層 DFD) | 要求仕様書 |
| 利用者の視点 | StRS (ステークホルダ要求)、OpsCon の運用シナリオ | 要件定義の業務要件、システム化業務説明 | ユースケース、アクター | 要求仕様書 |
| ソフトウェア要求 | SRS 3.2 Functions ほか (要求文) | 要件定義の機能・非機能要件一覧 | 要求 | 要求仕様書 |
| 外部設計 | SRS 3.1 External interfaces / 3.5 Logical database と SDD の両方に跨る | 基本設計 (画面設計、論理データモデル、CRUD) | 画面、エンティティ、データアクセス | 設計書 |
| 方式設計 | SDD の System architecture (ソフトウェアの分解と、添え物としての配置) | 基本設計のサブシステム分割・機能構成、方式設計のシステム構成 | コンポーネント (+ 配置の prose) | 設計書 |
| 内部設計 | SDD (1016 の Logical / Structure 等) | 詳細設計 (テーブル物理定義、クラス設計) | (対象外) | — |

29148 と日本の基本設計が重なるのは外部設計の層で、重なりが強いのはエンティティ (SRS 3.5 の中身はほぼ論理データモデル)、弱いのが画面 (3.1 が求めるのはインタフェースへの要求で、項目・アクション・遷移の定義は 29148 でも設計寄り)。本 showcase は日本の束ね方 (基本設計 = 設計書) を ja / en の両方で採る。文化差はモデルではなく束ね方にあるので、29148 寄りに束ね直す派生を作るなら動かすのは章の割り当てだけで済む。

要求と画面 / エンティティの間に直接の参照は無く、ユースケース経由で辿る。トレーサビリティ (要求 ↔ 設計) で設計要素から要求へ直接張りたくなった場合は、規律に従い 画面 / エンティティ → 要求 の向きで足す。

## 章立ての判断

目次はモデルから導出されるビューの一つで (29148 も IPA も章の並びは自由裁量と明記)、章 → ソース の対応は schema.yaml の description と views が持つ。ここには章立てを決めた際の典拠と判断だけを残す。

- **要求仕様書**は 29148 SRS 例示アウトライン (8.5.2) に informed by。BRS / StRS の層は 1 章に畳む (29148 自身が NOTE で「StRS と BRS は多くの業界で同一視され、結合してよい」と明記)。1 章に業務コンテキスト (レベル 0 = コンテキスト図) とシステム化範囲 (葉プロセス × ユースケース) を置くのは、29148 の 1.2 Scope / 1.3 Product perspective の位置に業務の境界と範囲が来る形にし、システム化範囲の導出という業務モデル同梱の主目的を付録の奥に沈めないため。4 章 (検証) は 3 章とパラレル (29148 SRS 4 の指定) で、同じ view を 検証方法 / 適合基準 の列で描き直す。要求属性は 29148 5.2.8 + Volere atomic requirement
- **設計書**は IPA の工程成果物 (画面編 / データモデル編) を日本の基本設計の慣行で束ねる。設計方針 (1.3) は 42010 の architecture decision / rationale に対応。3 章 (システム構成) は英語版の SDD に骨格を与えるために足した章で、分解の粒度は業務の単位 (サブシステム分割)、利用者から見えない横断の部品 (在庫) を独立させることで機能一覧の再掲ではなくソフトウェアの分解だと読める形にした。英語圏の SDD は分解が中心で配置は添え物なので、配置は章末の prose。ユースケースの一覧 (IPA システム化業務一覧) は設計書に再掲せず、要求仕様書へのリンクで参照する
- **業務モデル (階層 DFD) の同梱**。独立の showcase にせず要求仕様書の付録に同梱したのは、ユースケース → プロセス の参照が下流から上流への向きで規律に適合し、「本体が付録を参照する」のは文書配置 (テンプレート) の問題でデータの層とは別だから。同梱で得られるのは、層の表の業務行が埋まり四層が一つのデータで通ること、ユースケース → 葉プロセス からシステム化範囲が導出できること (Volere の work context → business events → product use cases と同じ構造)、エンティティ → データストア の参照が張れること (構造化分析の DFD → データ辞書 → ER の系譜)。項目定義の典拠: IPA ガイドに DFD は存在しない (データの流れは業務フロー / バッチ処理フロー / 外部システム関連図に分散) ので、構造化分析の古典 (DeMarco / Yourdon。レベル分割・バランシング規則は文献上厳密に定義されている) と IPA 外部システム関連図の凡例を参考に自作した。バランシング検査の規則は行を跨ぎ階層を辿る述語で view 言語では書けないため、view ではなくテンプレートのマクロで検査し、付録末尾の節に不一致を表で出す。ビルドの警告に載せる経路は[ツール側の検討事項](#showcase-で表面化したツール側将来の検討事項-未起票)

## 英語版の判断

- **別プロジェクトとして複製する**。同一モデルから両言語を出す案は採らなかった。識別子が日本語なので、同じデータから両言語を出すには識別子を二重に持つ拡張が要り、showcase の読みやすさ (改変の見本) を損なう。ja / en の構造同一性の検査は[ツール側の検討事項](#showcase-で表面化したツール側将来の検討事項-未起票)
- **章の割り当ては動かさない**。日本の基本設計の内容は 29148 の区分ではかなりの部分が SRS 側 (3.1 / 3.5) に入るので章の割り当てを変える余地を残していたが、設計書にシステム構成章が入ったことで、英語圏の SDD の雛形 (Introduction / System overview / Architecture / Data design / Interface design) と章立てが並びまで一致した。Data design は英語圏でも SDD の標準の章なので、29148 3.5 Logical database に合わせて論理データモデルを SRS 側へ移す必要は無い。移すと設計書から要求仕様書へのリンク (二文書 showcase の主題) が片側に偏り、ja と en の章の対応も崩れる。判断の基準は規格の条文との突合ではなく、英語圏の読者が見出しを見て「よく見る SRS / SDD だ」と思えるか
- **SDD は "Software Design Document"**。1016 の "Description" ではなく英語圏の雛形で多い語を採った (1016 は章に被せない方針なので名前も借りない)
- **ja も製品として残す**。日本語は英訳の作業言語に留めず、日本の従事者向けの見本として ja / en の両方を保つ。ja の識別子・enum 値は日本語のまま、英名の付記規約を ja / en の対応を保つ手段として維持する
