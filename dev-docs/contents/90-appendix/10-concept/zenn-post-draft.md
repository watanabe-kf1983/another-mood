## 上流工程の成果物作成における課題

### 「Excel作業」がなんかツライが・・・

システム開発の上流工程では、Excelが欠かせません。その最大の理由は、「ステークホルダー全員が読み書きできるフォーマット」であることにあります。

一方、Excelが嫌がられる理由もあって、こんなところかと思います。

- Diffがみれない！ソースリポジトリに同梱できない
   - GitHub 等 のソースベースのワークフローとの断絶
   - 実装の近くに仕様を置けない
     - コーディングエージェントに読み書きさせづらい

Excelドキュメントは、それを必要とする人とのコミュニケーションに限って作成・運用し、それとは別に設計書の正本はソースリポジトリにMarkdownで書く。というのがやり方の一つです。

では、これで解決するのでしょうか？ むしろ、「ExcelとMarkdown相互の翻訳コスト」に加え、「Excel作業と同じ作業をMarkdownでやる羽目」が生じ、苦しみが増すことになりはしないでしょうか？

ここで考え直すべきは、「Excel作業」でそもそも何が強いられているか、です。

### 工程の本質：「型付き」のモノの列挙

システムの要件定義書や設計書には、お定まりのような「型」をもつモノがあります。そして、そのモノの顔ぶれや属性こそが、システムの各種要件や仕様を定義します。

  - 画面
  - ファイル
  - トランザクション機能
  - etc...

多くの場合、設計上のそれは、システムに実装されるモノと 1対1 の関係になります。ステークホルダーと合意された内容を、これらの「モノ」としてリストアップし、属性を定義すること。これが上流工程の多くの部分を占めると言って良いでしょう。

上流工程の成果は、あるセクションは散文で書かれますが、多くの部分が表で書かれる理由は、おそらくそのためです。「表」は多くの場合、「型」を持ったモノの集合の表現形態でしかありません。

Excelの設計書のテンプレートは、「まだ埋められていない表を埋めよ」という形で、上流工程の作業を要求します。作業者はこの穴を埋めることに専念する。もちろん、穴は合意された内容だけでは埋まらないことがあります。埋まらない穴や、埋めてみて見つかる不整合は、まだ誰にも問われていない問いです。それをステークホルダーに投げ返すことも、「穴を埋めること」のうちに含まれています。

いずれにせよ、Excel がこの工程で使われ続けるのは、表を書きやすい UI だからというだけでなく、この工程そのものが表を求めるからでもあるのです。

### 列挙された「モノ」同士の関連を保つ

ところで、「モノ」同士は関連を持ち、その関連自体が成果を構成する、という点にもシステム開発の上流工程の特徴があります。

たとえば、画面は複数の画面イベントを持ち、画面イベントは属性として遷移先画面を持ちます。そしてもちろん、遷移先画面は画面の一つを指し示していなければいけません。また、たとえば、CRUD図の縦と横はそれぞれテーブルと機能を指し示していなければいけません。

そうやって「モノ」同士の関係性、整合性を保ってドキュメントを作成するわけですが、ドキュメントは工程が終わるまで（終わってからも）常に動き続けます。たとえば、画面名称の名づけがふさわしくないことに気付く。予算の関係上画面を1つ削除することになる。などなど。画面名称を修正する場合、その画面を参照する場所、その全てを修正をする必要が生じます。

このあたりのメンテナンスコストは、Excelだからと、Markdownだからというものではありません。また、この手の手間をLLMに委ねるのは大変不安定だと思います。そもそも **LLMには翻訳と転記を行わせ、検査は機械にやらせる**のが得策ですし。


### 強制させるべき「型」や「参照整合性」はプロジェクト固有

お決まりの「型」や「整合性」を守らせるしくみさえあればよいのなら、それこそ Webフォームでそれらをバリデーション付きで入力させるSaaSはなぜ現れないのでしょうか？

なぜなら、システム開発プロジェクトは、プロジェクトごとに「設計書の型」「ラインナップ」が異なり、カジュアルにテンプレそのものを変更したくなるものなのですね。

「このプロジェクトではこの列使わないから削ろう」「列を足そう」「表そのものを端折ろう」「新しい章を増やそう」。いわゆる **テーラリング** です。これは **工程の途中で日常的に発生します。**

なぜテーラリングが必ず発生するか。いろいろな要因がありますが、大きなものとして、プロジェクトごとに「決定の順序の違い」があります。たとえば、画面要件、帳票要件、システム間I/F要件、非機能要件。ステークホルダーはどの要求を具体的にもち、どの要求は融通が利き、どの要求は動かせないか。状況によって、各要件の決まる順序は変わりますよね。

## 結局、何が求められているか

今までの話をまとめると、上流工程におけるドキュメント成果物に、求められる **業務要件** はこうなります。

- 記述内容には、画面、機能、ユースケースなど「型」を持つモノが並び、これらは必要な属性を備えていなければいけない
- 守るべき「型」や「属性」は、プロジェクトやフェーズに応じて、機動的に採否を選択されなければならない
- 画面、機能、ユースケースなどは相互に関連をし、この関係は不整合なく定義され、相互を参照できる形になっていなければならない
- ステークホルダーが読み書きする形式（多くの場合Excel）で確認資料を出せること。ただしそれが正本である必要はない

以上を踏まえ、ドキュメントを執筆するためのツールに対する要求を **システム化要件** にするとこうなります。

- **DRYに書かれた内容**を、一覧や詳細ページ、Mermaid図 などに同時に出力できる
- ドキュメント化される **モノの型** は **利用者が定義可能** で、その更新差分もGit管理可能
- **モノ同士の参照関係**を、**ハイパーリンク**で表現できる
- モノの型や、参照整合性の **違反**は **機械的にチェックされる**
- 内容は**テキストベースでサーバレスに永続化**され、更新差分をGitで管理できる
- 後続工程にとっての可読性・加工性が担保されたフォーマットでデータを保持

この、当たり前に誰もが使いそうなツール、本当にないのでしょうか？ 

近いものならあります。要件のトレーサビリティ管理が目的なら sphinx-needs や StrictDoc、Doorstop が成熟しています。RDBのスキーマが正本で、そこから設計書を派生させたいなら tbls。静的サイトを組みたいだけなら Astro や Hugo。

ただ、「型を自分で定義し、一つのデータから複数の文書を組み立て、参照の実在をビルドで検査し、平文とCLIだけで完結する」という組み合わせを一つのツールでやっているものは、2026年10月時点で見つけられませんでした。

というわけで、私が作ってみた小ツールが Another Moodです。

## Another Mood は何をするか

### Another Mood とは何か

Another Moodは、**利用者自身の手で** 作成・更新されるテキスト形式のファイル群を読み、整合性をチェックし、その結果としてドキュメントを出力するCLIツールです。

ファイル群の例が [こちら](https://github.com/watanabe-kf1983/another-mood/tree/main/showcase/system-dev-docs-ja)で、Another Moodが それを読んで出力した結果が[こちら](https://watanabe-kf1983.github.io/another-mood/showcase/system-dev-docs-ja/)です。

### 動かしてみる

[Another Mood](https://github.com/watanabe-kf1983/another-mood) をインストールしてみてください。

Python ( >= 3.12 ) がある環境なら

```sh
pipx install another-mood
```

もしくは、[uv](https://docs.astral.sh/uv/) をインストールして

```sh
uv tool install another-mood
```
でインストール完了です。


```sh
mood blueprint apply system-dev-docs-ja sample
mood watch sample
```

で冒頭で紹介したサンプルをご自身のPCで動かし、ブラウザで Another Moodが出力したドキュメントを確認することができます。


### ソースベースDBの構成

Another Moodが読み取るファイル群のことを、**ソースベースDB** と名付けています。CRUDやトランザクションの機能がないのにDBと呼ぶのは、これらのファイル群が持つ内容が、型と参照整合性を保持するためです。

[実物](https://github.com/watanabe-kf1983/another-mood/tree/main/showcase/system-dev-docs-ja)を見ていただければ、なんとなく、なるほどと思っていただけるはずですが、ポイントを簡単に説明します。

![ソースベースDBの構成](https://static.zenn.studio/user-upload/4b59c2275519-20261101.png) 

主な構成要素は次の四つです。

- 型定義
- 内容
- 文書テンプレート
- ビュー

#### 型定義：JSON Schema により 内容の型を定義
RDBでいうところのテーブル定義（DDL）に当たるのが [schema.yaml](https://github.com/watanabe-kf1983/another-mood/blob/main/showcase/system-dev-docs-ja/definition/schema.yaml) です。この記法は **[JSON Schema](https://json-schema.org/) のサブセット**なので、Open API、Swaggerなどで馴染みのある方が多いと思います。
![schema.yaml](https://static.zenn.studio/user-upload/e41c128e70c5-20261101.png)

#### 内容：YAMLファイルで 内容を記述
データの内容は [contents/](https://github.com/watanabe-kf1983/another-mood/blob/main/showcase/system-dev-docs-ja/contents) 配下に**YAMLファイル**で書きます。その内容が、schema.yamlの定義や制約から違反していた場合は、誤っている箇所をツールがエラーとして出力します。

また、このcontents/ 配下には、Markdownの文章の断片や png, svg 画像など、設計書に埋め込みたい資材も格納できます。
![YAMLで定義されたデータの内容](https://static.zenn.studio/user-upload/f83ed05857cc-20261101.png)

#### 文書テンプレート：Jinja2記法による Markdown文書のテンプレ
Markdown文書出力は、 [templates/](https://github.com/watanabe-kf1983/another-mood/tree/main/showcase/system-dev-docs-ja/definition/templates) に **Markdown を [Jinja2テンプレート記法](https://jinja.palletsprojects.com/en/stable/templates/)** で定義します。なお Jinja2というのは、Python界隈でデファクトスタンダードとなっているテンプレートエンジンのことです。

![Markdown文書のテンプレ](https://static.zenn.studio/user-upload/1351f5239a6c-20261101.png)

#### ビュー：SQLに似た語彙のクエリで、ビューを定義
ビューは、DRYに書かれたデータ同士をつなげあわせて文書に登場させたい、もしくは文書テンプレートを簡潔に記述したい場合などに定義します。これはRDBのビュー（Microsoft Accessのクエリ）とほぼ同じと考えて良いです。

ビューの定義は [views/](https://github.com/watanabe-kf1983/another-mood/blob/main/showcase/system-dev-docs-ja/definition/views) 配下に置きます。`select` `from` `join` `where`など、**SQLの語彙を借用した[このツールの言語](https://github.com/watanabe-kf1983/another-mood/blob/main/docs/reference/view.md)** で**YAMLファイル**に書きます。

![ビューの定義](https://static.zenn.studio/user-upload/673aa9d7e050-20261101.png)

### Another Moodが 動くと

このCLIツールの中核的なコマンドは `mood build` ただ一つです。
```sh
mood build sample
```
このコマンドを実行すると、`sample/` ディレクトリが読まれ、内容の整合性のチェックが行われたうえで
- `.another-mood/sample/output` 配下に Markdown ファイル
- `.another-mood/sample/site` 配下に HTML ファイル

が出力されます。

![Another Moodの出力](https://static.zenn.studio/user-upload/acf9a6e2f299-20261101.png)

データの更新のつど `mood build` して結果を確認するのは面倒ですから、更新を検知するたびに `mood build` してブラウザを再描画する機能が備わっています。これが `mood watch`です。

## Another Mood をどう使うか

### 内容は AIエージェントに書かせましょう

JSON Schema や、Markdown Jinja2テンプレート、Mermaid.js、ビュー定義など、一つ一つはヒトが書けるものではあります。しかし、それなりの学習コストがかかりますし、そもそも上流工程に携わる人々に、そのスキルを求めること自体がどうかという気がします。

一方、AIエージェントは、JSON Schemaも、Jinja2記法も、Markdownも、Mermaid.jsも、全て知っています。取説も苦にせず読みます。

したがって、こんな進め方をするとよいでしょう。

1. ヒトは `mood watch`で 出来上がりのドキュメントをブラウザで眺める
1. ヒトは AIエージェントに修正指示を与える
1. AIエージェントはソースベースDBを更新。エラーが起きたら対応
1. ヒトは 与えた指示通りに更新されているかどうかブラウザで確認し **2.** に戻る

### 生成されたMarkdownは `.gitignore` するのが良いでしょう
**ソースベースDB**は、その内容が 簡潔かつDRYにYAMLで表現されています。したがって、**更新前後のDiffは、まさに更新内容そのもののみがDiffとして現れるはず**です。

一方、**生成されたMarkdown**は、ソースベースDB側の少しの修正でもその**変更箇所が大量**になります。したがってこちらは `.gitignore` するのがいいんじゃないかと思います。

ただし、ヒトは設計書をいつでも、すぐ、見たいもの。その欲求を叶えるためには、CIワークフローで `mood build` でHTMLを生成し、関係者全員が見れるところにホスティングしておくのがスマートなやり方だと思います。

### ExcelでやりとりするステークホルダーとのI/F
Another Moodには Excelファイルの入出力機能はありません。正本の最適なありかたがプレーンなYAMLである以上、それ以外のフォーマットでの出入口をツールが抱える必要がない、という判断です。

しかし、Excelでやりとりする場面がなくなりはしません。この記事の冒頭で以下の問題提起をしました。

> Excelドキュメントは、それを必要とする人とのコミュニケーションに限って作成・運用し、それとは別に設計書の正本はソースリポジトリにMarkdownで書く。というのがやり方の一つです。
> 
> では、これで解決するのでしょうか？ むしろ、「ExcelとMarkdown相互の翻訳コスト」に加え、「Excel作業と同じ作業をMarkdownでやる羽目」が生じ、苦しみが増すことになりはしないでしょうか？

この問いに答えるなら、

「Excelドキュメントは、それを必要とする人とのコミュニケーションに限って作成・運用し、それとは別に設計書の正本は **ソースリポジトリにAnother Moodで書く**」

がこの記事の提案です。

「Excel と Another Mood 相互の翻訳コスト」は残ります。ただ正本側の内容が構造化されているため、コストは減っているはずです。受け取ったExcel資料はAIエージェントに読ませ、Another Mood 管理の正本を必要に応じ更新。一方でAnother Moodの設計書の一部を Excelで渡したい場合には、AIエージェントにYAMLの内容をそのまま openpyxl などのライブラリで、Excel化させるのが良いでしょう。

なお、Another Mood は Markdownファイルを出力しますので、他のフォーマット（Microsoft Wordなど）への変換には pandocなどのドキュメントコンバータも利用できます。
