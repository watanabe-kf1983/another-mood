## 競合調査: 汎用ドキュメント生成ツールの空白 (2026-10-15)

2026-10-15 の調査の記録。公開 (Q3) に先立ち、「既存ツールで置き換えられるなら本リポジトリを破棄する」という選択肢を検討するために行った。Claude の調査エージェントが六領域 (静的サイトジェネレータ、スキーマ先行ツール、要件管理、モデル駆動アーキテクチャ、文書自動化と DIY、日本語圏) で約 80 システムを当たり、その結果を一本の報告に合成したもの。採点の軸 A–F は本ツールの働きを書き出したものなので、他ツールが点を落とすのは定義上そうなる。報告が答えているのは優劣ではなく「同じ組み合わせをやっているものが他にあるか」だけであり、各ツールが力を注ぐ軸 (変更影響の検出、LSP、図のレイアウト、Web エディタ、要件管理の語彙、実物からの逆生成、Office 出力) で採点すれば本ツールが落ちる。報告は作者宛ての文体のまま残し、未検証事項は末尾に明記してある。

**結論を先に言う。2026 年 10 月 15 日時点で、A（利用者定義の入れ子データモデル）・B（ビルド時の参照整合性検査）・C（ビュー + テンプレートによる多文書生成）・D（Markdown と静的 HTML、自動相互リンク、散文と構造データの混在）・E（ドメイン非依存）・F（平文・CLI・オフライン・ロックインなし）を同時に満たす既製ツールは、六つの調査領域（静的サイトジェネレータ、スキーマ先行ツール、要件管理ツール、モデル駆動アーキテクチャツール、文書自動化と DIY、日本語圏）を横断して約 80 システムを当たっても見つからなかった。** したがって「既存ツールで置き換えられるからリポジトリを破棄する」という判断は根拠を持たない。最も近い候補は三つあり、それぞれ一つの軸で強く、別の軸で決定的に欠ける: **sphinx-needs 9.0.0（2026-10-14）** は B を本物の宣言的検査として実装しているが、データモデルは「need」一種に固定され、フィールドはプリミティブとその配列のみで入れ子オブジェクトを持てない ([sphinx-needs schema](https://sphinx-needs.readthedocs.io/en/latest/schema/index.html))。**Astro 7.x** は Zod で入れ子スキーマを検証するが、参照の実在検査は 2025 年 1 月の PR #12990 で意図的に外され、`getEntry()` が `undefined` を返すだけになっており、出力は HTML のみ、スキーマは TypeScript コードである ([withastro/astro#12990](https://github.com/withastro/astro/pull/12990), [#13268](https://github.com/withastro/astro/issues/13268))。**LinkML 1.12.1（2026-10-13）** は A/E/F を満たすが、`gen-doc` が文書化するのはスキーマであってインスタンスデータではなく、データ描画器 linkml-renderer は 2024-06 以降更新が止まった実験的プロジェクトである ([LinkML docgen](https://linkml.io/linkml/generators/docgen.html), [linkml-renderer](https://github.com/linkml/linkml-renderer))。DIY スタック（`jsonschema` + Jinja2 + MkDocs/Hugo）で A・C の半分・D の大部分は数日で組めるが、入れ子レコード群に対する FK 検査、宣言的 join/group ビュー、参照から導出される自動相互リンク、散文 Markdown のレコードへの束縛は、どのライブラリも提供せず、これを束ねたパッケージは GitHub 検索 7 本・PyPI・awesome リストのいずれにも存在しなかった（最上位ヒットは 5 スターの menagerie と 16 スターの yamldocs）([menagerie](https://github.com/Bwc9876/menagerie), [yamldocs](https://github.com/yamldocs/yamldocs))。日本語圏では tbls（RDB スキーマ固定）と商用 OBDZ（SaaS、Word/Excel 出力）が「一元化データから設計書を派生させる」唯一の製品であり、「YAML 原本 + JSON Schema + 自作スクリプト → Markdown」の個人記事が 2019 年から 2025 年まで繰り返し現れながら一つもツール化されていない ([tbls](https://github.com/k1LoW/tbls), [Qiita @endk 2019](https://qiita.com/endk/items/2ae6ab257f0ad42a3bd8), [note 2025](https://note.com/tasty_dunlin998/n/nba2533cdc161))。これは需要の証拠であって競合の証拠ではない。公開に踏み切ってよい。ただし公開時に「なぜ Astro / sphinx-needs / Jinja で済まないのか」を一行で答えられる準備が要る。その答えは本報告の第 4 節にまとめた。

### 最近傍 9 候補はそれぞれどの軸で欠けるか

**Astro content collections** は SSG の中で唯一、コレクション単位の宣言的スキーマを全エントリに強制し、Zod の `z.object` / `z.array` で任意の入れ子を表現できる ([Astro content collections](https://docs.astro.build/en/guides/content-collections/))。しかし B は「宣言はあるが遅延される」状態にある。PR #12990（2025-01-16 マージ）は「referenced entry exists のチェックを削除する、実行時にも検証するから」と明記し、Astro 5.3 で壊れた参照が受理されるようになった回帰について issue #13268 でメンテナは「期待どおりの挙動」と答え、別のメンテナが「6.0 で扱いたい」と述べたが、v6・v7 のアップグレードガイドに該当する変更はない ([#12990](https://github.com/withastro/astro/pull/12990), [#13268](https://github.com/withastro/astro/issues/13268), [v6 guide](https://docs.astro.build/en/guides/upgrade-to/v6/))。ランタイムの `createReference()` は id の実在を確かめずに `{id, collection}` を返し、`getEntry` は warning を出して `undefined` を返す ([runtime.ts](https://github.com/withastro/astro/blob/main/packages/astro/src/content/runtime.ts))。つまり描画されない参照や optional chaining で握った参照は黙って通る。加えて、スキーマは `src/content.config.ts` の TypeScript であって平文データ言語ではなく、Markdown を成果物として出す機構はなく、ビューは `getCollection` のフィルタコールバックと `getStaticPaths` のループを手で書く手続き的なもので、「生成コレクションのソート順は非決定的でプラットフォーム依存」と自ら明記している ([Astro content collections](https://docs.astro.build/en/guides/content-collections/))。欠ける軸は B（実質）、C（宣言性）、D（Markdown 出力）、そして A のうち「スキーマが平文データであること」。

**sphinx-needs** は B の最良の先行例で、JSON Schema 流の `needs_schema_definitions` にローカル制約と network 制約（`minContains` / `maxContains` / `network_back`、再帰 4 段）を書き、違反は Sphinx の error と `schema_violations.json` になる ([schema docs](https://sphinx-needs.readthedocs.io/en/latest/schema/index.html))。欠けるのは A の核心である。フィールド型は「Primitive types (string, boolean, integer, number) and array types of those」で「Array items must be one of the primitive types」、入れ子オブジェクトは型として存在せず、フィールドは `needs_fields` でグローバルに宣言され型ごとに別のフィールド集合を持てない（sphinx-modeling が存在した動機そのもの）([configuration.rst](https://github.com/useblocks/sphinx-needs/blob/master/packages/sphinx-needs/docs/configuration.rst), [sphinx-modeling](https://pypi.org/project/sphinx-modeling))。「テーブルとそのカラム」を表すには、カラム一つ一つを一意 ID を持つ need にして link で束ねる必要があり、ID 自動付与の要望は 2021 年から開いたままである ([#253](https://github.com/useblocks/sphinx-needs/issues/253))。データは RST/MyST ディレクティブとして書くか、自前で needs.json を作って `needimport` するしかなく、任意 YAML を読む経路はない ([needimport](https://sphinx-needs.readthedocs.io/en/latest/directives/needimport.html))。C は needtable / needflow / needuml という固定カタログで、Jinja は need 単位（`:template:` は一つの need に一つ）と needuml 内に限られ、join/group して任意ページを吐く仕組みはない ([need directive](https://sphinx-needs.readthedocs.io/en/latest/directives/need.html))。E も「needs/requirements and specifications」と自己定義し、カラムや画面を扱うと全てが ID・status・tags 付きの箱として描かれる。

**LinkML** は A と E と F を満たし、`gen-doc` は要素ごとの Markdown、Jinja2 テンプレート上書き、Mermaid/PlantUML/ER 図まで出す ([docgen](https://linkml.io/linkml/generators/docgen.html))。だがそれはスキーマの文書である。インスタンスデータの検証 `linkml-validate` は JSON Schema 変換経由でレコード間参照に触れず、参照整合性は別プロジェクト linkml-store の `--set ensure_referential_integrity=true` でのみ得られ、例は DuckDB/MongoDB へのロードを前提にする ([validating-data](https://linkml.io/linkml/data/validating-data.html), [linkml-store RI](https://linkml.io/linkml-store/how-to/Check-Referential-Integrity.html))。データから HTML/Markdown を出す linkml-renderer は「Status: experimental」、スタイル YAML 以外のカスタマイズは不可、Bootstrap 固定、Jinja なし、最終リリース v0.3.1 は 2024-06-26 以降 push がない ([linkml-renderer](https://github.com/linkml/linkml-renderer))。三つのプロジェクトに分散し、C と D のデータ側が未完成。

**LikeC4** は要素 kind と関係 kind を利用者が宣言でき、参照の不在（`'api' not found`）と曖昧（`'api' is ambiguous`）を error にし、`likec4 validate` が非ゼロ終了する点で B が強い ([references](https://likec4.dev/dsl/references/), [CLI](https://likec4.dev/tooling/cli/))。だが kind は表示と既定値のクラスであって record スキーマではなく、「kind `table` は型付き配列 `columns` を必須に持つ」とは書けない。metadata は文字列か文字列配列のみで、入れ子は要素の包含だけである ([model](https://likec4.dev/dsl/model/))。文書出力は図サイトと JSON / 型付きモデルで、Markdown は `likec4.config.ts` に TypeScript の生成器を書くか MkDocs プラグインで図を埋め込むかしかない ([custom generators](https://likec4.dev/tooling/code-generation/custom/), [mkdocs-likec4](https://likec4.dev/tooling/community/mkdocs-plugin/))。メタモデルの形（element / relationship / view / deployment）が固定なので E も欠ける。代替ではなく、`likec4 export json` を Another Mood の入力にする補完関係にある。

**textX と Langium** は言語ワークベンチであり、文法がメタモデル、`[Type:ID]` が参照、スコープ解決と検証フックがあり、textX-jinja は「反復可能な context 変数 → 要素ごとに 1 ファイル」という生成器まで持つ ([textX scoping](https://textx.github.io/textX/scoping.html), [textX Jinja](https://textx.github.io/textX/jinja.html), [Langium workflow](https://langium.org/docs/learn/workflow/))。欠けるのは、データが YAML/JSON ではなく自作 DSL になること、スキーマが JSON Schema ではなく文法になること、ビュー層・散文混在・サイト・自動相互リンクのすべてが自作になること。textX-jinja は 47 コミットでリリースがない ([textX-jinja](https://github.com/textX/textX-jinja))。両者の上に Another Mood を再現するのは「パーサの上に Another Mood をもう一度作る」ことに等しい。

**Semantic MediaWiki と Cargo** は C の概念的先行例として最も完成している。`#ask` は条件・printout・sort・limit・format を持ち、template 形式で各結果行を任意テンプレートに流し込め、Cargo の `#cargo_query` は join on / where / group by / having / order by を備える ([Inline queries](https://www.semantic-mediawiki.org/wiki/Help:Inline_queries), [Cargo Querying](https://www.mediawiki.org/wiki/Extension:Cargo/Querying_data))。失格要因は F と B。SMW 7.2.0 は MediaWiki 1.43–1.46 と PHP 8.1–8.5 を要求し、Cargo は MySQL/PostgreSQL（SQLite は「poorly tested」）を要求する ([SMW 7.2.0](https://www.semantic-mediawiki.org/wiki/Semantic_MediaWiki_7.2.0), [Extension:Cargo](https://www.mediawiki.org/wiki/Extension:Cargo))。データは wiki ページ内のテンプレート呼び出しとして DB に住み、Cargo の `Page` 型は実在検証を持たず `form=` で赤リンク値からページを作る前提、つまり不在参照を保存できる ([Cargo Storing](https://www.mediawiki.org/wiki/Extension:Cargo/Storing_data))。出力は wiki の HTML で Markdown も静的書き出しも本来機能ではない。

**tbls** は日本製 OSS で最も近く、`relations:` による FK 相当の手動宣言、lint（コメント必須、重複関連、viewpoint 未所属など）、viewpoint 単位の Markdown + Mermaid ER 出力、テンプレート個人化を持つ ([tbls README](https://github.com/k1LoW/tbls))。しかしメタモデルは tables / columns / indexes / constraints / triggers / relations / viewpoints に固定で、画面・機能・要件という別の型は加えられず、schema.json の JSON Schema は tbls が定義して利用者は拡張できない。設計思想も「DB が正本、文書は派生物」であり、Another Mood の「文書データが正本」とは逆向きである。HTML サイトも生成しない（GitHub で Markdown を読む想定）。A・E が欠け、C は宣言的でない。

**Doorstop** は項目 1 件 = YAML 1 ファイルで、「任意の数の拡張属性」と「リストや辞書」を許す唯一の要件ツールだが、それを型付けも検証もせず、publish 時に「list of dictionaries」を `<br>` 連結セルに平坦化する ([item.md](https://github.com/doorstop-dev/doorstop/blob/develop/docs/reference/item.md))。B は木の整合性検査と fingerprint で堅いが、リンク種は parent 一種のみ。C/D は固定 publisher（text / Markdown / HTML / LaTeX）で、テンプレートとは HTML なら CSS ファイル一つ、LaTeX なら yml + class ファイルを指す ([publishing.md](https://github.com/doorstop-dev/doorstop/blob/develop/docs/cli/publishing.md))。自己定義は「Requirements management using version control」 ([PyPI](https://pypi.org/pypi/doorstop/json))。

**StrictDoc** は文書ごとの `[GRAMMAR]` で要素 TAG を自由に名付けられるが、フィールド型は `String` / `SingleChoice` / `MultipleChoice` / `Tag` の 4 種のみ、各要素は STATEMENT/DESCRIPTION/CONTENT のいずれか一つの content フィールドを必須に持ち、メタフィールドは単一行、関係は Parent / Child / File のみ ([grammar_grammar.py](https://strictdoc.readthedocs.io/en/stable/_source_files/strictdoc/backend/sdoc/grammar/grammar_grammar.py.html), [user guide source](https://github.com/strictdoc-project/strictdoc/blob/main/docs/strictdoc_01_user_guide.sdoc))。`IS_COMPOSITE` による入れ子は文書木の包含であってオブジェクト値フィールドではない。描画は 6 種の `VIEW_STYLE` から選ぶもので利用者テンプレートはなく、コンプライアンス行列は「生成する」のではなく Parent と Child 関係を持つノードで「書く」パターンとして文書化されている。文書（`.sdoc`）が執筆単位なので「一つのデータセットから多数の文書」という概念自体がない。Markdown は「experimental」 ([feature map](https://strictdoc.readthedocs.io/en/stable/stable/docs/strictdoc_02_feature_map.html))。

### DIY スタックで何が組めて、何が組めず、糊のパッケージはあるか

個々の部品は揃っている。JSON Schema 検証は `jsonschema` や LinkML（LinkML スキーマから JSON Schema を生成して検証）、CUE の `cue vet` が YAML を行番号付きで検証する ([LinkML validation](https://linkml.io/linkml/data/validating-data), [CUE and YAML](https://cuelang.org/docs/concept/how-cue-works-with-yaml))。「データ → Jinja → 多数ファイル」は gomplate の `--input-dir` / `--output-map`、Jsonnet の `-m`、textX-jinja で可能 ([gomplate usage](https://docs.gomplate.ca/usage/), [Jsonnet](https://jsonnet.org/learning/getting_started.html))。「レコード 1 件 = ページ 1 枚」のサイトは Eleventy の pagination `size: 1` と Hugo の content adapter（v0.126.0、2024-05-14 以降）が担う ([Eleventy pagination](https://www.11ty.dev/docs/pagination/), [Hugo content adapters](https://gohugo.io/content-management/content-adapters/))。散文に表を混ぜるには sphinxcontrib-datatemplates（「mix machine-readable data with prose」）や mkdocs-macros がある ([datatemplates](https://sphinxcontribdatatemplates.readthedocs.io/), [mkdocs-macros](https://mkdocs-macros-plugin.readthedocs.io/en/stable/pages/))。表形式に限れば FK 検査も Frictionless の `foreign-key` エラーで既製である ([Frictionless FAQ](https://v4.framework.frictionlessdata.io/docs/faq))。2026 年の新顔として Typst 0.15.0（2026-06-15）の bundle 出力は一つのプロジェクトから複数の HTML/PDF を出せるようになったが、HTML 出力は「Do not use this feature for production use cases」でフィーチャーフラグ付き、CSS を出さず、ページ間リンクは著者が組む ([typst v0.15.0](https://github.com/typst/typst/releases/tag/v0.15.0), [Typst HTML](https://www.typst.app/docs/reference/html))。

欠けるのは四つで、いずれもライブラリの形で存在しない。第一に、利用者スキーマで定義された**入れ子レコード群**に対する FK 解決——どのフィールドがどの型を指すか、id の一意性、エラー報告——は Frictionless（平坦 CSV）と sphinx-needs / Doorstop（固定エンティティ）にしかない。第二に、安定した意味論を持つ宣言的 filter / sort / join / group / flatten ビューはどの OSS にもなく、Hugo の adapter は生成中に `Site.Pages` を参照できず、パス衝突は「published page の内容は不定」になる ([Hugo content adapters](https://gohugo.io/content-management/content-adapters/))。第三に、参照から導出される生成ページ間の自動相互リンクは、既存の参照検査が散文ラベル（MyST、Asciidoctor `-v`、Antora xref-validator）かページパス（Hugo `ref`、Zola `@/`）を対象にしているため、レコード参照からは生まれない。第四に、散文 Markdown ファイルをレコードの第一級データとして束ねる仕組みは Astro の frontmatter + body 以外になく、それも同一レコードを YAML と隣接 `.md` に分けることはできない。調査者の推定では DIY の到達度は A ≈ 90%、B ≈ 20%、C ≈ 50%、D ≈ 70% で、「有能な開発者が数日で一回限りのパイプラインを組める」が、「宣言されたビュー言語・スキーマレベルの参照宣言・参照由来の相互リンクを持つ再利用可能なツール」にはならない。この数値は出典のある統計ではなく調査ノートの推論である。

糊のパッケージは見つからなかった。2026-10-15 に `gh search repos` で `jsonschema jinja2 markdown`、`yaml markdown documentation generator`、`yaml jinja markdown generator`、`data-driven documentation generator`、`jinja2 static site yaml schema`、`jsonschema jinja2 generator`、`single source of truth documentation` を走らせた最上位は menagerie（5 スター、2024-10 最終 push）、yamldocs（16 スター、2023、PHP、スキーマ・参照検査なし）、data-dictionary-builder（15 スター、データモデル専用）で、GitHub topic `yaml-to-markdown` は「hasn't been used on any public repositories, yet」だった ([menagerie](https://github.com/Bwc9876/menagerie), [yamldocs](https://github.com/yamldocs/yamldocs), [data-dictionary-builder](https://github.com/valerylobachev/data-dictionary-builder), [topic](https://github.com/topics/yaml-to-markdown))。Web 検索で出るのはスキーマ文書化器（jsonschema2md 系、json-schema-for-humans 2.1.0 / 2026-10-07）ばかりで、「スキーマの文書化」と「スキーマに従うデータの文書化」は明確に別市場である ([json-schema-for-humans](https://github.com/coveooss/json-schema-for-humans))。awesome リストにも「awesome docs-as-code」は存在せず、testthedocs/awesome-docs は SSG・スタイルガイド・リンタの分類で、スキーマ駆動の項目を持たない ([awesome-docs](https://github.com/testthedocs/awesome-docs))。日本語圏でも同じ形が繰り返される。Qiita @endk（2019）は画面設計書 YAML に JSON Schema を当て handlebars で Markdown 表にし、クロスリファレンスは「今後の課題」、note hirokaji（2025）は `/specs` の YAML を唯一の情報源に PR ごとに自作 validate.mjs → generate.mjs → `must_cover` カバレッジ判定を回すが、文書間の参照整合性には触れず、いずれも公開リポジトリがない ([Qiita @endk](https://qiita.com/endk/items/2ae6ab257f0ad42a3bd8), [note hirokaji](https://note.com/tasty_dunlin998/n/nba2533cdc161))。日立の 2014 年論文は「画面設計書やデータベース設計書などの複数の設計書に記述された項目間の不一致」が規模を問わず発生し手動では検出しきれないと実証し、設計書テンプレート + 整合チェックツールを提案したが社内に留まった ([IPSJ DP Vol.5 No.3](https://ipsj.ixsq.nii.ac.jp/record/102257/files/IPSJ-DP05032013.pdf))。パターンは 12 年にわたり認識され続け、毎回スクリプトで終わっている。

### 二つの決断への含意: 破棄の根拠はなく、公開には「比較の一行」が要る

**破棄について。** 置き換え候補は存在しない。最も近い sphinx-needs に乗り換えれば、カラム一つ一つが ID 付き need になり、データは RST/MyST で書き、CRUD 行列は 4 種のリンク型 + needtable か自作 `filter-func` で擬似的に組み、すべてが need の箱として描かれる。Astro に乗り換えれば、スキーマは TypeScript になり、壊れた参照は描画時に `undefined` を触るまで発見されず、Markdown 成果物は出ない。LinkML に乗り換えれば、スキーマ文書だけが既製で、データ文書は停止した renderer か自作 Jinja になる。いずれも Another Mood の六軸のうち二つ以上を手放す移行であり、「同じ仕事をする既製品がある」という破棄の前提が成り立たない。

**公開について。** ニッチは空いているが、見る人は必ず既知のツールに引き寄せて理解する。公開文で先回りして述べる価値がある差分は、競合ごとに一つずつに絞ると次のようになる。sphinx-needs に対しては「エンティティ型は利用者が JSON Schema で定義し、入れ子オブジェクトと配列を持てる。データは YAML/JSON、文書は Jinja ビューから生成し、Markdown も成果物として出る」。Astro に対しては「参照はビルド時に実在検査され、壊れていればビルドが止まる。スキーマは TypeScript でなく平文の JSON Schema。出力は HTML サイトと Markdown の両方。Python 単体で Node 不要」。LinkML に対しては「文書化するのはスキーマではなくデータ。ER 図とデータ辞書（スキーマ由来）と CRUD 行列・ユースケース・トレーサビリティ表（データ由来の join/group）を同じデータセットから出す」。tbls に対しては「メタモデルを利用者が定義する。DB が正本ではなく文書データが正本で、RDB 以外の型（画面・業務ルール・要件）も同じ仕組みで扱う」。DIY（jsonschema + Jinja + MkDocs）に対しては「宣言的ビュー言語、スキーマでの参照宣言、参照由来の自動相互リンク、散文 Markdown のレコード束縛の四つがパッケージ化されている」。

聞かれると予想すべき比較は、英語圏では「Astro content collections で足りるのでは」「sphinx-needs の schema validation と何が違う」「jsonschema と Jinja を自分で繋げば済むのでは」「LinkML の gen-doc は」「Hugo の content adapter / Eleventy の pagination は」「dbt docs のように固定スキーマで十分では」「なぜ DB / Notion / Semantic MediaWiki でなく平文か」の七つ、日本語圏では「tbls との違い」「Excel 出力はあるのか」「AI に設計書を書かせれば済むのでは」の三つである。dbt は良い説明の足場になる。`ref()` を parse 時に解決して欠落を error にし、manifest から lineage 付きの docs サイトを出す dbt は、Another Mood が利用者定義型に一般化しているものの固定スキーマ版と言える ([dbt ref()](https://docs.getdbt.com/reference/dbt-jinja-functions/ref))。AI に対しては、国内の 2026 年トレンドが「構造化 Markdown/YAML を AI に読ませる・書かせる」方向にあり、Claude Skills で設計書 6 点を一括生成する記事が「テーブル定義書と CRUD 図の内容が食い違う」を手作業の痛点として挙げつつ機械的検証なしに「前段成果物を参照させる」運用で整合性を担保している点が参考になる ([Qiita jtths474](https://qiita.com/jtths474/items/690d387871342619889a))。決定論的な生成と機械的な整合性検証を持つツールは、AI ワークフローの入力層・検証層として位置づけるのが自然である。

逆に、競合が持ち Another Mood が（記述上）持たない機能も正直に把握しておくべきである。Doorstop・OpenFastTrace・sphinx-graph の fingerprint / revision による変更影響検出、Langium の LSP による参照補完、LikeC4 の図レイアウトと対話的サイト、StrictDoc の非開発者向け Web エディタ、sphinx-needs のトレーサビリティ語彙（status / tags / 多段 network 制約）はいずれも Another Mood の軸外にある。これらは「要件管理ドメインの機能」であって汎用データの機能ではないが、質問された時に「それはやらない、代わりに LikeC4 の `export json` や tbls の schema.json を入力にできる」と補完関係で答えられるようにしておくと、競合との対立構図を避けられる。

### 未検証事項と調査の限界

年の推定が残る版がある。Astro 7.3.8、Eleventy 3.1.6（別ノートは API で 2026-06-02 を確認）、Zola 0.23.6、LikeC4 1.60.0、textX 4.4.0、Langium 4.4.0、tbls 1.96.1、sphinx-needs の GitHub 側リリース、Widoco、Wiki.js は GitHub のリリースページが年を省くため文脈推定であり、Hugo・LinkML・StrictDoc・Doorstop・Frictionless・Typst・SMW のみ API または公式ページで年まで確定している。Astro・Hugo・Eleventy・Gatsby・Zola・Jekyll・Docusaurus・Lume のライセンスは事前知識で未再確認。Astro の実験的 "Collection storage"（v7 ナビに存在）が参照検証を変えるかは未調査で、Gatsby の `@link` が欠落 id で error か null かも文書化されていない。StrictDoc が存在しない UID を指す Parent `VALUE` に対して error を出すか黙って省くかは取得範囲に明文がない。linkml-store が平文 YAML/JSON をロードなしに直接バックエンドとして扱えるかは未確認で、「DuckDB/MongoDB 前提」は例からの判断である。tbls の `templates:` の表現力（ループ・条件・他テーブル参照）は README 要約から確定できなかった。sphinx-needs のスター数 312 は履歴に対して低く、リポジトリの再作成・移管の可能性があるが未検証。GitHub のコード検索（認証が必要）と PyPI の全文検索（API がない）は実施できておらず、低スターの PyPI 専用パッケージや日本語 README の小規模リポジトリ（「設計書」「画面定義書」「CRUD図」を名に含むもの）の悉皆調査は未実施。Strapi / Directus のリレーション仕様ページは取得不可（Directus docs は 404）、OBDZ の 2026 年時点の提供状況・出力形式・価格は公式ページ到達不可で未確認。各候補で ER 図・データ辞書・CRUD 行列・ユースケース・画面定義・トレーサビリティ表の六種を実際に試作して比べた一次情報は存在せず、「現実的に出せる」順位は機能記述からの推論である。DIY の到達度パーセンテージも同様に推論であり、出典のある数値ではない。

### 結論

調査が明らかにした構造は「二つの分断の継ぎ目」である。一つは「スキーマを文書化する市場」（LinkML gen-doc、json-schema-for-humans、Widoco、pyLODE）と「データを文書化する市場」（SSG、要件ツール、wiki）の分断で、前者は豊富、後者は固定メタモデルか手続き的か DB 常駐のいずれかに割れている。もう一つは「参照整合性を本物にするためにモデルを固定した系譜」（sphinx-needs、Doorstop、Frictionless、dbt）と「モデルを自由にするために整合性を手放した系譜」（Astro、Hugo、Eleventy、LinkML 単体）の分断である。Another Mood はこの二つの継ぎ目に同時に立っており、12 年分の DIY 記事と日立の論文は、継ぎ目に需要があることを示している。

したがって作者の本当のリスクは冗長性ではなく発見可能性である。既製の分類名がない道具は「Astro の劣化版」「sphinx-needs の汎用版」「Jinja のラッパ」のどれかとして読まれやすい。公開文は機能列挙より先に、どの分類にも属さない理由——型は利用者が決め、参照はビルドで止まり、同じ一件が ER 図と CRUD 行列と散文の章に同時に現れる——を一段落で述べ、七つの英語圏比較と三つの日本語圏比較に一行ずつ答えを添えるのが、この調査結果から導かれる最も実践的な含意である。

## 告知文の骨子 (Q3 の覚書、2026-10-15)

上の競合調査を受けて、同日の対話で出た告知文の筋。Q3 に着手するときの出発点として残す。文体は告知そのものではなく、段の並びと各段の役割を書いた覚書。

### 筋

1. **痛み** — みんな設計書の Excel で消耗する。
2. **いまの流れ** — AI に作業させるにあたって、参照すべき要求仕様をソースリポジトリに同梱させるやり方はいいやり方だ ([Qiita: Claude Skills で設計書 6 点を生成する記事](https://qiita.com/jtths474/items/690d387871342619889a) がその一例)。
3. **その流れの限界** — ドキュメントは修正が入り続けるもの。整合性を保っていくのが大変。記事の運用でも、整合性は「前段の成果物を参照させる」ことで担保していて、機械的な検証はない。
4. **毎回作り直し** — どの仕様から固まっていくかはプロジェクト次第。プロジェクトごとに skill を書き直す。
5. **だったら** — Excel の代わりに「型は利用者が決め、参照整合性の違反はビルドで止まり、同じ一件が ER 図と CRUD 行列と散文の章に同時に現れる」ツールがあればいいのではないか。
6. **作りました** — サンプルはこれ (二文書 showcase)。インストールして scaffold から同じ仕様書を作って、できあがる YAML を眺めてみてください。お好きなエージェントに、お好きなように変更を命令してみてください。

### 各段が担うこと

- 3 → 5 のつなぎが本ツールの核心をそのまま言う。「プロジェクトごとに skill を書き直す」の答えが「スキーマ・ビュー・テンプレートを書く」で、それは平文で Git に入り、エージェントは `mood docs read` で読める。[Product Vision](../../10-concept/10-product.md#ai-エージェントによる認知負荷の吸収) の「認知負荷をエージェントに吸収させる」が、抽象論ではなく運用の話として伝わる。
- 5 は「なぜこんな当たり前のものがないのか」への答えも含む。競合調査が示した分断 (整合性を本物にしたツールはモデルを固定し、モデルを自由にしたツールは整合性を手放した) に対して、両方を同時に取るという選択をした、ということ。告知では、ここで価値の高さをしれっと歌ってよい。言い方の候補: 「RDB を知っている者には両取りは当然に見えた。ただ、作ってみると工夫がそれなりに要ったのも確かだ」。工夫の中身は [データモデル](../../10-concept/10-product.md#データモデル-規律を与えた-json-の木) の節が持つ (RDB が禁じる入れ子を許しつつ、FK と宣言的なクエリが成り立つだけの規律を残す)。
- 6 の試し方は「触って判断してください」であって「質問してください」ではない。告知後の反応に付き合わない方針と整合し、同じものを作ろうとしている人も YAML を眺めれば自分で判断できる。

### 告知の目的と、そこから決まること

- 目的は二つ。本ツールの保守を手放す (かつ、本ツールで作られたものを作者自身が使い続ける) ための宣伝と、同じものを作ろうとしている人に別のことへ情熱を注いでもらうこと。即時の反応が求められる場には出ない。
- この目的で効くのは告知の瞬間の盛り上がりではなく、「作ろうかな」と思った人が検索や LLM で見つけられること。残り続けるもの (記事、GitHub topics / PyPI classifiers、awesome リスト) を優先し、Show HN のようにコメント欄に作者がいる前提の場は見送るか、記事のリンクを置く程度にとどめる。順序 (日本語圏 / 英語圏) は、反応を見て直す運用をしないなら重要度が下がる。
- 後継者は告知から直接は現れない。利用者がつき、その中で困った人が fork する流れになる。MIT なので受け皿はリポジトリ移譲より fork が自然。README の Status に「作者の用途に対しては完成 / 以後の保守は作者が引き受けない / fork 歓迎」を正面から書く (R3)。
- 「やらないこと」を書く。読み手は自分のドメインの軸 (変更影響の検出、LSP、図のレイアウト、Web エディタ、要件管理の語彙、実物からの逆生成、Office 出力) で測りに来るので、先に「その軸では測っていない。要件管理ツールや図ツールの入力側に置くか、出力を渡す側になる」と言っておく。聞かれるはずの比較 (英語圏で七つ、日本語圏で三つ) と競合ごとの一行の差分は、上の調査結果の「二つの決断への含意」節にある。

### チャネル (2026-10-15 時点の案)

場所の数は要らない。検索に残る長文が言語ごとに一本あればよい。

- **日本語圏: Zenn に一本**。六段の筋をそのまま記事にする。Twitter は記事リンクと一行の導線を一回。note は、書くなら Zenn の複製ではなく、非エンジニア寄りの読者に向けて 1〜4 段 (Excel で消耗する側の話) を短く書いて Zenn へ送る形。省いても損はない。
- **英語圏: 同じ記事の英訳を dev.to に一本**。英語版 showcase (S10) にリンクするので、日本語の後になる。記事より太い経路は GitHub 検索・PyPI・LLM なので、README の最初の画面 (R3)・GitHub topics・PyPI の classifiers / keywords を記事と同じ重さで扱う。任意で PyCoder's Weekly 等のニュースレターにフォームから URL を送る (その後の対応は要らない)。
- **見送り**: Show HN、Reddit (作者がコメント欄にいる前提の場)。Write the Docs Slack (主題は最も近く、[規約](https://www.writethedocs.org/slack/)は `#community-showcase` での自作の共有を許すが、文化として継続的な参加を期待する場で、一見の一投稿は歓迎の中心ではない)。目的は「それを目的とする人の検索に引っかかること」であり、コミュニティへの参加はその手段に含めない。
- **記事の末尾に Status を置く**。記事は数年後の検索流入の着地点でもあるので、README の Status と同じ一文 (作者の用途に対しては完成 / 以後の保守は作者が引き受けない / fork 歓迎) を記事側にも書く。後から読む人への親切であり、反応に付き合わない方針の説明にもなる。

### 前提

- 6 の「scaffold から同じ仕様書を作る」には、二文書 showcase が bundled blueprint として配られている必要がある。2026-10-15 時点で `mood blueprint list` に出るのは starter / music / japanese-table-design / sbom の四つで、system-dev-docs-ja は showcase/ にあるが `showcase/index.yaml` に未登録。S9 (合成ビューで二文書に割る)・S10 (英語版) の完了と合わせて登録する。
